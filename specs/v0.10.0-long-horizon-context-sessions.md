# v0.10.0 — Long-Horizon Context Sessions

## Status

Released

## Learning Question

What becomes observable and controllable when one Research Worker can continue across bounded
in-memory context sessions, replacing an unsafe-to-replay active history with a validated
research-state summary while preserving run-level identity, tools, budgets, and stopping
semantics?

## Problem and Rationale

Release 0.9.0 lets only the Research Worker choose between an OpenAI-hosted model and a local
open-weight model while the other model stages remain OpenAI-hosted. Release 0.10.0 retires the
local runtime path and replaces stage-specific routing with one required run-level `LLM_PROVIDER`.
The selected provider and its environment-configured model serve every LLM call in Scope,
Supervisor, Worker research, context summary, Write, Critic, and Revise. `LLM_PROVIDER` accepts
only `openai` and `deepseek`; DeepSeek V4 Flash is the DeepSeek acceptance baseline rather than a
hard-coded runtime model.

Every Worker still has one `input_items` list. Each model turn appends all returned Responses items
and every linked function output, and the next request replays that complete ordered history. Six
model turns, five tool attempts, two selected-source reads, and bounded tool results keep the
current history small enough for the verified release, but merely raising those limits would make
one request grow for the entire Worker run.

That growth creates two distinct problems:

- the next request can approach or exceed the selected model's context window; and
- even before a hard API rejection, an increasingly long trajectory can make prior evidence,
  unresolved gaps, and the next useful action harder for the research policy to recover.

The existing `context_limit` termination reason was reserved in release 0.7.0 but has no
application-owned budget or stopping path. Provider request failures are classified as
`model_error`, so the current application cannot distinguish its own decision to stop an unsafe
replay from an endpoint failure that has already occurred.

Release 0.10.0 turns the single Worker history into a sequence of bounded context sessions:

```text
AgentRunRequest
    -> session 1: task + approved brief + fresh history
       -> search/read/tool loop
       -> application context boundary
       -> selected run-level model creates ResearchStateSummary
       -> application validates and renders the summary
    -> session 2: same task + same brief + validated summary
       -> continue with fresh Responses history and the same run budgets
       -> finish notes or cross one final boundary
    -> AgentRunResult
```

The boundary is lossy by design. The application preserves only a bounded, validated account of
completed work, selected sources, unresolved questions, and next actions. It does not claim that
a summary is equivalent to the full Responses history or that omitted evidence can be recovered.
That loss is part of the learning mechanism and must remain visible.

### Research and API decision

The [ReSum paper](https://arxiv.org/abs/2509.13313) reports that periodically converting a growing
search-agent history into a compact reasoning state can extend exploration, while also observing
that an untrained policy is not automatically aligned to summary-conditioned reasoning. The
[LongSeeker paper](https://arxiv.org/abs/2605.05191) studies more adaptive operations such as
compression, rollback, snippets, and deletion. This release adopts only the smallest deterministic
periodic-summary mechanism. Model-selected context operations, rollback, retained raw tails,
training for summary-conditioned reasoning, and context-quality evaluation remain later work.

OpenAI now provides `POST /responses/compact`. The official
[compact-response reference](https://developers.openai.com/api/reference/java/resources/responses/methods/compact)
returns provider-produced compaction items, and current official model guidance says those items
are opaque and should be replayed without parsing. That hosted feature is useful as a future
comparison but does not answer this release's learning question: the summary structure, validation,
source references, and session replacement would be hidden. DeepSeek's Responses compatibility
contract does not support `context_management`, so it also does not provide a matching automatic
compaction mechanism.

Release 0.10.0 therefore uses ordinary non-streaming `responses.create` requests through the
existing `llm_call` primitive. The run-level selected client and exact environment-configured model
create every response, including a Pydantic-validated `ResearchStateSummary` with Structured
Outputs. This keeps the mechanism explicit and shared across the OpenAI and DeepSeek providers.

DeepSeek's official [Responses API compatibility guide](https://api-docs.deepseek.com/guides/responses_api/)
documents the `https://api.deepseek.com` base URL, the exact `deepseek-v4-flash` model ID,
function tools, `max_output_tokens`, JSON-schema `text.format`, and Responses-style token usage.
It also documents that the endpoint is stateless: `previous_response_id`, Conversations, and
`context_management` are unsupported. This matches the application's existing manual history
replay and explicit context-session design. DeepSeek ignores `parallel_tool_calls` and always
permits parallel calls. The application therefore accepts zero, one, or multiple function calls
in one response, executes every budget-permitted call synchronously in response order, and
appends one linked output for every returned call. The official
[model table](https://api-docs.deepseek.com/quick_start/pricing/) records a one-million-token
context window for `deepseek-v4-flash`, exceeding this release's declared minimum.

No provider-managed compaction, tokenizer library, model metadata request, provider-specific
request extension, or hidden hosted summarizer is added.

## Architectural Decision

The complete application remains the deterministic Scope workflow, sequential Supervisor-Worker
Research subsystem, and Write-Critic-Revise report workflow from release 0.9.0:

```text
load and validate run configuration
    -> select one LLM provider, API key, and model name once
    -> selected-provider Scope workflow and approved ResearchBrief
    -> selected-provider Research Supervisor loop
       -> one AgentRunRequest
       -> same selected client and model
          -> one through five context sessions
          -> zero through four validated context summaries
          -> one terminal AgentRunResult
       -> merge only completed notes
    -> selected-provider Write-Critic-Revise workflow
    -> final Markdown report
```

Ownership boundaries are fixed as follows:

- `AgentRunRequest` continues to define one immutable Worker invocation and records the run-level
  provider and model selection.
- `AgentRunState` owns run-level counters, the active session history, the source registry, the
  successfully read source-ID set, the latest validated summary, context accounting, and terminal
  state.
- One context session owns only its current `input_items`. Replaced session histories are not
  retained as recovery data or copied into `AgentRunResult`.
- The application decides when a context boundary is required from bounded usage and projection
  rules. The research policy cannot request, delay, or suppress a boundary.
- One selected client and exact model create every LLM response in the run. The application does
  not construct the unselected provider client, require its credentials, or route individual
  stages to another provider.
- Pydantic validates the model-produced summary shape. Application checks additionally validate
  every summarized source identifier against the run-owned source registry and every claimed
  selected-source evidence level against the run-owned successfully read source-ID set.
- The source registry, successfully read source-ID set, and all turn, tool, read, and context
  counters remain run-level and survive a session replacement.
- The Research Supervisor sees only the terminal `AgentRunResult`, as before. It does not observe
  or control Worker sessions.

A session is a context-management boundary inside one Agent run, not a new Worker, task, rollout,
conversation, retry, or provider request chain.

## User-Visible Behavior

The CLI invocation, five top-level stages, Scope approval, Supervisor policy, source registration,
report stages, and final report remain unchanged. The initial configuration line and every Agent
Run Result label the run-level `LLM provider` and exact `Model`; the former `Model source` label is
removed.

Most short Workers may finish in session 1 and print no summary. A longer Worker prints one
visible boundary before the application discards its active history:

```text
  [Context 1/5] Session | STARTED | fresh task history
    [Context 1/5] Boundary | REQUIRED | projected 12,418 tokens; trigger 12,000
    [Summary 1/4] Research state | STARTED

================================================================================
RESEARCH STATE SUMMARY | WORKER 1 | SESSION 1 -> 2
================================================================================
...validated summary...
================================================================================

    [Summary 1/4] Research state | COMPLETED | validated
  [Context 2/5] Session | STARTED | validated summary
```

The exact progress helper may preserve the repository's current spacing, but the Worker number,
old and new session numbers, boundary reason, bounded token values, and summary validation outcome
must remain visible in this order. The application prints the deterministically rendered summary,
not raw model output.

Every Agent Run Result adds:

```text
Context sessions: <used>/5
Context summaries: <used>/4
Peak observed input tokens: <count>
Peak projected input tokens: <count>/20000
```

Existing provider, model, status, termination reason, turn, tool, and read lines remain. A completed Worker
still prints one final research-notes block only after its Agent Run Result.

Worker research requests set `parallel_tool_calls=False` as a provider hint. If an endpoint still
returns multiple custom function calls, the application executes them synchronously in response
order. Tool schemas, results, hard limits, and linked result ordering remain application-owned.

## Runtime Flow

### Run initialization

For each Supervisor task:

1. Build the existing `AgentRunRequest` with Worker number, approved brief, task, run-level LLM
   provider, and model name.
2. Initialize one `AgentRunState` with session number 1, no summary, zero run-level usage, a fresh
   source registry, an empty `read_source_ids` set, and the existing task-and-brief user input.
3. Print the session-1 start boundary.
4. Enter the existing synchronous Worker loop with the expanded run-level budgets.

### Ordinary research turn

For each ordinary research request:

1. Confirm that a model turn remains.
2. Send the active session's complete ordered `input_items` through the run-level selected client,
   selected model, `RESEARCH_INSTRUCTIONS`, current strict tools, `store=False`, and
   `parallel_tool_calls=False`.
3. Use `tool_choice="auto"` while tool budget remains. After tool budget exhaustion, append the
   existing application-owned final-notes input and use `tool_choice="none"`.
4. Count the request as one run-level model turn.
5. Apply the existing cancellation, refusal, incomplete-response, malformed-output, and final-
   notes classification before considering a context boundary.
6. Require `response.usage.input_tokens`, `output_tokens`, and `total_tokens` to be non-negative
   integers with `total_tokens == input_tokens + output_tokens`. Update the run's peak observed
   input count.
7. Append every returned output item in its original order.
8. If the response requests one or more tools, execute every budget-permitted call synchronously
   in response order and append its linked `function_call_output`. A call beyond the remaining
   tool budget is not executed, does not increment tool usage, and receives a linked limit-error
   output so the replayed Responses history remains complete. After a successful normalized
   `read_source_tool` result, add that application-resolved source ID to the run-level
   `read_source_ids` set. Tool and read counters, the source registry, and `read_source_ids`
   remain run-level.
9. Compute the projected next research-input size. If it is below the session trigger, continue
   in the current session. If it reaches the trigger, run the context-boundary flow before any
   next research request.

A response with valid final notes completes immediately even if its usage reaches the session
trigger. No summary is generated after the Worker has already completed.

### Context-boundary flow

When the projected next research input reaches the trigger:

1. Print the required boundary with current session, projected input, and trigger.
2. If the projection exceeds the pre-summary session projection hard limit, finalize
   `failed/context_limit` without making a summary request.
3. If five sessions have already started, finalize `failed/context_limit`.
4. If fewer than two model turns remain, finalize `failed/turn_limit`; one turn is required for
   the summary and at least one for resumed research or forced final notes.
5. Append one short application-owned summary request to the active history for the summary call
   only.
6. Send the full active history through the same run-level selected client and model using
   `RESEARCH_SUMMARY_INSTRUCTIONS`, `store=False`, no tools, `ResearchStateSummary` as the Pydantic
   text format, and a 16,000-token output limit.
7. Count the summary request as one run-level model turn. Validate its response status, refusal
   state, usage, parsed type, field bounds, source identifiers, and source evidence levels.
8. Print the validated summary block and summary completion progress.
9. Increment the session and summary counters.
10. Replace `state.input_items` with one new user item containing the same approved brief, same
    task, run-level remaining budgets, and a deterministic rendering of the validated summary.
11. Replace any prior `latest_summary` value. Do not retain the replaced Responses items as a
    trace, fallback tail, or recovery checkpoint.
12. Print the new session start and continue the ordinary Worker loop.

The source registry and `read_source_ids` remain intact, so a summary may carry an earlier
application-issued source ID and its application-observed access level into the new session, and
the existing read tool may resolve it. Source identifiers absent from the summary remain in
application memory but are not exposed to the resumed model unless a later tool result returns
them again.

### Completion

Final notes, tool-limit completion, turn-limit failure, cancellation, and all existing model or
tool failures retain the release 0.9.0 result and fail-fast behavior. Finalization copies the new
context accounting into `AgentRunResult`. Only completed notes merge into `ResearchState`.

## Context Budget and Projection Contract

Release 0.10.0 uses these fixed learning limits:

| Budget | Limit | Scope |
| --- | ---: | --- |
| Model turns | 15 | One Agent run, including summary requests |
| Tool attempts | 10 | One Agent run across all sessions |
| Selected-source reads | 4 | One Agent run across all sessions and within the tool limit |
| Context sessions | 5 | One Agent run |
| Context summaries | 4 | One Agent run; exactly one fewer than sessions |
| Session boundary trigger | 12,000 projected tokens | One active research session |
| Pre-summary session projection hard limit | 20,000 projected tokens | One active research session |
| Supervisor output | 8,000 tokens | One Supervisor decision request |
| Summary output | 16,000 tokens | One summary request |
| Projection overhead | 256 tokens | One pending linked function output |

Both provider model names are environment-configured. The DeepSeek acceptance scenario uses the
official `deepseek-v4-flash` model ID, but the application does not hard-code it or query model
metadata. Every selected model must satisfy this release's complete API contract and provide a
context window of at least 65,536 tokens. The
20,000-token value is a hard limit on the conservative projection of the next ordinary research
input; it is not an exact measurement or upper bound for the subsequent summary request's input.
The summary request appends a short summary instruction, replaces the
ordinary research instructions and tool definitions with summary instructions and a JSON schema,
and is not separately tokenized by the application. The 20,000-token projection plus a
16,000-token bounded summary output leaves a fixed conservative allowance for those changes and
for tokenizer or chat-template differences under the 65,536-token minimum context contract.
Supervisor requests retain an 8,000-token output allowance. Reasoning tokens count against
`max_output_tokens` on the selected provider paths: real DeepSeek acceptance showed that a
4,000-token Supervisor limit and an 8,000-token summary limit could each end with
`incomplete_details.reason=max_output_tokens` before returning a small validated value. The
official DeepSeek [Responses API reference](https://api-docs.deepseek.com/api/create-response/)
defines `max_output_tokens` as the combined upper bound for visible and reasoning tokens.

All requests retain the selected model's provider-default reasoning behavior. Real DeepSeek
probes with both `reasoning.effort=low` and `reasoning.effort=none` returned JSON inside Markdown
code fences even though `text.format` requested a strict schema, which the official SDK correctly
rejected as `json_invalid`. The application therefore neither overrides reasoning effort nor
strips or repairs fenced output. A model or endpoint that does not satisfy this declared contract
may fail at the existing `model_error` boundary; the application does not discover or silently
substitute a model.

One pre-verification DeepSeek run crossed required boundaries in its first three sessions, used a
fourth session to finish its remaining tool work, and reached another required boundary before the
forced-notes turn after tool exhaustion. A four-session limit therefore stopped before final
notes. The final real DeepSeek acceptance run reached session 5 after one Worker crossed boundaries
at projected inputs of 14,862, 13,980, 13,227, and 14,904 tokens. Five sessions and four summaries
preserve the same 12,000-token trigger and 20,000-token hard limit while allowing one final bounded
session for notes; the model-turn and tool budgets remain unchanged.

After one ordinary response and all of its linked tool outputs, compute:

```text
projected_next_input_tokens =
    response.usage.input_tokens
    + response.usage.output_tokens
    + sum(UTF-8 byte length of each compact JSON function_call_output)
    + 256 tokens for each function_call_output
```

The UTF-8 byte length is intentionally a conservative tokenizer-independent upper estimate for
new application-owned content. The estimate is not presented as exact provider tokenization.
Returned model output uses the endpoint's exact `output_tokens`; the application must not estimate
or inspect reasoning text. The same calculation is used on the OpenAI and DeepSeek paths.

The projection is updated only after a successful ordinary research response and its tool
boundary. Summary-response usage updates peak observed input but does not itself trigger another
summary. A fresh session cannot immediately summarize before completing at least one ordinary
research request.

`parallel_tool_calls=False` requests sequential tool use where the endpoint honors it. The
application does not rely on that hint: every returned function call receives one linked output,
execution remains synchronous and ordered, and the projection includes every linked output.
Actual tool executions remain bounded by the run-level tool and read budgets. No automatic
truncation is enabled. The application never drops an arbitrary prefix, deletes selected items
inside a session, or sends a request after its own hard projection has been exceeded.

## ResearchStateSummary Contract

Pydantic 2 defines one frozen Structured Output boundary with forbidden extra fields. The intended
shape is:

```text
ResearchStateSummary
    completed_work: 1..8 bounded strings
    visited_sources: 0..8 SummarySource values
    unresolved_questions: 0..6 bounded strings
    next_actions: 1..4 bounded strings

SummarySource
    source_id: bounded non-empty string
    evidence_level: discovery_snippet | selected_source
    key_evidence: bounded non-empty string
    limitations: bounded non-empty string
```

Field limits are:

- completed-work entries: at most 500 characters each;
- source IDs: at most 20 characters each;
- key-evidence entries: at most 600 characters each;
- source limitations: at most 300 characters each;
- unresolved questions: at most 400 characters each; and
- next actions: at most 300 characters each.

The summary instructions repeat every list-count limit and use conservative generation targets
below the hard character bounds: 400 for completed work, 450 for key evidence, 225 for source
limitations, 300 for unresolved questions, and 225 for next actions. Source IDs retain the exact
20-character hard limit. Real DeepSeek acceptance accepted the JSON schema but exceeded a
600-character key-evidence bound even after that hard limit was stated in the prompt. The smaller
generation targets leave room for model-side character-count error; Pydantic remains authoritative
and the application does not truncate, repair, or retry invalid summary output.

The summary instructions require:

- only work and evidence present in the active session history or its prior validated summary;
- concise findings rather than process narration, private reasoning, or copied raw tool output;
- enough provenance to distinguish source evidence from synthesis;
- an evidence level no stronger than the application-observed access level for each source;
- material disagreement, uncertainty, missing coverage, and failed search directions;
- only next actions that fit the original task and remaining run-level budgets; and
- no URLs, credentials, prompts, tool syntax, or invented source identifiers.

After Pydantic parsing, the application requires every `source_id` to be unique and present in
`state.source_urls`. `evidence_level` is a required literal value. `discovery_snippet` means only a
registered search result, abstract, or discovery snippet is known to have contributed.
`selected_source` means the application successfully normalized at least one `read_source_tool`
result for that source ID during the run. The application rejects a summary that labels a source
`selected_source` when its ID is absent from `state.read_source_ids`; conservatively labeling a
successfully read source as `discovery_snippet` remains valid. The deterministic renderer obtains
each URL from the source registry and prints it with the validated evidence level beside the
model's bounded evidence and limitation text. The model never supplies or replaces a URL in the
summary boundary.

Here, `visited_sources` means registered sources whose discovery snippet, abstract, or selected-
source content contributed to the active research state. The explicit evidence level prevents a
resumed Worker or terminal reader from treating discovery-only text as if the application had
performed a selected-source read. Shape and evidence-level validation still do not prove that the
model's `key_evidence` faithfully represents the source content.

The resumed input clearly labels the summary as application-validated research state and repeats
that source content is untrusted evidence, not instructions. It includes remaining model-turn,
tool, read, session, and summary budgets so the resumed policy does not assume fresh run limits.

Summary validation establishes shape, bounds, source identity, and a non-inflated evidence level;
it does not prove factual faithfulness or completeness. Omitted details are not recoverable after
the active history is replaced.

## Agent Run Contract Changes

`AgentRunStatus` and `AgentTerminationReason` gain no new members. `AgentModelSource` is renamed to
`LLMProvider`; its bounded values are `openai` and `deepseek`. `AgentRunRequest.model_source` and
`AgentRunResult.model_source` are renamed to `llm_provider`. Because Worker results are neither
persisted nor accepted as external input, these internal vocabulary changes require no stored-
result migration path.

`AgentRunState` adds the smallest context-session state needed by this release:

```text
context_session_number: starts at 1
context_summaries_used: starts at 0
latest_summary: ResearchStateSummary or None
read_source_ids: empty set of application-issued source IDs
peak_input_tokens: starts at 0
peak_projected_input_tokens: starts at 0
```

Its existing `input_items` now means only the active session history. Model-turn, tool, read,
source-registry, successfully read source IDs, status, termination, notes, and error fields remain
run-level. `read_source_ids` is updated only after a successful normalized selected-source result;
a rejected request or failed read does not add an ID.

`AgentRunResult` adds immutable copies of:

```text
context_sessions_used
context_session_limit
context_summaries_used
context_summary_limit
peak_input_tokens
peak_projected_input_tokens
context_trigger_tokens
context_hard_limit_tokens
```

Finalization requires:

- `1 <= context_sessions_used <= 5`;
- `0 <= context_summaries_used <= 4`;
- `context_sessions_used == context_summaries_used + 1`;
- non-negative peak token values;
- `read_source_ids` to be a subset of the run-owned source registry with no more unique IDs than
  successful selected-source reads;
- peak projected input no greater than the hard limit unless the result is
  `failed/context_limit`; and
- all existing status, termination, notes, error, turn, tool, and read invariants.

A summary call consumes a model turn but no tool or read attempt. Starting a new session consumes
no model turn by itself.

## LLM Provider and DeepSeek Compatibility Contract

Release 0.10.0 removes the release 0.9.0 local Worker client construction, configuration, and
stage-specific model routing. `LLM_PROVIDER` is required and accepts only `openai` and `deepseek`.
Configuration selection is exact:

| `LLM_PROVIDER` | Required API key | Required model name | SDK base URL |
| --- | --- | --- | --- |
| `openai` | `OPENAI_API_KEY` | `OPENAI_MODEL_NAME` | Official OpenAI default |
| `deepseek` | `DEEPSEEK_API_KEY` | `DEEPSEEK_MODEL_NAME` | `https://api.deepseek.com` |

`TAVILY_API_KEY` remains required independently. Empty or unsupported `LLM_PROVIDER`, an empty
selected API key, or an empty selected model name fails configuration before client construction.
Unselected-provider API key and model variables are neither required nor substituted. The
application constructs exactly one official OpenAI SDK client with `max_retries=0`, then uses that
client and the exact selected model name for Scope, Supervisor, every ordinary Worker request,
every summary request, Write, Critic, and Revise. There is no per-stage override or provider
fallback.

Both provider endpoints must return non-streaming Responses usage with non-Boolean, non-negative
integer `input_tokens`, `output_tokens`, and `total_tokens` values satisfying
`total_tokens == input_tokens + output_tokens` on every ordinary research and summary response.
Both must accept free-text Responses, function tools, and JSON-schema `text.format` for every
structured Scope, Supervisor, and summary request.
Every Pydantic Structured Output instruction explicitly requests the raw JSON object required by
the supplied schema and forbids Markdown code fences. DeepSeek's official
[JSON output guidance](https://api-docs.deepseek.com/guides/json_mode) requires the prompt to name
JSON and notes that empty content may still occur; the application uses the schema supplied by
`text.format`, validates through the official SDK and Pydantic, and does not strip fences, parse
free-form output, or retry an invalid value.
Scope instructions retain the inherited list counts and use conservative generation targets below
the Pydantic hard bounds: 225 characters per clarification question, 600 for the objective, and
225 for audience, time horizon, and every ResearchBrief list entry. Supervisor instructions use
targets of 75 characters for the title, 450 for the research question, and 150 for each of one
through three evidence targets. The Pydantic hard bounds remain 300/800/300 for Scope and
100/600/200 for Supervisor values and remain authoritative when provider output exceeds them.
The application sends `parallel_tool_calls=False`, but endpoint compatibility does not depend on
DeepSeek honoring it. The application accepts multiple returned function calls and executes the
budget-permitted calls synchronously in response order.

Complete compatibility requires one complete real workflow with each provider. In each workflow,
the selected provider must serve every model stage. At least one real Worker per endpoint must
cross a boundary, return a validated summary, resume from it, call another tool or return notes,
and complete through the same immutable result, or the endpoint must pass the real summary-
protocol probe plus the deterministic production state-machine sequence defined by the manual
acceptance scenario. A deterministic stub client alone cannot establish endpoint compatibility.
An endpoint that supports ordinary tool calls but not the other model stages, usage, or summary
Structured Outputs does not satisfy this release.

The application does not expose a configurable provider base URL, call Chat Completions, discover
model metadata, introduce a provider adapter, or route stages across providers. The released
v0.9.0 specification remains the historical record of the removed local path.

## CLI Contract

Invocation remains:

```text
uv run deep_research.py "Question"
```

`LLM_PROVIDER` and `TAVILY_API_KEY` are always required. The selected provider's API key and model
name are required exactly as defined above. The application no longer reads `WORKER_BACKEND`,
`MODEL_NAME`, `LOCAL_WORKER_BASE_URL`, `LOCAL_WORKER_API_KEY`, or `LOCAL_WORKER_MODEL_NAME`. No
context, summary, token, turn, tool, read, session, or provider base URL is configurable through
the CLI or environment in this learning release.

There is no user approval at a context boundary. ResearchBrief approval remains the only research
approval point, and user cancellation remains limited to the existing terminal-input and process
boundaries.

## Observability Contract

Live terminal output remains the only run observability mechanism. Release 0.10.0 newly permits
printing:

- context session and summary ordinal values;
- the fixed trigger and hard-limit values;
- exact input/output usage counts returned by the endpoint when used in boundary calculations;
- the conservative projected next-input count;
- the deterministic validated summary, including application-resolved source URLs and evidence
  levels; and
- context accounting in the terminal Agent Run Result.

It must not print API keys, base URLs, request headers, complete request bodies, instructions, raw
Responses items, complete old histories, unvalidated summary output, raw reasoning, encrypted
reasoning, tokenizer contents, server metadata, or model hardware details.
For a Pydantic validation failure, the concise model-error message may include only rejected field
paths and Pydantic error-type identifiers. It must not include rejected values, raw validation
input, or source content.

This release adds bounded context accounting, not structured tracing, telemetry, cost accounting,
latency measurement, quality scoring, or private chain-of-thought access.

## Artifact Contract

Release 0.10.0 creates no run directory and writes no application output files. The active history,
source registry, latest validated summary, counters, report-stage values, and final report remain
in process memory.

When a session is replaced, the old `input_items` list is not written, returned, retained in a
summary-history collection, or made recoverable by the application. Provider-side behavior outside
`store=False` is outside the application artifact contract. The validated summary is printed once
and only its latest value remains in mutable run state.

There is no checkpoint, resume file, durable memory, trace, trajectory, cache, evaluation artifact,
or training example.

## Failure and Stopping Behavior

Existing configuration, Scope, Supervisor, Worker, tool, cancellation, and report failures retain
their current process exit behavior.

Context-specific outcomes are:

- Missing, Boolean, negative, inconsistent, or malformed Responses usage on either a research or
  summary response becomes `failed/model_error`.
- A required boundary whose next-research-input projection exceeds the 20,000-token pre-summary
  session projection hard limit becomes `failed/context_limit` before a summary request.
- A required boundary after session 5 has begun becomes `failed/context_limit`.
- A required boundary with fewer than two model turns remaining becomes `failed/turn_limit`.
- A summary request exception, incompatible Structured Output request, incomplete response,
  refusal, missing parsed value, invalid field value, duplicate source ID, unknown source ID, or
  false `selected_source` evidence-level claim becomes `failed/model_error`.
- A top-level cancelled summary response becomes `cancelled/cancelled`.
- A context-window error returned by an endpoint despite the application projection remains
  `failed/model_error`; the application does not parse provider exception text to reclassify it.
- Successful final notes after tool exhaustion remain `completed/tool_limit`, including when a
  context summary occurred earlier.
- Exhausting 15 model turns without notes remains `failed/turn_limit`.

Every expected terminal outcome prints one Agent Run Result. An unsuccessful Worker does not merge
notes, does not start another Worker, and stops before report generation, as in release 0.9.0.

There is no summary retry, schema-repair request, smaller emergency summary, retained-tail fallback,
provider compaction fallback, model switch, endpoint switch, partial notes recovery, or partial
report.

## Known Limitations and Successor Boundaries

This release is a periodic structured-state-replacement baseline, not a production durable-memory
system. Its known limitations are part of the mechanism:

- the validated summary is lossy and receives provenance checks rather than semantic
  faithfulness verification;
- no recent raw response or complete recent tool boundary survives replacement;
- raw search and selected-source evidence remain only in the replaced history unless the summary
  carries their source identity and a bounded description;
- source registry entries survive in application memory, but source content is neither persisted
  nor retrievable after omission from the active model context;
- fixed projection thresholds do not adapt to evidence value, language, model behavior, or task
  phase;
- five sessions and 15 total model turns provide bounded continuation rather than indefinite
  execution; and
- an interrupted process cannot resume because this release creates no durable checkpoint.

These limitations intentionally motivate separate cumulative releases: v0.11 persists normalized
evidence, v0.12 links structured claims and citations to that evidence, v0.13 introduces durable
checkpoints and resume, and v0.15 compares this summary-only baseline with hybrid context memory.
The [ReSum paper](https://arxiv.org/abs/2509.13313) supplies the periodic-summary baseline and also
reports the need to adapt policies to summary-conditioned reasoning. Anthropic's
[context-engineering guidance](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
describes compaction, external memory, and subagent isolation as complementary context controls;
later releases test those mechanisms separately rather than silently adding them here.
