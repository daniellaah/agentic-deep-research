# v0.1.0 — Minimal Observable Tool Loop

## Status

Draft

## Learning Question

What is the smallest complete Responses API agent loop that can request a function tool,
execute it, continue model inference, stop safely, expose its trajectory, and produce a
final report?

## Problem and Rationale

A single model request does not demonstrate an agent harness. A useful first release must
show the boundary between model activity and application-owned tool execution without
mixing in web retrieval, source quality, planning, or multi-agent coordination.

The release therefore uses one deterministic local tool. This keeps the environment simple
while making every part of the loop observable:

```text
question
→ model response
→ function tool call
→ local execution
→ function_call_output
→ next model response
→ final answer
```

## User-Visible Behavior

The user runs one command with one question. The CLI:

1. validates required environment configuration;
2. creates a unique run directory;
3. displays concise progress as the run advances;
4. allows the model to request the available local tool;
5. executes requested tool calls;
6. continues until the model returns a final answer or a limit is reached;
7. writes the complete observable trace to `trace.jsonl`;
8. writes the final answer to `report.md`; and
9. prints the artifact paths and final status.

The CLI does not accept input after the run starts.

## Runtime Flow

The implementation uses `AsyncOpenAI` and `asyncio.run`.

Each iteration:

1. records an iteration-started event;
2. requests a Response from the configured model;
3. records response metadata, usage, and public output items;
4. finds every `ResponseFunctionToolCall` in the response output;
5. if calls exist, validates and executes them;
6. creates one `function_call_output` item for each call;
7. continues the Responses API interaction with those outputs and the completed
   response's `previous_response_id`; and
8. stops when no function call remains and final output text exists.

The exact Responses API continuation method must stay explicit in the code and trace.
Using an agent framework or hosted agent loop is not allowed.

## Response State Decision

This release uses `previous_response_id` to continue between model iterations. It does not
use the Conversations API and does not manually rebuild the complete provider input
history.

This choice keeps the first release focused on application-owned loop control and tool
execution. The trace records every response identifier and continuation link so the state
boundary remains visible. Manual history ownership and response compaction are deferred
until the long-horizon harness release, where they can be compared against this baseline.

## Local Tool

The release provides one function tool:

```text
get_current_utc_time
```

It accepts no arguments and returns the current UTC timestamp in an unambiguous ISO 8601
form.

The acceptance question is designed to require this tool. The tool exists to prove the
loop, not to provide research capability.

## CLI Contract

Planned invocation:

```text
uv run --env-file .env deep_research.py \
  "What is the current UTC time? Use the available tool and explain that this is a loop test."
```

Requirements:

- the question is one required positional argument;
- `OPENAI_API_KEY` must be present;
- `MODEL_NAME` must be present;
- missing configuration or question produces a concise error and nonzero exit code;
- normal progress is written to standard output;
- fatal errors are written to standard error;
- terminal text is English.

No additional CLI dependency is introduced.

## Trace Contract

The canonical trace format is newline-delimited JSON. Each line is one event with at least:

| Field | Meaning |
| --- | --- |
| `timestamp` | UTC ISO 8601 event time |
| `event` | Stable event name |
| `run_id` | Identifier shared by the complete run |
| `iteration` | Current model-loop iteration when applicable |
| `data` | Event-specific JSON object |

Required event families:

- `run.started`
- `iteration.started`
- `model.request.started`
- `model.response.completed`
- `tool.requested`
- `tool.execution.started`
- `tool.execution.completed`
- `report.written`
- `run.completed`
- `run.failed`

The trace records provider-visible response items, tool names, arguments, outputs, response
identifiers, continuation links, model name, timing, and token usage when available. It
must not claim to contain private chain-of-thought. Any reasoning summaries exposed by the
API are treated as provider output, labeled accurately, and are not required by this
release.

Every requested tool call must have a matching completion or failure event.

Events are appended as they occur so a failed run retains its trajectory.

## Terminal Projection

Terminal updates are derived from the same event creation path as the JSONL trace. The
first release displays event-level progress; token-by-token model streaming is out of
scope.

Terminal output should make these transitions clear without dumping raw JSON:

- run started;
- model iteration started;
- tool requested;
- tool execution completed or failed;
- final report written;
- run completed or failed.

## Artifact Contract

A run creates:

```text
runs/<run-id>/
├── trace.jsonl
└── report.md
```

The run directory must be created before the first API request.

On success, `report.md` contains the model's final Markdown output. This release does not
require citations or a fixed report outline.

On failure, `trace.jsonl` remains available. `report.md` may be absent if no final answer
was produced.

## Stopping and Failure Behavior

The loop has a small explicit maximum iteration count. Reaching the limit fails the run
instead of requesting indefinitely.

The run also fails on:

- invalid or unsupported tool names;
- malformed tool arguments;
- local tool execution errors;
- Responses API errors;
- a completed model response without tool calls or final text;
- artifact write failures.

A failure records `run.failed` whenever the trace destination remains writable and exits
with a nonzero status.

Automatic retries are out of scope for this release.

## Implementation Constraints

- All runtime code lives in `deep_research.py`.
- Use the OpenAI Responses API and official Python SDK directly.
- Do not use the OpenAI Agents SDK or another agent framework.
- Use only the current runtime dependencies in `pyproject.toml`.
- Prefer frozen, slotted dataclasses for named internal event values.
- Use the standard library for CLI parsing, time, paths, and JSON serialization.
- Keep tool registration and dispatch explicit.
- Use `previous_response_id` for response continuation in this release.
- Do not add automated tests.
- Do not add an HTTP API, Web UI, database, or package directory.

## Manual Acceptance Scenario

### Setup

Provide valid values in the local `.env` file:

```text
OPENAI_API_KEY=...
MODEL_NAME=...
```

### Run

```text
uv run --env-file .env deep_research.py \
  "What is the current UTC time? Use the available tool and explain that this is a loop test."
```

### Verify

Confirm that:

1. the terminal shows at least two model-loop iterations;
2. the model requests `get_current_utc_time`;
3. the local tool executes exactly once for the acceptance question;
4. the terminal does not expose hidden reasoning;
5. the run directory contains `trace.jsonl` and `report.md`;
6. every trace line is valid JSON;
7. the tool request has matching execution events;
8. the trace ends in `run.completed`;
9. the report contains a final answer based on the returned UTC value; and
10. the process exits successfully.

Then perform one failure check by omitting `MODEL_NAME` and confirm a concise error,
nonzero exit status, and no API request.

## Completion Criteria

The specification may become `Verified` when:

- the manual success and configuration-failure scenarios pass;
- Ruff and mypy pass for `deep_research.py`;
- the implementation remains in one runtime file;
- the trace and report are manually inspected;
- no requirement depends on unrecorded private reasoning; and
- the roadmap and README accurately describe the implemented behavior.

Only then may the project create the `v0.1.0` Git tag.

## Out of Scope

- paper or web search;
- citations and evidence quality;
- explicit research planning;
- mid-run user input;
- model token streaming;
- parallel tool execution;
- retries and checkpoints;
- context compaction;
- critique and report revision;
- multiple agents;
- automated tests or formal evaluation.
