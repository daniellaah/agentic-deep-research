# v0.14.0 — Idempotent Tools and Failure-Aware Orchestration

## Status

Draft

## Learning Question

What becomes safely recoverable when external tool attempts have stable execution identities,
transient failures receive bounded retries, and unsuccessful Worker results remain visible to a
Supervisor that can narrow, replace, accept partial work, or stop?

## Problem and Rationale

Release 0.13.0 resumes committed state but cannot safely resolve every call interrupted between
external execution and checkpoint commit. The Supervisor also remains fail-fast. Release 0.14.0
adds idempotent external boundaries and bounded failure-aware policy without adding concurrency.

LangGraph's durable-execution guidance requires deterministic workflows and idempotent side
effects; its documentation recommends idempotency keys, upserts, or read-before-write checks when
steps may re-execute. See
[Graph re-execution and idempotency](https://langchain-ai.github.io/langgraph/how-tos/configuration/)
and [Interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts). Its
[fault-tolerance guide](https://docs.langchain.com/oss/python/langgraph/fault-tolerance) separates
typed retry policies from error handlers and preserves failure provenance across resume.

## Primary Mechanism

Every external tool call receives a stable logical execution key and committed execution record.
Infrastructure retries are bounded and classified separately from Agent-level replacement work.
Every terminal Worker result, including failure, enters ResearchState for a structured Supervisor
recovery decision.

## Architectural Decision

```text
logical tool call
    -> lookup execution key
    -> completed: replay committed result
    -> absent: execute with bounded transient retries and commit
    -> ambiguous: reconcile or pause

Worker result, including failure
    -> SupervisorRecoveryDecision
    -> retry | narrow | replace | accept_partial | abandon | finish
```

## User-Visible Behavior

Progress distinguishes logical tool calls, infrastructure attempts, Agent attempts, and replayed
results. Failed Worker summaries remain visible. Recovery decisions state the prior failure,
selected action, remaining global budget, and replacement task when applicable.

## Runtime Flow

1. Derive the execution key from run, Worker, model call, provider call ID, tool name, and
   normalized arguments.
2. Return an existing committed result without another outbound request.
3. Retry only classified transient failures with exponential backoff and bounded jitter.
4. Commit one terminal execution record before exposing success to the model.
5. Finalize every Worker outcome and merge it into ResearchState.
6. Request a strict `SupervisorRecoveryDecision` for recoverable failures.
7. Enforce global budgets and per-task attempt limits before dispatch.
8. Preserve all prior results and decisions through checkpoint resume.

## State Ownership and Budget Contract

Add `ToolExecutionRecord`, `WorkerFailure`, `SupervisorRecoveryDecision`, and `RunBudget`. The run
budget covers total model calls, logical tool calls, source reads, Workers, context summaries,
Agent retries, elapsed time, and optional estimated cost. Resume, retries, replacement Workers,
and context sessions never reset it.

Infrastructure attempts do not consume another logical Agent tool call but do consume elapsed time
and recorded provider cost. Agent-level retry requires a changed task scope or source strategy and
consumes Worker and model budgets.

## Persistence and Artifact Contract

Append logical executions, infrastructure attempts, Worker failures, recovery decisions, and
global-budget snapshots to versioned run artifacts referenced by checkpoints. Records are
immutable; later reconciliation appends a new status transition rather than overwriting prior
failure provenance.

## Retry and Idempotency Contract

Retry connection failures, timeouts, HTTP 408, 429, and 5xx up to three infrastructure attempts.
Do not retry invalid schema, unknown IDs, destination-policy rejection, budget exhaustion,
application invariants, or safety refusals. Use bounded exponential backoff with jitter. A safety
refusal cannot be bypassed by automatic paraphrase.

## Security and Trust Boundary

OWASP identifies excessive agency as a risk when models choose extensions and recommends least
privilege, authorization, and human approval for consequential actions; see
[OWASP LLM06:2025](https://genai.owasp.org/llmrisk/llm062025-excessive-agency/). Current read-only
research tools remain automatic. Any later side-effecting tool must declare a risk level and an
approval requirement before joining this retry framework.

## CLI Contract

Existing modes remain. `--inspect` adds global budgets, logical and infrastructure attempt counts,
pending recovery decision, and next permitted action.

## Observability Contract

Record execution key hash, logical attempt, infrastructure attempt, retry class, backoff, replay,
Worker failure class, Supervisor action, and budget snapshot. Never log credentials or raw private
reasoning.

## Evaluation Contract

Deterministic tests cover each retryable and non-retryable class, duplicate resume, ambiguous
completion, maximum attempts, unchanged-task retry rejection, budget exhaustion, refusal handling,
partial acceptance, and fail-safe behavior. A fake clock replaces real waits in tests.

## Failure and Stopping Behavior

One task receives at most two Agent-level attempts. Exhausted or unsafe work may be abandoned or
accepted only as explicitly labeled partial evidence. Global-budget exhaustion ends research and
allows a report only when at least one validated claim exists; the report must expose material
coverage gaps.

## Implementation Constraints

Keep synchronous execution. Use existing checkpoint artifacts and standard-library retry timing.
Do not add a distributed queue, generic resilience library, provider fallback, or unlimited retry.

## Manual Acceptance Scenario

Inject a transient search timeout followed by success, crash after execution before response
delivery, invalid source ID, repeated 429, and one insufficient-evidence Worker. Confirm one logical
result, bounded attempts, exact budget accounting, replay without duplicate external work, and a
visible Supervisor narrow-or-abandon decision.

## Completion Criteria

All failure matrix, recovery, idempotency, budget, real-provider, and resume tests pass. No
completed logical tool operation is duplicated across retry or resume.

## Out of Scope

Parallel Workers, distributed leases, provider fallback, automatic safety-refusal circumvention,
compensating transactions for write tools, and learned recovery policy.

## Known Limitations and Deferred Decisions

Some third-party read APIs offer no provider idempotency key, so the application can prevent
duplicate persistence but cannot prove the provider did not process an ambiguous request twice.
Parallel cancellation and domain rate limiting are deferred to v0.17.
