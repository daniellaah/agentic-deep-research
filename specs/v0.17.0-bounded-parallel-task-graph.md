# v0.17.0 — Bounded Parallel Task Graph

## Status

Draft

## Learning Question

What becomes faster or more complete when the Supervisor may issue a small dependency-aware task
batch whose ready Workers run concurrently under shared evidence, budget, checkpoint, and
evaluation contracts?

## Problem and Rationale

Release 0.16.0 can measure the sequential baseline, but independent research directions still run
one at a time. Release 0.17.0 introduces only bounded concurrency after persistence, idempotency,
provenance, and evaluation exist.

Anthropic describes its production Research system as an orchestrator-worker architecture in
which a lead agent delegates independent directions to specialized subagents running in parallel.
The same report warns that multi-agent systems consume substantially more tokens and require
careful scaling, prompting, and evaluation. See
[How we built our multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system).
LangGraph recommends per-invocation state for most independent multi-agent subagent calls because
it preserves isolation while supporting durable execution; see
[subgraph persistence](https://docs.langchain.com/oss/python/langgraph/use-subgraphs).

## Primary Mechanism

The Supervisor may return a batch of zero through four `ResearchTaskNode` values with explicit
dependencies. The application schedules only ready nodes, runs at most two by default and four at
the hard limit, and merges immutable results in deterministic graph order rather than completion
order.

## Architectural Decision

```text
Supervisor observes graph and global budget
    -> add bounded task batch
    -> validate acyclic dependencies and non-duplication
    -> dispatch ready nodes within concurrency limit
    -> isolated Workers share only durable evidence services and global budget authority
    -> checkpoint terminal results
    -> deterministic merge
    -> Supervisor observes again or finishes
```

No Worker communicates directly with another Worker or mutates graph state.

## User-Visible Behavior

The CLI prints graph additions, dependency edges, ready/running/completed counts, Worker start and
finish events, cancellation, global budget snapshots, and deterministic merge order. Output may be
interleaved by progress event but final artifacts remain stable.

## Runtime Flow

1. Validate unique task IDs, bounded batch size, dependencies, and acyclicity.
2. Reject tasks substantially duplicating completed or running task objectives.
3. Select ready nodes by dependency depth, priority, creation order, then task ID.
4. Reserve global model, tool, read, time, cost, and domain capacity before dispatch.
5. Run isolated Worker states concurrently.
6. Commit each result and release reservations exactly once.
7. Cancel dependents when a required predecessor is abandoned, unless Supervisor replaces it.
8. Merge completed results in deterministic task order.
9. Evaluate quality, duplication, cost, and latency against the sequential baseline.

## Task Graph and State Contract

`ResearchTaskNode` contains task ID, title, question, evidence targets, dependency IDs, priority,
status, creation index, attempts, and optional replacement-of ID. Status transitions are pending,
ready, running, completed, failed, abandoned, blocked, and cancelled. Graph mutation is
application-owned and append-only except for status transitions.

## Persistence and Artifact Contract

Persist the validated graph, mutation sequence, capacity reservations, dispatch identities,
terminal results, cancellation lineage, and deterministic merge order as versioned run artifacts.
Checkpoint recovery reconstructs scheduler state from these committed records without inferring it
from interleaved terminal output.

## Global Budget and Rate-Limit Contract

All Workers share `RunBudget`. Default concurrency is two; hard maximum is four. Reserve capacity
before dispatch and reconcile actual use afterward. Apply global Tavily concurrency and per-domain
selected-source read limits. Waiting for capacity consumes elapsed-time budget but not logical tool
budget. Simple tasks remain one Worker when another independent direction is not justified.

## Persistence and Idempotency Contract

Graph mutations, reservations, dispatches, and terminal results are checkpointed. Stable task and
execution IDs prevent duplicate dispatch on resume. Only one scheduler instance may own a run;
multi-host distributed leases remain out of scope.

## Security and Trust Boundary

Workers have per-invocation contexts and cannot read another Worker's transient history. Shared
evidence remains immutable and run-scoped. Prompt injection in one source cannot grant permissions
or send instructions to peer Workers.

## CLI Contract

Existing invocation remains. Environment configuration may reduce concurrency to one for a
sequential comparison but cannot exceed the hard limit.

## Observability Contract

Trace graph decisions, reservations, queue delay, execution overlap, domain throttling,
cancellation, merge order, duplicate-task rejection, and per-Worker/global cost.

## Evaluation Contract

Compare sequential and parallel configurations on the same suite. Required metrics include
completion quality, evidence-target coverage, citation accuracy, duplicated queries and sources,
model/tool calls, total tokens, estimated cost, wall-clock latency, recovery, and determinism.
Parallel mode is accepted only if it improves a declared quality or latency objective without
regressing deterministic provenance and recovery gates.

## Failure and Stopping Behavior

One Worker failure follows v0.14 recovery policy while unrelated Workers may finish. Fatal run
invariants cancel all active tasks and checkpoint cancellation. User cancellation propagates to
active Workers and prevents new dispatch. Global budget exhaustion prevents new work and produces
an explicitly partial report only when validated claims exist.

## Implementation Constraints

Introduce only the minimum asynchronous or thread-based execution required by measured tools and
SDK behavior. Do not add a distributed queue, actor framework, generic DAG engine, worker-to-worker
chat, or unbounded recursive delegation.

## Manual Acceptance Scenario

Use a brief with two independent topics and one comparison dependent on both. Confirm the first two
Workers overlap, the comparison waits, one injected failure does not duplicate unrelated work,
resume does not redispatch completed tasks, domain limits hold, and final claims merge in stable
graph order. Compare against concurrency one.

## Completion Criteria

Graph validation, isolation, reservation, cancellation, recovery, stable merge, rate limiting,
real-provider concurrency, and sequential comparison pass. Evaluation justifies the configured
default concurrency.

## Out of Scope

Distributed scheduling, dynamic recursive delegation, peer messaging, more than four concurrent
Workers, speculative execution, cross-run evidence sharing, and batch rollout orchestration.

## Known Limitations and Deferred Decisions

Single-process concurrency does not provide horizontal scale. Provider and source rate limits can
remove latency gains. v0.18 scales independent complete runs rather than increasing per-run Agent
complexity.
