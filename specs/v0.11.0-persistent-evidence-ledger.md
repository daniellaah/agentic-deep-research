# v0.11.0 — Persistent Evidence Ledger

## Status

Draft

## Learning Question

What becomes recoverable and verifiable when every successful search result and selected-source
read is normalized into an application-owned evidence record before bounded content enters a
Worker's model history?

## Problem and Rationale

Release 0.10.0 preserves source identity across context sessions but discards raw search and read
content when it replaces the active history. A summary omission therefore makes evidence
unrecoverable even though the run still remembers the source URL. Release 0.11.0 separates durable
evidence from transient model context: model history becomes a bounded view over an application-
owned ledger rather than the only copy of retrieved material.

The W3C PROV family defines provenance as information about entities, activities, and agents used
to assess quality, reliability, and trustworthiness. Its model includes derivation, attribution,
primary-source, and quotation relationships. This release adopts only the smaller identity and
derivation boundary needed by the Worker; it does not implement RDF or PROV-O. See the W3C
[PROV overview](https://www.w3.org/TR/prov-overview/) and
[PROV-O Recommendation](https://www.w3.org/TR/prov-o/). Anthropic's
[context-engineering guidance](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
also describes storing information outside the context window and retrieving it when needed.

## Primary Mechanism

Every successful discovery or read creates one immutable `EvidenceRecord` with a stable run-scoped
`E<number>` identifier, retrieval provenance, bounded content, and content hash. Tool output sent
to the Worker references that record. The active context may omit content, but the ledger does not.

## Architectural Decision

```text
search or selected-source read
    -> validate and normalize provider result
    -> append immutable EvidenceRecord
    -> return bounded observation with evidence_id
    -> context replacement may discard observation
    -> later evidence lookup resolves evidence_id from ledger
```

The application owns evidence identity, source identity, hashing, persistence, and lookup. The
model may select known IDs but cannot construct, overwrite, or delete records.

## User-Visible Behavior

The CLI creates one visible run ID after brief approval. Search and read progress reports the
created or reused evidence IDs. A completed run prints the evidence-record count and ledger path.
The final report remains Markdown and does not expose internal IDs unless diagnostic output is
requested.

## Runtime Flow

1. Create the run artifact directory after brief approval.
2. For every valid search item, canonicalize its primary URL and normalized bounded content.
3. For every valid read, retain the application-resolved source URL and bounded extracted content.
4. Compute a SHA-256 content hash from the exact persisted UTF-8 content.
5. Reuse an existing record only when retrieval type, canonical destination, normalized query, and
   content hash match; otherwise append a new record.
6. Persist the record atomically before returning a successful linked tool output.
7. Allow the Worker to retrieve bounded records issued in its active run.
8. Preserve the ledger across context replacement and successful or failed run completion.

## State Ownership and Data Contract

`EvidenceRecord` contains: evidence ID, run ID, Worker number, source ID, canonical and original
URL, optional title, retrieval type (`web_snippet`, `arxiv_abstract`, or `selected_source`), query,
bounded content, content hash, retrieval timestamp, truncation flag, and originating tool call ID.
Credentials, provider response objects, cookies, headers, private reasoning, and unbounded content
are forbidden.

Evidence IDs are contiguous within a run and never reused for different content. Source IDs remain
Worker-scoped controls; evidence IDs are run-scoped immutable artifact references.

## Persistence and Artifact Contract

```text
runs/<run-id>/
|- run.json
`- evidence.jsonl
```

Append records through a temporary file plus atomic replacement, or an equivalently crash-safe
standard-library mechanism. `run.json` records schema version, application version, provider,
exact model name, creation time, and evidence count, but never credentials. Full workflow resume
is deferred to v0.13.

## Idempotency and Replay Contract

The originating tool call ID plus normalized arguments forms the logical execution identity. A
replayed completed call returns its existing records and must not append duplicates. Conflicting
content for an already completed logical call is an invariant failure rather than an overwrite.

## Security and Trust Boundary

Persisted web content remains untrusted data. Lookup returns content inside an explicit untrusted-
evidence envelope, never as instructions. Existing destination validation remains mandatory.
OWASP identifies indirect prompt injection through websites and recommends least privilege and
separating untrusted external content from trusted prompts; see
[OWASP LLM01:2025](https://genai.owasp.org/llmrisk/llm01-prompt-injection/).

## CLI Contract

The existing invocation remains unchanged. No arbitrary evidence-path argument or cross-run lookup
is added.

## Observability Contract

Progress exposes evidence ID, retrieval type, source ID, safe hostname, bounded character count,
reuse versus creation, and final record count. It never prints full persisted content by default.

## Evaluation Contract

Deterministic tests cover stable IDs, hash calculation, duplicate replay, conflicting replay,
atomic write failure, context replacement survival, unknown ID rejection, Worker isolation, and
absence of credentials. No model grader is needed for these application-owned invariants.

## Failure and Stopping Behavior

A persistence failure converts the current tool boundary to `tool_error`; the model must not see a
success whose evidence was not committed. A malformed ledger or hash mismatch fails inspection and
lookup explicitly. Earlier valid records remain available after later failure.

## Implementation Constraints

Use standard-library JSONL, hashing, and atomic filesystem operations. Do not add a database,
embedding model, vector store, generic repository, or workflow framework.

## Manual Acceptance Scenario

Run a question that produces web search, arXiv search, and one selected-source read. Confirm stable
evidence IDs, exact hashes, ledger survival after a context boundary, successful bounded lookup,
duplicate-call reuse, and explicit rejection of an unknown ID. Interrupt one ledger write and
confirm no successful tool output references an uncommitted record.

## Completion Criteria

The runtime, deterministic tests, real-provider scenario, README, changelog, tech stack, and
artifact documentation agree with this contract. Every persisted record is attributable to one
run, Worker, source, and tool call.

## Out of Scope

Claim schemas, citation placement, semantic entailment, embeddings, cross-run memory, full resume,
parallel Workers, trace events, retention-policy UI, cloud storage, and batch rollout generation.

## Known Limitations and Deferred Decisions

Content hashing proves artifact integrity, not truth. Search snippets remain weaker evidence than
selected-source reads. Claim-level support and citation verification are deferred to v0.12;
durable workflow recovery is deferred to v0.13.
