# v0.5.0 — Scoping and ResearchBrief

## Status

Verified

## Learning Question

What becomes easier to align, inspect, and control when an ambiguous research request is
clarified once and converted into a user-approved `ResearchBrief` before planning begins?

## Problem and Rationale

Release 0.4.0 passes the user's initial question directly into a one-shot planner. That is
adequate when the question already specifies its purpose and boundaries, but an underspecified
request can produce a valid plan for the wrong audience, time horizon, evidence preference, or
deliverable. Because the plan starts immediately, the user cannot inspect or correct those
interpretations before model calls and research tools begin consuming the run budget.

Release 0.5.0 adds a bounded Scope stage before the existing static Plan stage. One structured
assessment identifies only ambiguities whose answers would materially change the research.
When clarification is needed, the CLI presents at most three questions together and collects
one answer to each without generating follow-up questions. A second structured call converts
the original question and any clarification answers into a validated `ResearchBrief`.

The application prints the complete brief and requires an explicit user decision. The user may
approve it, cancel the run, or request one revision. A revision produces one new validated
brief and requires a final approve-or-cancel decision. Planning cannot begin until a brief has
been explicitly approved. The approved brief then replaces the original question as the sole
research contract passed into Plan, Research, Write, Critic, and Revise.

This release deliberately keeps both model behavior and user interaction bounded. It does not
add an open-ended intake chat, repeated clarification, plan approval, replanning, or adaptive
research. The resulting contract provides a stable input for the existing immutable planner
and for the adaptive supervisor planned for a later release.

The structured boundaries follow the
[OpenAI Structured Outputs guide](https://developers.openai.com/api/docs/guides/structured-outputs),
which documents Pydantic schemas with `client.responses.parse`, `text_format`, and
`response.output_parsed`, as well as programmatically detectable refusals. All model calls
continue to use the
[Responses API](https://developers.openai.com/api/reference/cli/resources/responses/methods/create)
with application-owned state and `store=False`.

## User-Visible Behavior

The CLI still accepts one positional research question, then runs six top-level stages:

1. **Scope** assesses ambiguity, optionally asks one round of clarification questions,
   creates a validated `ResearchBrief`, and obtains explicit approval.
2. **Plan** creates, validates, and prints one immutable research plan from only the approved
   brief.
3. **Research** executes every plan task in order with the existing tool-using Agent.
4. **Write** drafts a report against the approved brief and combined research notes.
5. **Critic** reviews the draft against those same inputs.
6. **Revise** produces the final Markdown report.

Scope always performs one clarification assessment. When its validated question list is empty,
the CLI states that clarification is not required and proceeds directly to brief creation. When
the list contains questions, the CLI prints all questions before reading the first answer, then
prompts for one non-empty answer per question. The model cannot ask a follow-up question or add a
second clarification round.

The initial brief is printed in a labeled `RESEARCH BRIEF | PENDING APPROVAL` block. The CLI then
accepts exactly one of the case-insensitive control words `approve`, `revise`, or `cancel`:

- `approve` marks that exact validated brief as approved and starts Plan;
- `cancel` stops the run before Plan; and
- `revise` prompts for one non-empty revision request, makes exactly one brief-revision call,
  prints the revised brief, and allows only `approve` or `cancel` as the final decision.

The revised brief is never auto-approved. A second revision request is not available. Invalid,
empty, or overlong local input prints a concise validation message and repeats only the current
local prompt. It does not create another model request, clarification round, or revision
opportunity. End-of-file while the CLI is waiting for input is treated as cancellation.

After approval, the existing Plan, Research, Write, Critic, and Revise behavior remains visible.
The final report must satisfy the approved brief's objective, scope, output requirements, and
success criteria to the extent supported by returned evidence. It must respect exclusions and
time horizon, cite useful returned URLs, distinguish evidence from inference, and state important
limitations.

## Runtime Flow

```text
question
→ load and validate configuration
→ Scope assessment call(question, ClarificationAssessment schema)
→ require one parsed and validated ClarificationAssessment
→ if questions are present
    → print all questions together
    → collect one non-empty answer per question
  else
    → print that clarification is not required
→ Brief call(question + optional clarification Q&A, ResearchBrief schema)
→ require one parsed and validated ResearchBrief
→ print the brief as pending approval
→ read approve, revise, or cancel
→ if cancel
    → stop before Plan
→ if revise
    → collect one non-empty revision request
    → Brief revision call(question + optional Q&A + current brief + revision request,
      ResearchBrief schema)
    → require one parsed and validated revised ResearchBrief
    → print the revised brief as pending final approval
    → read approve or cancel
    → if cancel, stop before Plan
→ mark the selected brief approved and immutable for the remainder of the run
→ Plan call(approved brief, ResearchPlan schema)
→ require and print one validated immutable ResearchPlan
→ for each ResearchTask in list order
    → build a task input from the approved brief and current task
    → start a fresh ordered Responses API history for that task
    → run the existing bounded research Agent loop
    → associate and print the returned notes with the current task
→ combine and print task note text in plan order
→ Write(approved brief + combined research notes)
→ print the draft
→ Critic(approved brief + combined research notes + draft)
→ print the critique
→ Revise(approved brief + combined research notes + draft + critique)
→ print the final Markdown report
```

Scope contains two required structured model calls and at most one optional structured revision
call. It is a bounded application-owned intake workflow, not an Agent loop. Clarification answers
and approval commands are read by the local CLI; they are not tool calls and do not create a
provider-managed conversation.

## Clarification Contract

The first Scope call returns exactly this Pydantic model shape:

```text
ClarificationAssessment
└── questions: list[string]
```

The application enforces these invariants:

- the `questions` field is required and extra fields are forbidden;
- surrounding whitespace is stripped from every question;
- the list contains zero through three questions; and
- each question contains 1 through 300 characters after stripping.

An empty list means the initial question is sufficiently specified for this release. A non-empty
list is the complete clarification round. List order is presentation order; the application
numbers questions from one and associates each answer by list position. The model does not
generate question IDs.

A clarification question is permitted only when different plausible answers would materially
change at least one of these parts of the eventual contract:

- objective or intended decision;
- audience or required level of explanation;
- included or excluded subject matter;
- time horizon;
- source preference; or
- output requirements or success criteria.

The assessment must not ask for information already present in the initial question, ask a
generic preference question merely because a field could be more detailed, answer the research
question, conduct research, propose a plan, or expose private reasoning. It should prefer a
reasonable explicit default in the later brief when an omission would not materially change the
work.

The CLI collects one answer for every printed question in order. Each answer must contain 1
through 2,000 characters after stripping. An answer such as `no preference` is valid; an empty or
overlong answer repeats the same numbered answer prompt until valid input or end-of-file. All
questions are known before any answer is collected, and answers cannot trigger new
model-generated questions.

## ResearchBrief Contract

Both initial brief creation and optional brief revision return exactly this Pydantic model shape:

```text
ResearchBrief
├── objective: string
├── audience: string
├── scope: list[string]
├── exclusions: list[string]
├── time_horizon: string
├── source_preferences: list[string]
├── output_requirements: list[string]
└── success_criteria: list[string]
```

The application enforces these invariants:

- every field is required and extra fields are forbidden;
- surrounding whitespace is stripped from every string;
- `objective` contains 1 through 800 characters;
- `audience` and `time_horizon` each contain 1 through 300 characters;
- `scope` contains 1 through 6 items;
- `exclusions` contains zero through 6 items;
- `source_preferences`, `output_requirements`, and `success_criteria` each contain 1 through 6
  items; and
- every list item contains 1 through 300 characters after stripping.

Each field has one responsibility:

- **objective** states the research goal or decision the report must support;
- **audience** identifies the intended reader and appropriate level of explanation;
- **scope** lists the subjects, comparisons, entities, or questions that must be covered;
- **exclusions** lists adjacent subjects or interpretations that must not be researched;
- **time horizon** states the relevant date range, recency requirement, or explicit absence of a
  time restriction;
- **source preferences** states required or preferred evidence types within the available Tavily
  web and arXiv search capabilities, including any important evidence limitations;
- **output requirements** states the expected report structure, length, citation behavior, or
  presentation constraints; and
- **success criteria** lists observable conditions by which the final report can be judged
  complete.

When the user has no exclusion or special source preference, the brief must express that state
unambiguously: `exclusions` may be empty, while `source_preferences` must contain an explicit
default. The brief must not claim that the runtime can inspect arbitrary URLs, read selected pages
or full papers, use a source type unavailable through the current custom tools, or guarantee that
a source will be found. Requested evidence that exceeds current tool behavior must be represented
as a preference or limitation rather than a false capability claim.

The brief records the resolved contract rather than a transcript. It must not include the
clarification questions, conversational wording, approval commands, hidden reasoning, a research
plan, search queries, findings, citations, or claims that research has already occurred.

The application renders every validated brief into one deterministic Markdown representation in
the field order shown above. The same renderer is used for terminal display and for downstream
model input. An empty `exclusions` list is rendered as an explicit `None specified.` item; the
Pydantic value itself remains an empty list.

Once approved, the selected `ResearchBrief` is immutable for the remainder of the run. The
application must not add, remove, infer, reorder, or rewrite brief content after approval.

## Approval and Revision Contract

The first approval prompt occurs only after the complete validated initial brief has been printed.
The accepted commands are exactly `approve`, `revise`, and `cancel`, compared after trimming
surrounding whitespace and normalizing case. Empty or unknown commands print the accepted choices
and repeat the same approval prompt without a model request.

If the user requests revision, the CLI reads one free-text revision request containing 1 through
2,000 characters after stripping. Empty or overlong revision text repeats that local prompt
without consuming the one revision model call. The revision call receives the original question,
any complete clarification Q&A, the complete current brief, and the revision request as explicitly
labeled input. It returns a complete replacement `ResearchBrief`, not a patch. The model must
apply the requested change, preserve unrelated contract details, resolve any direct conflict in
favor of the latest revision request, and stay within the current runtime's research capabilities.

The application prints the complete revised brief before reading the final decision. That prompt
accepts exactly `approve` or `cancel`; invalid local input repeats only that prompt and cannot
request another model call. Only the exact brief selected by an `approve` command may enter Plan.

The original question, clarification assessment, clarification Q&A, superseded brief, user
revision request, and approval commands remain Scope inputs. After approval, none of them is sent
to Plan, Research, Write, Critic, or Revise independently of the approved brief.

## Research Plan Contract

The release 0.4.0 `ResearchPlan` and `ResearchTask` shapes and validation invariants remain
unchanged:

```text
ResearchPlan
└── tasks: list[ResearchTask]
    ├── title: string
    ├── research_question: string
    └── completion_criteria: list[string]
```

The plan still contains 1 through 4 ordered tasks; each task still contains a 1-through-100
character title, a 1-through-600 character research question, and 1 through 3 completion criteria
of 1 through 240 characters each. Every field remains required, extra fields are forbidden, and
surrounding whitespace is stripped.

The planner now derives focused, non-duplicative, independently researchable, and jointly
sufficient tasks from only the approved brief. Plan completion criteria must reflect the brief's
scope, exclusions, time horizon, source preferences, output requirements, and success criteria
where they affect evidence collection. The plan remains immutable after validation and is still
executed once in list order without approval, editing, regeneration, or replanning.

## Responses API Contract

Scope uses the configured model in separate synchronous `client.responses.parse` requests:

1. **Clarification assessment** receives the original question as explicit input and uses
   `text_format=ClarificationAssessment`.
2. **Initial brief creation** receives the original question plus any numbered clarification Q&A
   as explicit input and uses `text_format=ResearchBrief`.
3. **Optional brief revision** receives the original question, any numbered clarification Q&A,
   the current rendered brief, and the user's revision request as explicit input and uses
   `text_format=ResearchBrief`.

Every call has stage-specific instructions, `store=False`, and no tools,
`previous_response_id`, or Conversation. Scope does not replay response output items between
calls; the application passes only the explicit artifacts named above. No Scope request contains
approval control words entered for application flow.

Each structured request must produce a non-refusal, complete response whose `output_parsed` is an
instance of the requested Pydantic model. The runtime does not fall back to JSON mode, unvalidated
text, default questions, an inferred brief, or a superseded brief when a response is incompatible,
refused, incomplete, missing, or invalid.

`llm_call` remains the thin provider boundary introduced in earlier releases. Structured output
remains mutually exclusive with tools and tool choice, and all paths return the official SDK
`Response` without wrapping it. The application may generalize the existing structured-response
validation helper so Scope and Plan share status, refusal, parsed-type, and error behavior; it must
not add a schema-repair model call or provider abstraction.

The Plan request remains one `client.responses.parse` call, but its explicit input is now only the
deterministically rendered approved brief. It does not receive the original question,
clarification artifacts, or approval history.

For each plan task, the existing research Agent receives one user input containing only:

- the complete rendered approved brief;
- the current task number and title;
- the task's research question; and
- the task's completion criteria.

The release 0.4.0 task-history contract remains unchanged. Each task begins with fresh history;
every response output item is appended in order; custom function calls execute synchronously in
response order; linked `function_call_output` items are appended; and complete task history is
replayed with `store=False`. Research uses the existing tools with `tool_choice="auto"` while
budget remains and `tool_choice="none"` for the final-notes request after budget exhaustion.

Write receives only the rendered approved brief and combined research note text. Critic adds the
draft to that same context, and Revise adds the critique. Those stages do not receive the original
question, clarification artifacts, approval history, plan, task metadata, raw Responses, or
research transcripts.

## Instruction Contract

All model instruction and application-owned model-input constants remain plain strings in the
repository-root `agent_instructions.py`. Release 0.5.0 adds stage-specific Scope instructions and
updates downstream instructions to use the approved brief as their contract:

- **Clarification assessment:** return only one `ClarificationAssessment`. Ask zero through three
  concise, non-overlapping questions only for ambiguities that would materially change the brief.
  Ask the complete round at once. Do not answer the request, research, propose a plan, ask for
  confirmation, or expose private reasoning.
- **Brief creation:** return only one complete `ResearchBrief` derived from the original question
  and any clarification answers. Resolve answered ambiguities, make reasonable non-material
  defaults explicit in the appropriate fields, respect current tool boundaries, and do not add
  findings, a plan, or process narration.
- **Brief revision:** return only one complete replacement `ResearchBrief`. Apply the user's one
  revision request, preserve unrelated contract details, prefer the latest request when it
  conflicts with the current brief, and do not answer the research question or claim approval.
- **Plan:** create one static `ResearchPlan` from only the approved brief. Tasks remain focused,
  non-duplicative, self-contained, independently researchable, and jointly sufficient. Planning
  must respect exclusions and evidence preferences and must not answer the objective, claim
  research occurred, request tools, or produce a report outline.
- **Research:** investigate only the current task under the approved brief. Use its objective for
  relevance, respect scope, exclusions, time horizon, and source preferences, retain useful URLs,
  identify evidence limitations, and return task-scoped Markdown notes only. Existing tool-use
  and budget-exhausted instructions otherwise remain unchanged.
- **Write:** satisfy the approved brief using only combined research notes. Respect its audience,
  exclusions, time horizon, and output requirements; address success criteria that the notes can
  support; and state unsupported criteria as limitations rather than invent evidence.
- **Critic:** evaluate the draft against the approved brief and research notes, including every
  brief field relevant to report completeness and instruction following. It does not independently
  verify sources or introduce new research.
- **Revise:** produce the final Markdown report against the approved brief, research notes, draft,
  and useful critique. It must not mention the brief or other workflow artifacts and must retain
  the existing evidence, citation, limitation, and output boundaries.

No instruction may request or claim to expose private chain-of-thought. Structured models contain
application-facing decisions and contract fields only.

## CLI Contract

The invocation shape remains:

```text
uv run deep_research.py "Research the impact of AI coding agents."
```

The positional question and these environment variables remain required:

- `OPENAI_API_KEY`;
- `MODEL_NAME`; and
- `TAVILY_API_KEY`.

`MODEL_NAME` must support the required Structured Outputs schemas and existing custom function
tools. `python-dotenv` still loads the repository-root `.env`. Missing input or configuration
makes no external request and does not prompt for Scope input.

Standard output carries progress, formatted model results, clarification questions, and input
prompts. Fatal errors go to standard error. The standard-library input mechanism reads
clarification answers, revision text, and approval commands from standard input, so an interactive
terminal and intentionally piped input are both supported. This release adds no prompt-toolkit,
terminal UI dependency, timeout, default approval, or non-interactive bypass flag. Local input
validation uses a small standard-library loop that repeats the current prompt until the value is
valid or standard input reaches end-of-file.

Progress uses the fixed top-level stage labels `Scope`, `Plan`, `Research`, `Write`, `Critic`, and
`Revise`, including their one-based position out of six. Successful output makes visible:

- when each Scope model boundary starts and completes;
- whether clarification is required and how many questions were returned;
- all clarification questions before the first answer prompt;
- the complete initial and, when requested, revised brief;
- when a brief becomes approved;
- the complete validated plan and every existing research/report boundary; and
- the final Markdown report.

The CLI never asks the user to approve or edit the static plan.

## Limits and Stopping Contract

Scope has these hard interaction limits:

- exactly one clarification-assessment request;
- zero or one clarification round containing at most three questions;
- exactly one initial-brief request after clarification answers, if any, are collected;
- at most one user revision request;
- at most one brief-revision model request;
- one initial approval decision and, only after revision, one final approval decision; and
- no model-generated follow-up clarification, second revision, or automatic approval.

Scope completes only after an explicit `approve`. Invalid, empty, or overlong local input repeats
only the current prompt and may do so until the user provides a valid value. These local retries
do not alter the hard model-interaction limits or consume model or tool budget. Cancellation,
end-of-file, structured-output failure, or API failure stops the run before Plan. Waiting for
local user input has no application timeout.

The plan still contains at most 4 tasks. Every task independently retains at most 10 Research
model turns, 8 tool execution attempts, and 5 results per tool call. Malformed, unknown, failed,
and budget-exceeding tool calls preserve their release 0.4.0 behavior and count against the
current task's tool budget.

With `N` validated tasks and `R` brief revisions, where `1 <= N <= 4` and `R` is zero or one, a
successful run makes exactly `3 + R` structured requests before Research: two Scope requests,
the optional revision request, and one Plan request. It then makes at least `N` and at most `9N`
Research requests, followed by exactly three report-stage requests. The total is therefore at
least `6 + R + N` and at most `6 + R + 9N` model requests. The absolute hard maximum remains 32
tool attempts and becomes 43 model requests.

After approval, Plan and downstream stopping behavior remains unchanged. Tasks run sequentially;
a fatal task failure prevents later tasks and report stages; and unmet completion or success
criteria do not modify the brief, plan, or budgets.

## Observability Contract

Live terminal output remains the complete observability mechanism. Scope adds visible ambiguity
assessment, clarification questions, the research contract, and the human decision boundary
before the existing visible plan and execution boundaries.

The application prints every model-generated question and every field of each pending brief.
It prints approval, revision, cancellation, and stage status, but does not separately reprint user
answers, revision text, or control commands. Ordinary terminal input echo is not application-owned
output. The terminal also does not print raw structured-output JSON, Pydantic representations,
prompts, complete Responses API histories, tool payloads, secrets, or model reasoning items.

`ClarificationAssessment`, `ResearchBrief`, and `ResearchPlan` are application-facing structured
values. They expose questions, an explicit contract, tasks, and completion criteria; they do not
request, store, reconstruct, or claim to expose private chain-of-thought. This release adds no
structured trace.

## Artifact Contract

Release 0.5.0 creates no run directory and writes no application output files. Clarification data,
pending and approved briefs, the plan, task-scoped notes, combined notes, draft, critique, and
final report remain in memory. Model-generated boundary values and report artifacts required by
the observability contract are printed in full.

## Failure Behavior

Missing input or configuration, any Scope or Plan API error, an unsupported Structured Outputs
schema, a refusal, an incomplete structured response, a missing or invalid parsed value, user
cancellation or end-of-file, any fatal research-task error, an empty required report-stage output,
or a later API error prints a concise message and exits nonzero.

Clarification-assessment failure stops before questions or a brief are printed. Initial-brief
failure stops before the approval prompt. Revision failure stops without falling back to the
superseded brief. Cancellation or final-approval failure stops before Plan. Plan failure stops
before research tools can run. Research and report-stage failures retain their release 0.4.0
stopping behavior.

There are no API retries, schema-repair calls, fallback questions, inferred or auto-approved
briefs, fallback plans, skipped tasks, partial reports, or output artifacts. Local prompt retries
validate only user input and never repeat or repair a model boundary. Ordinary research-tool
errors remain linked function outputs for the active Agent and do not by themselves stop the run.

## Implementation Constraints

- Keep clarification assessment, brief creation, brief approval and revision, the planner,
  Pydantic boundary models, sequential task execution, Agent loop, report workflow, CLI input,
  and terminal output in `deep_research.py`.
- Keep all model instruction and application-owned model-input constants in
  `agent_instructions.py` as plain strings without model calls, tools, state, validation, user
  input, or output post-processing.
- Keep custom tool definitions and implementations in `agent_tools.py`; update only project
  version metadata such as the arXiv `User-Agent` when implementing the release.
- Reuse Pydantic 2 for `ClarificationAssessment` and `ResearchBrief`; add no dependency for
  scoping or terminal input.
- Keep Responses API histories and task-result collections as plain lists and dictionaries.
- Use the synchronous OpenAI Responses API directly, keep `llm_call` thin, preserve
  `store=False`, and do not use `previous_response_id` or the Conversations API.
- Implement Scope as one explicit synchronous application function that owns the bounded model
  calls and local input sequence and returns only the explicitly approved `ResearchBrief`.
- Use one small local-input helper to trim text, enforce allowed values or length bounds, report
  invalid input, and repeat only the same prompt. It must not call a model or mutate Scope state.
- Render a validated brief through one deterministic formatter used for both display and model
  input. Do not pass `model_dump_json()` or a Pydantic representation to the user or downstream
  stages.
- Make exactly one clarification-assessment call and one initial-brief call. Make a brief-revision
  call only after the `revise` command, and never more than once.
- Do not call Plan until approval. After approval, pass only the rendered approved brief into
  Plan and downstream stage inputs; do not preserve the original question as a hidden parallel
  contract.
- Make exactly one planning request and preserve the existing immutable plan schema and
  sequential execution.
- Keep `agent_loop` task-agnostic and preserve its fresh per-task history, current model-turn and
  tool-call budgets, tool ordering, and budget-exhausted behavior.
- Keep report-stage calls explicit in `research_workflow`; do not introduce a workflow engine,
  intake framework, chat session, base Agent class, repository layer, or provider abstraction.
- Do not add file output, structured tracing, retries, caching, streaming, asynchronous code,
  concurrency, hosted tools, MCP, automated tests, Ruff, or mypy.

## Manual Acceptance Scenario

With valid configuration and a Structured Outputs-compatible model, run:

```text
uv run deep_research.py "Research the impact of AI coding agents."
```

Across the clarification answers, establish a software-engineering audience, a recent time
horizon, and interest in measured productivity benefits, one failure mode, and one limitation. At
the first approval prompt enter `revise`, then provide this revision:

```text
Require at least one recent arXiv paper and one current web source, compare their evidence, and
cite the returned URLs in a concise Markdown report.
```

At the final prompt enter `approve`. Confirm that:

1. Scope, Plan, Research, Write, Critic, and Revise complete once in that order;
2. Scope makes exactly one clarification-assessment request, returns one through three questions
   for this deliberately ambiguous input, and prints every question before collecting the first
   answer;
3. no follow-up clarification call or second clarification round occurs;
4. exactly one initial brief is created and printed with every required field;
5. `revise` causes exactly one replacement brief call, the revised brief preserves unrelated
   fields and applies the request, and the CLI requires final approval;
6. Plan makes no request and no research tool runs before final `approve`;
7. the approved revised brief, rather than the original question, clarification artifacts,
   superseded brief, or revision request, is the sole contract passed to Plan and downstream
   stages;
8. exactly one valid plan containing 1 through 4 tasks is printed and executed in order;
9. Tavily and arXiv are both used somewhere in Research without printing their payloads;
10. every task's notes, combined notes, draft, critique, and final report are printed in labeled
    sections;
11. the final report is non-empty Markdown and the visible output contains at least one returned
    arXiv URL and one returned web URL; this release does not manually score factual quality,
    evidence strength, or semantic adherence to every brief field;
12. the program creates no run directory or application output files; and
13. the process exits successfully.

Then run a sufficiently explicit question and confirm the assessment may return zero questions,
the CLI visibly states that clarification is not required, and brief creation and explicit
approval still occur.

Run the ambiguous scenario again and enter `cancel` at the first approval prompt. Confirm that the
process exits nonzero without a Plan request or tool call. In another run request one revision and
then enter `cancel` at final approval; confirm the superseded and revised briefs are not used for
planning. Confirm that an invalid approval command, an empty required clarification answer, an
overlong answer, and an empty revision request each print a concise validation message and repeat
only the current local prompt without another model call. Then provide valid input and confirm the
bounded workflow continues. Confirm separately that end-of-file stops without a downstream model
call.

In isolated structured-boundary checks, provide refused, incomplete, missing, wrong-type, or
schema-invalid results for clarification assessment, initial brief, revised brief, and Plan.
Confirm that each fails at its own boundary without a repair request, fallback value, or later
stage. Preserve the release 0.4.0 task-failure and tool-budget checks.

## Completion Criteria

The specification may become `Verified` after these checks pass:

```text
uv run python -m py_compile deep_research.py agent_instructions.py agent_tools.py
uv run deep_research.py --help
```

The success, no-clarification, one-revision, first-approval cancellation, final-approval
cancellation, local-input retry, end-of-file, structured-boundary failure, configuration failure,
task-stopping, and tool-budget scenarios must also pass. Inspect stage order, question count and
presentation order, Q&A association, both brief renderings, approval boundaries, downstream input
isolation, plan ordering, task-note association, combined notes, draft, critique, final report,
and absence of application output files.

Acceptance for this learning release is mechanism-focused. Manual verification confirms that the
CLI, workflow boundaries, structured model calls, custom Agent loop, tool dispatch, budgets,
stopping behavior, and visible artifacts operate as specified with real services. It does not
grade the research conclusions, independently verify citations, score evidence quality, or judge
whether the model output perfectly satisfies every semantic requirement. Structured tracing and
repeatable output evaluation remain deferred until a later release explicitly introduces them.

Confirm that project documentation, direct dependencies, lock file, tool `User-Agent`, and project
version match the implementation. Automated tests, Ruff, and mypy are not required.

concurrency, retries, checkpoints, file artifacts, structured traces, selected-page reading,
arbitrary URL fetching, full-paper retrieval, deterministic citation validation, source-quality
