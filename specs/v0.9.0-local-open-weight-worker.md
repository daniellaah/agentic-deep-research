# v0.9.0 — Local Open-Weight Worker

## Status

Released

## Learning Question

What becomes observable when the same application-owned Research Worker harness can run either
an OpenAI-hosted research policy or a local open-weight policy through a vLLM
Responses-compatible endpoint, while the rest of the workflow remains hosted and unchanged?

## Problem and Rationale

Release 0.8.0 gives every Research Worker a bounded request, private mutable run state, immutable
result, explicit Responses item replay, three custom tools, and selected-source reading. The
Research policy nevertheless remains inseparable from the one OpenAI client and model used by
Scope, Supervisor, Write, Critic, and Revise. This prevents direct observation of which behavior
belongs to the application harness and which behavior belongs to the hosted Worker model.

Release 0.9.0 separates only the Worker inference selection:

```text
hosted Scope and Supervisor
    -> AgentRunRequest
    -> the existing Worker harness
       -> OpenAI-hosted model
          or
       -> local open-weight model through vLLM /v1/responses
    -> AgentRunResult
    -> hosted Write, Critic, and Revise
```

The application still uses the official OpenAI Python SDK on both paths. The local path changes
the SDK client's `base_url`, API key, and model name; it does not add a provider interface,
request translator, alternate response model, or second Agent loop. A run selects exactly one
Worker backend before Scope starts and never routes or falls back between backends.

This release targets vLLM 0.20.2 as the portable compatibility reference. Its official
server documentation lists the Responses API at `/v1/responses`, and its official Responses
tool example uses the OpenAI SDK, strict function schemas, a model-produced `function_call`, an
application-produced linked `function_call_output`, and a second request containing that manual
history. See the [vLLM OpenAI-compatible server documentation](https://docs.vllm.ai/en/v0.20.2/serving/openai_compatible_server/),
[tool-calling documentation](https://docs.vllm.ai/en/v0.20.2/features/tool_calling/), and
[Responses tool example](https://docs.vllm.ai/en/v0.20.2/examples/online_serving/openai_responses_client_with_tools/).

The acceptance reference model is `Qwen/Qwen3-1.7B`, started with the reasoning parser,
structured-output backend, automatic tool selection, and Hermes tool parser shown by that vLLM
example. This small model is an interoperability reference, not a quality recommendation or a
hard-coded application default.

Current protocol differences remain explicit:

- OpenAI's current model guidance requires manually managed stateless history to preserve prior
  user inputs and every response output item, including encrypted reasoning when returned. The
  hosted path retains that exact behavior. See the
  [official OpenAI model guidance](https://developers.openai.com/api/docs/guides/latest-model#update-api-and-model-parameters).
- vLLM 0.20.2 accepts manually replayed response messages, reasoning items, function calls, and
  linked function outputs. Its non-Harmony converter rejects encrypted reasoning content; the
  selected local Qwen model instead returns parser-produced reasoning text. Hosted and local
  histories are isolated, so an encrypted hosted item is never sent to the local endpoint. See
  the tagged [vLLM Responses input conversion](https://github.com/vllm-project/vllm/blob/v0.20.2/vllm/entrypoints/openai/responses/utils.py).
- vLLM 0.20.2 represents output-token exhaustion as an `incomplete` Response with
  `max_output_tokens` details, which the existing Worker classifies as `model_error`. Its
  Responses protocol does not define OpenAI refusal content items for the selected local model,
  so a local policy refusal may arrive as ordinary text and cannot be given the hosted
  `refusal` termination reason reliably. See the tagged
  [vLLM Responses protocol](https://github.com/vllm-project/vllm/blob/v0.20.2/vllm/entrypoints/openai/responses/protocol.py).

The application records these limitations and exposes failures at the existing Agent result
boundary. It does not infer provider semantics from message text or hide incompatibility with a
fallback request.

## Architectural Decision

The complete application remains the v0.8.0 deterministic Scope, sequential
Supervisor-Worker Research, and Write-Critic-Revise workflow:

```text
load and validate run configuration
    -> construct hosted OpenAI client
    -> select Worker backend once
       -> reuse hosted client and MODEL_NAME
          or
       -> construct local OpenAI client with LOCAL_WORKER_* values
    -> print the selected Worker model boundary
    -> hosted Scope workflow
    -> hosted Research Supervisor loop
       -> AgentRunRequest with model source and model name
       -> existing synchronous Worker loop and tools
       -> AgentRunResult with model source and model name
       -> merge only completed notes
    -> hosted Write-Critic-Revise workflow
    -> final Markdown report
```

Ownership boundaries are fixed as follows:

- The operator chooses `openai` or `local` through one environment value before the run.
- `main` validates conditional configuration and constructs at most two SDK clients.
- The existing hosted client and `MODEL_NAME` own Scope, Supervisor, Write, Critic, and Revise.
- The selected Worker client and model own every request inside `run_research_worker_loop`.
- `AgentRunRequest` records the selected model source and model name for one Worker invocation.
- `AgentRunResult` copies those two values so hosted and local results remain distinguishable.
- The Worker harness owns history replay, custom tool execution, source registration, budgets,
  response classification, and stopping exactly as before.
- The external operator owns vLLM installation, model download, server startup, parser flags,
  hardware selection, and endpoint security.

No Supervisor decision can select or change a model. No Worker can delegate to another model.

## User-Visible Behavior

The CLI invocation, five top-level stages, Scope approval, Supervisor policy, tool behavior,
final report, and fail-fast policy remain unchanged.

Before Scope starts, the terminal prints one Worker model boundary containing only:

```text
[Worker model] Research policy | CONFIGURED | <openai|local>, <model name>
```

It does not print the base URL or either API key. Every Agent Run Result summary adds:

```text
Model source: <openai|local>
Model: <model name>
```

All existing turn, tool, source-registration, selected-source read, result, notes, and report
output remains in its current order. The local path does not change terminal vocabulary based on
model-specific reasoning or tool-parser output.

## Runtime Flow

At startup:

1. Load `.env` without overriding process environment values.
2. Require `OPENAI_API_KEY`, `MODEL_NAME`, and `TAVILY_API_KEY` for every run.
3. Read `WORKER_BACKEND`; an absent value defaults to `openai` for backward compatibility.
4. Reject a non-empty value other than `openai` or `local` before constructing a client.
5. Construct one hosted `OpenAI` client with `OPENAI_API_KEY` and `max_retries=0`.
6. For `openai`, reuse that client and `MODEL_NAME` for the Worker.
7. For `local`, require `LOCAL_WORKER_BASE_URL`, `LOCAL_WORKER_API_KEY`, and
   `LOCAL_WORKER_MODEL_NAME`, then construct a second `OpenAI` client with those values and
   `max_retries=0`.
8. Print the safe Worker model boundary and start the unchanged workflow.

For each Supervisor task:

1. Build an `AgentRunRequest` containing Worker number, approved brief, validated task, model
   source, and model name.
2. Initialize the same fresh `AgentRunState` and Responses input history.
3. Send every Worker model turn through the selected Worker client and request model.
4. Keep `store=False`, full ordered output-item replay, strict tools, automatic tool choice while
   budget remains, linked function outputs, and the forced tool-disabled final-notes request.
5. Classify the returned SDK `Response` through the existing status, refusal, output-item, notes,
   and budget checks.
6. Copy model source and model name into the immutable result.
7. Print the result and merge only completed notes into `ResearchState`.

The local endpoint is not contacted during Scope, Supervisor, Write, Critic, or Revise. The
OpenAI endpoint is not contacted for a local Worker's model turns. Tavily and arXiv tool calls
remain application-owned external requests and are identical on both Worker paths.

## Local vLLM Compatibility Contract

The supported local contract is deliberately narrower than the complete OpenAI Responses API:

- one non-streaming text-generation model served through a vLLM 0.20.2-compatible `/v1` base
  URL;
- non-streaming `responses.create` requests with `instructions`, list-shaped `input`, strict
  custom function tools, `tool_choice="auto"` or `tool_choice="none"`, and `store=False`;
- output items parseable by the installed OpenAI Python SDK;
- `completed`, `incomplete`, or `cancelled` top-level status values;
- zero or more ordered `function_call` items with JSON argument strings and stable `call_id`
  values; and
- replay of returned output items followed by matching application-owned
  `function_call_output` items.

The reference vLLM server command is:

```text
vllm serve Qwen/Qwen3-1.7B \
  --reasoning-parser qwen3 \
  --structured-outputs-config.backend xgrammar \
  --enable-auto-tool-choice \
  --tool-call-parser hermes \
  --api-key local-worker
```

The matching application values are:

```text
WORKER_BACKEND=local
LOCAL_WORKER_BASE_URL=http://127.0.0.1:8000/v1
LOCAL_WORKER_API_KEY=local-worker
LOCAL_WORKER_MODEL_NAME=Qwen/Qwen3-1.7B
```

Different open-weight models and parser combinations may work, but they are not accepted merely
because the server starts. They must satisfy the same complete manual history and tool-loop
scenario. The application sends no vLLM-specific request body fields and does not inspect server
version, model metadata, parser configuration, or hardware.

## Agent Run Contract Changes

Add one bounded `AgentModelSource` value with `openai` and `local` members.

`AgentRunRequest` adds:

```text
model_source: AgentModelSource
model_name: non-empty string
```

`AgentRunResult` adds immutable copies of the same fields. Initialization rejects an invalid
source or empty model name. Finalization copies the validated request values without accepting a
second source or model argument.

The mutable state adds no client, endpoint, API key, parser, server, hardware, or provider
object. Model selection is immutable for the life of one request and does not consume a turn,
tool, or read budget.

All existing status, termination, notes, error, turn, tool, and read invariants remain unchanged.

## CLI Contract

Invocation remains:

```text
uv run deep_research.py "Question"
```

Configuration is:

| Variable | Required | Meaning |
| --- | --- | --- |
| `OPENAI_API_KEY` | Always | Hosted Scope, Supervisor, report, and hosted Worker authentication |
| `MODEL_NAME` | Always | Hosted model for Scope, Supervisor, report, and hosted Worker |
| `TAVILY_API_KEY` | Always | Web search and selected-source extraction |
| `WORKER_BACKEND` | No | `openai` by default; set `local` for the vLLM Worker |
| `LOCAL_WORKER_BASE_URL` | Local only | vLLM OpenAI-compatible `/v1` base URL |
| `LOCAL_WORKER_API_KEY` | Local only | Value sent only to the local vLLM endpoint |
| `LOCAL_WORKER_MODEL_NAME` | Local only | Exact model identifier served by vLLM |

The local variables are ignored on the `openai` path. `OPENAI_API_KEY` is never reused as the
local key, and the local key is never sent to OpenAI. There is no CLI model flag, per-Worker
override, automatic model listing, configuration file, or endpoint-discovery request.

## Observability Contract

Live terminal output remains the only run observability mechanism. It may print the bounded
model source, exact model name, existing progress, safe source hostnames, counts, and Agent result
fields.

It must not print model base URLs, API keys, request headers, request bodies, prompts,
instructions, full Responses history, raw model responses, token usage, raw reasoning, parser
configuration discovered from a server, or hardware details.

This release adds model-source visibility, not structured tracing, telemetry, model evaluation,
latency measurement, token accounting, or cost comparison.

## Artifact Contract

Release 0.9.0 creates no run directory and writes no application output files. Client objects,
endpoint values, credentials, model output items, source registries, and extracted content remain
in process memory. Completed notes, draft, critique, and final report remain in memory and
terminal output as before.

The application does not download models, write vLLM logs, cache weights, or create server
configuration. External vLLM and model caches are outside the application's artifact contract.

## Failure and Stopping Behavior

Missing always-required configuration, an unknown Worker backend, or missing local-only values
prints one concise configuration error and exits with status 2 before any model or tool request.

Local client construction errors and workflow errors retain the top-level exit status 1. A local
Worker connection failure, authentication failure, incompatible request field, missing parser,
malformed SDK response, incomplete response, invalid output items, or other Responses request
failure becomes the existing failed `AgentRunResult` with `model_error`. The result is printed,
no notes merge, and the workflow stops before another Supervisor or report request.

A top-level local `cancelled` response remains `cancelled`/`cancelled`. A local endpoint that
returns a supported refusal item remains `failed`/`refusal`; the vLLM 0.20.2 Qwen reference path
does not guarantee such items. Ordinary refusal-like text is not reclassified by string matching.

Tool failures, tool limit, turn limit, source-read limit, result finalization, Supervisor, Scope,
report, and user cancellation behavior remain unchanged. There are no client retries, fallback
models, backend switching, repair requests, replacement Workers, partial reports, or new
termination reasons.

## Implementation Constraints

- Write this specification before changing runtime code.
- Keep client construction, backend selection, run-contract changes, workflow wiring, terminal
  progress, and CLI configuration in repository-root `deep_research.py`.
- Keep all model instructions in `agent_instructions.py` and all research tools in
  `agent_tools.py`; this release requires no changes to their architecture.
- Use the existing official OpenAI Python SDK for both clients and the existing `llm_call`
  request primitive for all model calls.
- Reuse one hosted client on the OpenAI Worker path. Construct one separate local client only on
  the local path.
- Keep both SDK clients synchronous with `max_retries=0`.
- Preserve `store=False`, ordered output-item replay, linked function outputs, strict tool
  schemas, tool-choice behavior, no Worker output-token limit, and all current budgets.
- Extend the existing request and result dataclasses. Add no model client class, provider
  protocol, router, gateway, adapter, configuration class, endpoint class, server manager, or
  model registry.
- Do not send provider-specific request extensions or translate Responses items.
- Do not inspect or print API keys or read the local `.env` into documentation or diagnostics.
- Add no vLLM, PyTorch, Transformers, CUDA, model, parser, or HTTP dependency to the project.
- Preserve current Scope, Supervisor, report, retrieval, destination, failure, and artifact
  behavior.
- Update `TECH_STACK.md`, `ROADMAP.md`, `specs/README.md`, README, changelog, project version and
  description, lock metadata, and arXiv `User-Agent`.
- Do not create a release tag until the complete manual acceptance scenario is verified.

## Manual Acceptance Scenario

Start either the documented portable vLLM 0.20.2 reference server or the Apple Silicon manual
verification profile and configure the local Worker. With valid OpenAI and Tavily configuration,
run:

```text
uv run deep_research.py "Compare recent evidence about AI coding-agent productivity and failure modes."
```

Establish a recent time horizon and require current web evidence plus one relevant arXiv source.
Approve the brief. Confirm that:

1. the terminal identifies the Worker as `local` with the exact model name from the selected
   verification profile without printing its endpoint or key;
2. Scope and the first Supervisor decision use only the hosted client;
3. every Worker model turn uses only the local client and exact local model name;
4. the local Worker emits at least one strict custom function call, receives its matching linked
   output, and successfully continues from manually replayed Responses items;
5. one Worker searches, receives application-issued source IDs, and completes at least one
   bounded selected-source read;
6. the local response output order is preserved without printing reasoning items;
7. the Agent result reports `local`, the exact model, and exact turn, tool, and read usage;
8. completed local notes alone merge into ResearchState;
9. Write, Critic, and Revise use only the hosted client and produce the complete final Markdown
   report; and
10. the process exits successfully without creating a run directory or application output file.

Run the same question with `WORKER_BACKEND=openai` and confirm that one hosted client and
`MODEL_NAME` serve every stage, the result reports `openai`, and existing v0.8.0 behavior is
unchanged.

Exercise controlled configuration and Worker paths:

1. absent `WORKER_BACKEND` selects `openai`;
2. an unknown backend exits before client construction;
3. the OpenAI path does not require or use any `LOCAL_WORKER_*` value;
4. the local path reports all missing local-only variables together and never substitutes
   `OPENAI_API_KEY`;
5. hosted and local client construction both disable SDK retries;
6. every local Worker request retains `store=False`, the local model, current tools, and current
   tool choice without a Worker output-token limit;
7. returned message, reasoning, and function-call items remain ordered in the next local input,
   followed by linked tool outputs in execution order;
8. an `incomplete` local response becomes visible `failed`/`model_error` with no fallback;
9. a supported refusal item becomes `failed`/`refusal`, while ordinary text is never classified
   as refusal by wording; and
10. request initialization and result finalization reject invalid model sources or empty model
    names and copy valid values into the immutable result.

Preserve the complete v0.8.0 registration, destination, read, tool-budget, turn-budget,
run-contract, early Supervisor finish, four-Worker hard stop, Scope, structured-output, report,
request-count, cancellation, and failure scenarios.

## Completion Criteria

The specification may become `Verified` after these checks pass:

```text
uv run python -m py_compile deep_research.py agent_instructions.py agent_tools.py
uv run deep_research.py --help
```

The real local-service scenario, hosted regression scenario, and controlled configuration,
client-isolation, request, history, response, result, and failure scenarios must pass. Inspect
terminal ordering, exact model routing, exact usage, fresh Worker state, completed-result merging,
hosted report inputs, and absence of application output files.

Acceptance confirms protocol and harness interoperability. It does not grade either model's
research conclusions, establish performance parity, benchmark quality, measure latency or cost,
or certify every vLLM model and parser combination.
