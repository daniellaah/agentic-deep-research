# v0.7.0 — Explicit Agent Run Contract

## Status

Verified

## Learning Question

What becomes easier to observe, test manually, and reuse when every bounded Research Worker is
expressed as an application-owned request, mutable run state, and immutable terminal result
instead of returning notes on success and raising an unstructured exception on failure?

## Problem and Rationale

Release 0.6.0 makes the Supervisor and Worker control relationship explicit, but one Worker's
runtime boundary is still implicit. `run_research_worker_loop` owns an ordered Responses API
history and local counters, then either returns one Markdown string or raises an exception. The
caller can see successful notes, but it cannot inspect one stable value that says whether the
Worker completed, why it stopped, or how much of its turn and tool budgets it used. Failure paths
discard those counters and stopping details before the top-level error boundary reports them.

That string-or-exception boundary is adequate for the first supervised release, but it is too
weak for the accepted harness-first roadmap. Release 0.9.0 must compare an OpenAI-hosted Worker
with a local Worker without changing the meaning of completion. Release 0.10.0 must retain
run-level accounting across context sessions. Release 0.13.0 must return comparable rollout
results through the same Worker harness. Those consumers need one application-owned contract
before retrieval, providers, sessions, concurrency, persistence, or rollout storage make the
runtime harder to inspect.

Release 0.7.0 therefore introduces the smallest named runtime representation justified by that
need:

- `AgentRunRequest` is the immutable semantic input for one Research Worker;
- `AgentRunState` is the private mutable state used while that Worker runs; and
- `AgentRunResult` is the immutable terminal value returned for every expected operational
  outcome.

The result distinguishes the application-owned Agent run status from the status of any one
provider response. It also uses a bounded termination vocabulary and exposes derived turn and
tool usage. A completed run still supplies non-empty Markdown notes. A failed or cancelled run
supplies no notes and instead carries one concise error message. The Supervisor loop continues to
merge only completed results and remains fail-fast for unsuccessful Workers, so this release does
not introduce failure-aware orchestration early.

The current official Responses API reference defines a response-level status that may be
`completed`, `failed`, `in_progress`, `cancelled`, `queued`, or `incomplete`; it also defines an
optional per-response `usage` object. Those are provider response fields, not an application
Agent-run contract. The same reference states that `max_output_tokens` includes both visible and
reasoning tokens, and that disabled input truncation fails when the input exceeds the model
context window. Release 0.7.0 records response status and output items through the existing
explicit loop, but retains only application-owned turn and custom-tool budgets in the result. It
does not add token or cost accounting, automatic truncation, token preflight, or a new output
limit. See the official
[Responses API reference](https://developers.openai.com/api/reference/cli/resources/responses/methods/create).

The new structures are ordinary standard-library dataclasses and string enums. They are not
model-generated data, so Pydantic remains limited to Structured Outputs boundaries. They do not
define a provider-neutral Agent API, tool registry, workflow engine, event hierarchy, trace
schema, or reusable base class.

## Architectural Decision

The complete application remains the release 0.6.0 hybrid workflow. Only the inside and return
boundary of one Research Worker change:

```text
deterministic Scope workflow
    -> approved ResearchBrief
    -> adaptive Research Supervisor loop
       -> validated ResearchTask
       -> application builds AgentRunRequest
       -> Research Worker initializes AgentRunState
       -> explicit Responses function-tool loop mutates that state
       -> application finalizes one AgentRunResult
       -> print result summary
       -> merge only a completed result or fail the complete run
       -> observe updated ResearchState and repeat or finish
    -> deterministic Write-Critic-Revise workflow
    -> final Markdown report
```

The release fixes these ownership boundaries:

- **Supervisor policy** still chooses one next `ResearchTask` or finishes from the approved brief
  and completed research. It does not manage Worker lifecycle state or interpret raw provider
  failures.
- **Worker request** contains the complete semantic input for one isolated research task. It does
  not contain an SDK client, API key, mutable history, provider endpoint, retry policy, or shared
  research state.
- **Worker run state** owns the ordered Responses items, counters, status, and stopping details
  for exactly one invocation. It is private to the synchronous Worker loop and is never sent to
  another model stage.
- **Worker result** is the only expected terminal value from the Worker lifecycle boundary. It
  contains task association, terminal status, termination reason, notes or error, and derived
  budget usage.
- **Application runtime** constructs requests, initializes and finalizes state, prints result
  summaries, validates terminal consistency, merges completed results, and fails the overall run
  after an unsuccessful result.
- **Report workflow** continues to receive only the approved brief and deterministically rendered
  completed task notes. It does not receive run statuses, errors, counters, or histories.

No model may construct or mutate an `AgentRunRequest`, `AgentRunState`, or `AgentRunResult`. These
values describe application execution and are not Structured Outputs schemas or tool arguments.

## User-Visible Behavior

The CLI invocation, Scope approval experience, sequential Supervisor policy, search tools, and
Write-Critic-Revise workflow remain unchanged. The five top-level stages are still Scope,
Research, Write, Critic, and Revise.

Within Research, every started Worker now ends at one visible result boundary. The terminal
prints a result summary containing:

- the Worker number and task title;
- terminal status;
- one bounded termination reason;
- model turns used and the fixed turn limit; and
- tool calls used and the fixed tool-call limit.

A completed result is followed by the existing full Research Notes block. A failed or cancelled
result prints one concise error in its summary, prints no Research Notes block, is not merged into
`ResearchState`, and stops the complete run before another Supervisor or report request. The
top-level CLI still exits nonzero for that unsuccessful overall run.

The visible distinction between status and reason is intentional. For example, a Worker that
uses its fifth tool call and then successfully returns notes on the application-forced final
turn has status `completed` and termination reason `tool_limit`. A Worker that consumes all six
turns without final notes has status `failed` and termination reason `turn_limit`.

Acceptance remains mechanism-focused. It verifies request construction, state transitions,
result consistency, budget accounting, integration with the Supervisor, and visible stopping.
It does not grade research quality, factual correctness, source quality, citation accuracy, or
semantic completeness.

## Runtime Flow

```text
question
-> load and validate configuration
-> run bounded Scope workflow and approve one ResearchBrief
-> initialize application-owned ResearchState
-> Research
   -> request and validate one SupervisorDecision
   -> if the Supervisor finishes, retain the existing successful stop behavior
   -> otherwise select the one validated ResearchTask
   -> construct AgentRunRequest(worker number, approved brief, task)
   -> run Research Worker
      -> initialize AgentRunState(request, initial ordered input)
      -> while state is running and model-turn budget remains
         -> derive whether the tool budget is exhausted
         -> increment model turns used for the request attempt
         -> make one synchronous Responses request
         -> classify a provider cancellation, refusal, or model failure
         -> otherwise append every response output item in order
         -> if no function call exists
            -> require non-empty Markdown notes
            -> finalize completed/completed or completed/tool_limit
         -> if function calls exist
            -> execute them synchronously in response order within the tool budget
            -> increment tool calls used for every attempted custom call
            -> append every linked function_call_output item
            -> continue
      -> if the sixth turn ends without notes, finalize failed/turn_limit
      -> return one immutable AgentRunResult
   -> print the complete Worker result summary
   -> if result.status is completed
      -> print notes
      -> append the result once to ResearchState
      -> continue existing Supervisor flow
   -> otherwise
      -> raise one concise fatal application error from the returned result
      -> do not merge, continue, or write a partial report
-> render completed notes in Worker order
-> run Write, Critic, and Revise
-> print final Markdown report
```

Every expected operational stop inside the Worker loop is finalized once. Finalization validates
the complete state-to-result invariants before constructing the immutable result. An unexpected
programming invariant violation may still raise directly because it indicates a defect in the
harness rather than an Agent outcome that should be normalized.

## AgentRunRequest Contract

`AgentRunRequest` is one frozen standard-library dataclass with this shape:

```text
AgentRunRequest
|- worker_number: application-assigned positive integer
|- approved_brief: non-empty rendered ResearchBrief string
`- task: validated immutable ResearchTask
```

The application constructs one request only after accepting a valid Supervisor task. The
request contains exactly the semantic values the Worker currently receives. It does not contain
the original user question, clarification transcript, approval commands, earlier Worker notes,
global Worker budget, report artifacts, model name, provider endpoint, client object, API key,
tool implementation, instructions string, mutable counters, or Responses history.

`worker_number` is contiguous and one-based within the interactive Research run.
`approved_brief` is the exact rendered approved brief. `task` is the same frozen Pydantic
`ResearchTask` accepted from the Supervisor decision. The request itself uses no Pydantic model
because it is application-generated rather than model-generated.

The Worker input renderer consumes the request and produces the same initial user item as release
0.6.0: the complete approved brief followed by the Worker number and delegated task. One request
always initializes one fresh run state; requests and states are never reused across Workers.

## AgentRunState Contract

`AgentRunState` is one mutable standard-library dataclass private to the Worker harness:

```text
AgentRunState
|- request: AgentRunRequest
|- input_items: ordered list of Responses API input/output items
|- model_turns_used: integer
|- tool_calls_used: integer
|- status: running | completed | failed | cancelled
|- termination_reason: null | AgentTerminationReason
|- notes: null | non-empty Markdown string
`- error_message: null | string with 1 through 300 characters
```

Initialization is deterministic:

- `request` is the caller's frozen request;
- `input_items` contains exactly one application-owned user message built from that request;
- both usage counters are zero;
- `status` is `running`; and
- termination reason, notes, and error message are null.

The state follows these invariants:

- only the application mutates it;
- one state belongs to exactly one request and one Worker invocation;
- `input_items` preserves the existing manual Responses history order;
- `model_turns_used` counts attempted Research model requests, including an attempt that ends in
  an SDK exception or non-completed response;
- `tool_calls_used` counts attempted custom function calls, including malformed, unknown, and
  recoverably failed calls, but never exceeds the fixed limit;
- counters increase monotonically and are never reset within a Worker;
- only `running` may transition to a terminal status;
- finalization sets status, termination reason, and exactly one of notes or error as one logical
  transition; and
- a terminal state cannot return to `running` or be finalized twice.

Every successful provider response contributes all of its output items in original order before
linked application-owned `function_call_output` items are appended. Provider-owned reasoning or
message items required for stateless continuation remain opaque and are replayed without
interpretation. The state does not store parsed private reasoning, a separate event log,
Supervisor state, report values, token totals, costs, wall-clock timing, or persistent IDs.

The state exists only while `run_research_worker_loop` executes. After finalization, the complete
history is discarded; only `AgentRunResult` may enter `ResearchState`.

## AgentRunResult Contract

`AgentRunResult` is one frozen standard-library dataclass:

```text
AgentRunResult
|- worker_number: positive integer copied from the request
|- task: immutable ResearchTask copied from the request
|- status: completed | failed | cancelled
|- termination_reason: AgentTerminationReason
|- notes: null | non-empty Markdown string
|- error_message: null | string with 1 through 300 characters
|- model_turns_used: integer
|- model_turn_limit: integer
|- tool_calls_used: integer
`- tool_call_limit: integer
```

The result is derived from one terminal `AgentRunState`; callers cannot construct it by parsing
model text. Error messages are application-facing summaries limited to 300 characters; they may
retain a useful provider code or refusal excerpt but never an exception representation, response
body, request payload, or secret. Limits are copied from the application constants so the result
remains interpretable without consulting mutable state. Remaining budgets are derived as limit
minus used and are not stored as duplicate fields. The result contains no SDK response object,
raw history, raw tool
payload, provider exception, API key, prompt, model instructions, token usage, cost, or private
reasoning.

Final result consistency is strict:

| Status | Allowed termination reasons | Notes | Error message |
| --- | --- | --- | --- |
| `completed` | `completed`, `tool_limit` | Required and non-empty | Must be null |
| `failed` | `turn_limit`, `context_limit`, `refusal`, `model_error`, `tool_error` | Must be null | Required and non-empty |
| `cancelled` | `cancelled` | Must be null | Required and non-empty |

Both used counters must be between zero and their corresponding limits. An ordinary Worker run
attempts at least one model turn; a zero-turn cancelled result is representable for a future
application cancellation before the first request, but v0.7.0 adds no such interactive runtime
path.

The result itself is the release's structured application-owned Worker result. No additional
`ResearchResult` wrapper, result dictionary, Pydantic result schema, or generic artifact envelope
is introduced.

## Status and Termination Contract

`AgentRunStatus` and `AgentTerminationReason` are standard-library string enums. The mutable state
uses `running`, `completed`, `failed`, and `cancelled`. A returned result is always terminal and
therefore never has status `running`.

The exact termination vocabulary is:

- `completed`: the model returned valid non-empty notes before the application had to force a
  final-notes turn for tool exhaustion;
- `tool_limit`: all five tool attempts were used and a later tool-disabled turn successfully
  returned valid non-empty notes;
- `turn_limit`: all six model-turn attempts were used without valid final notes;
- `context_limit`: an application-owned context boundary ends the run before completion;
- `refusal`: a Worker response contains provider refusal content instead of usable research
  progress or notes;
- `model_error`: any other Worker model-request exception, failed or incomplete response,
  unexpected synchronous response status, or invalid required model output;
- `tool_error`: the application cannot produce a valid linked function output at the custom-tool
  execution boundary; and
- `cancelled`: application cancellation ends the Worker before completion.

These values describe why the complete Worker invocation stopped. They do not copy a raw SDK
exception class, HTTP status, arbitrary provider error string, `incomplete_details.reason`, or
tool error message into the vocabulary.

The application uses the most specific terminal reason it can establish from the stopping event.
If a tool-exhausted final-notes request is refused or its API request fails, the reason is
`refusal` or `model_error`, not `tool_limit`. If the sixth completed model response still does not
contain valid final notes, no seventh request is allowed and the result is
`failed`/`turn_limit`. `tool_limit` is therefore a successful bounded completion reason rather
than a synonym for every state where `tool_calls_used == tool_call_limit`.

The existing search-tool error behavior remains recoverable. Malformed arguments, unknown tool
names, request failures, and other ordinary exceptions caught by `execute_worker_tool_call` are
returned to the model as linked error outputs and count against the tool budget. They do not by
themselves terminate the run or produce `tool_error`. `tool_error` is reserved for a fatal failure
of the application-owned tool boundary itself, such as being unable to construct or serialize a
linked output after ordinary execution errors have been caught.

The bounded vocabulary reserves `context_limit` for the application-owned context boundary
planned for release 0.10.0, but the hosted v0.7.0 Worker does not emit it. The official Responses
reference says disabled truncation produces an HTTP 400 when input exceeds the context window,
but it does not document a dedicated stable context error code, and its documented incomplete
reasons are `max_output_tokens` and `content_filter`. This release therefore does not estimate
tokens, parse exception messages, infer a context failure from an arbitrary HTTP 400, enable
automatic truncation, or establish a context budget. Hosted request failures use `model_error`.

The `cancelled` value completes the bounded contract, but the interactive Worker still has no
post-approval user input or cancellation control in this release. Existing Scope cancellation
continues to end before any Worker request and therefore creates no `AgentRunResult`.

## ResearchState Integration Contract

`ResearchState` remains one application-owned in-memory dictionary:

```text
ResearchState
|- approved_brief: rendered string
|- worker_results: ordered list[AgentRunResult]
`- stop_reason: null | application-owned string
```

Only completed `AgentRunResult` values may be appended. Every appended result has a non-empty
`notes` field and retains the same contiguous Worker order as release 0.6.0. A failed or cancelled
result is printed but is not appended, is not shown to the Supervisor, and does not change the
global completed-Worker count.

To preserve the current Supervisor policy and model-input boundary, deterministic Supervisor
state rendering uses only these fields from each completed result:

- Worker number;
- delegated task; and
- final notes.

Agent status, termination reason, turn usage, tool usage, and fixed per-Worker limits remain
application-facing metadata. They are not added to the Supervisor prompt because all merged
results are already completed and the Supervisor has no failure-recovery policy in this release.
The report workflow likewise receives only task-associated notes.

The Supervisor's empty-decision and four-Worker global stop reasons remain unchanged. The global
Worker budget is still derived from the number of completed results. Result metadata does not add
a global turn, tool, token, cost, or time budget.

## Responses API Contract

Scope, Supervisor, and report requests retain the complete release 0.6.0 behavior. The one
official SDK client still uses `max_retries=0`; all calls remain synchronous and set
`store=False`; no request uses `previous_response_id` or a Conversation.

The Research Worker retains manual ordered history:

1. initialize `AgentRunState.input_items` with the application-owned request rendering;
2. increment `model_turns_used` immediately before each Responses request attempt;
3. require a synchronous terminal provider response;
4. append every returned output item in original order when the response is usable;
5. execute returned custom function calls in response order;
6. increment `tool_calls_used` immediately before each allowed tool attempt;
7. append every linked application-owned `function_call_output`; and
8. replay the complete ordered list on the next turn.

A provider response with status `completed` may contain function calls or final notes. Provider
status `cancelled` finalizes the Worker as `cancelled`/`cancelled`. Refusal content finalizes as
`failed`/`refusal`. `Failed`, `incomplete`, `queued`, or `in_progress` responses returned from the
synchronous call, SDK exceptions including HTTP 400 responses, missing required output, and
completed responses with empty text before the sixth hard turn finalize as
`failed`/`model_error`.

While custom-tool budget remains, Worker requests use `tool_choice="auto"`. Once five tool calls
have been attempted, a later available turn appends the existing application-owned budget-
exhausted input and uses `tool_choice="none"`. A valid response to that forced turn finalizes as
`completed`/`tool_limit`. A tool request returned despite `tool_choice="none"` is invalid required
model output and finalizes as `failed`/`model_error` when another turn would otherwise remain. If
that invalid completed response consumes the sixth and final turn, the hard turn boundary wins
and the result is `failed`/`turn_limit`.

Worker requests continue to omit `max_output_tokens`. The application reads neither provider
`usage` nor pricing data into `AgentRunState` or `AgentRunResult`. `model_turns_used` is request-
attempt accounting, not token accounting, and `tool_calls_used` counts application custom-tool
attempts rather than provider built-in tools.

`llm_call` remains a thin provider primitive that returns the official SDK `Response` without
wrapping it. Response-to-run classification belongs inside the Worker harness and does not alter
the structured or free-text extraction rules used by Scope, Supervisor, Write, Critic, or Revise.

## Instruction Contract

All instructions remain plain strings in `agent_instructions.py`. Scope, Supervisor, Worker,
Write, Critic, Revise, and budget-exhausted instructions retain their release 0.6.0 behavioral
responsibilities.

No instruction mentions `AgentRunState`, asks the model to choose a run status or termination
reason, requests budget accounting, or asks the model to return a result envelope. Final Worker
notes remain ordinary Markdown free text because status, reason, counters, and consistency are
application facts. No instruction requests or claims to expose private chain-of-thought.

## CLI Contract

The invocation remains:

```text
uv run deep_research.py "Research the impact of AI coding agents."
```

The positional question and these environment variables remain required:

- `OPENAI_API_KEY`;
- `MODEL_NAME`; and
- `TAVILY_API_KEY`.

The fixed top-level labels remain Scope, Research, Write, Critic, and Revise. Every successfully
completed Worker adds this visible boundary before its notes:

```text
AGENT RUN RESULT | WORKER <number> | <task title>
Status: completed
Termination reason: <completed or tool_limit>
Model turns: <used>/6
Tool calls: <used>/5
```

A failed or cancelled result uses the same heading and budget lines, adds one concise `Error:`
line, and omits the notes block. Exact separator width and capitalization may follow the existing
terminal helpers, but every field and value above must be present.

Successful top-level output still shows every Scope boundary, Supervisor decision and task,
Worker turn and tool activity, Research stop reason, combined notes, draft, critique, and final
report. It does not expose raw state or histories.

## Limits and Stopping Contract

All release 0.6.0 Scope, Supervisor, global Worker, search-result, and text-size limits remain
unchanged.

Each Agent run has:

- at most 6 attempted Research model turns;
- at most 5 attempted custom function calls;
- at most 3 results per search call; and
- at most 2,000 Tavily-content or arXiv-summary characters per returned result before model
  history.

The state counters are the single source for enforcing and reporting the per-Worker turn and tool
budgets. Loop indices, progress labels, forced-final-turn decisions, and result usage are derived
from those counters rather than maintained as duplicate mutable accounting.

Multiple function calls in one model response are handled in response order. Calls beyond the
remaining budget receive the existing linked limit-error output, are shown as skipped, and do not
increase `tool_calls_used` above five. Once the limit is reached, the next model turn, if one
remains, is the forced final-notes turn. The forced turn still consumes one of the six model-turn
attempts.

Global successful-run request counts and absolute hard limits remain those of release 0.6.0. The
new result structures do not make additional model or tool calls. An early successful result,
successful tool-limit result, Supervisor finish, or four-Worker application stop proceeds under
the existing rules. Any failed or cancelled Worker result stops the complete run.

## Observability Contract

Live terminal output remains the only run observability mechanism. Release 0.7.0 adds one result
summary for every started Worker and makes status, termination reason, and budget usage visible
even when the Worker does not complete.

The application may print the result's task identity, status, bounded reason, usage, limits,
notes, and concise error. It must not print the mutable state object, enum representations, raw
dataclass representation, complete Responses history, response `usage`, request bodies, prompts,
instructions, API keys, raw provider exceptions, raw tool payloads, or reasoning items.

The result is structured application state, not a structured trace. The runtime creates no event
stream, span hierarchy, per-turn record, trajectory file, token log, cost report, dashboard, or
evaluation score. Terminal turn and tool progress remains ephemeral.

## Artifact Contract

Release 0.7.0 creates no run directory and writes no application output files. Requests, mutable
run states, terminal results, ResearchState, notes, report artifacts, and final report remain in
memory. The Worker state and complete history are discarded after its result is finalized.

Generated traces, reports, caches, and secrets remain ignored and uncommitted. Persistence and
rollout artifacts are deferred to later specifications.

## Failure Behavior

Configuration, Scope, Supervisor, and report failures retain release 0.6.0 behavior. They occur
outside a Worker and therefore do not create an `AgentRunResult`.

Within an active Worker, expected operational failures are converted into exactly one immutable
result and printed before the application exits:

- exhausting all turns without notes produces `failed`/`turn_limit`;
- refusal content produces `failed`/`refusal`;
- other API exceptions, non-completed responses, invalid tool-disabled output, and empty required
  notes produce `failed`/`model_error`;
- a fatal failure of the application-owned custom-tool boundary produces
  `failed`/`tool_error`; and
- an application cancellation during the Worker would produce `cancelled`/`cancelled`, although
  no interactive Worker cancellation path is added in this release.

After printing an unsuccessful result, the Supervisor loop raises one concise fatal error. It
does not merge the result, make another Supervisor decision, start a replacement Worker, retry
the Worker, continue with partial results, or run Write-Critic-Revise. This preserves the current
fail-fast overall behavior and leaves adaptive failure handling to release 0.12.0.

Ordinary caught search-tool failures remain recoverable linked outputs. If the Worker later
returns valid notes, its result may still be completed, and the notes must state material missing
coverage under the existing instruction contract.

There are no SDK-owned or application-owned retries, fallback decisions, inferred notes, schema-
repair calls, partial report, output file, or raw exception dump. An internal contract-invariant
violation raises as a programming error rather than fabricating a valid-looking result.

## Implementation Constraints

- Keep the complete workflow, boundary types, Worker harness, Supervisor loop, report workflow,
  CLI input, and terminal output in repository-root `deep_research.py`.
- Keep model instructions and application-owned model-input constants in
  `agent_instructions.py`; keep research-tool schemas, implementations, and dispatch in
  `agent_tools.py`.
- Add exactly the three named dataclasses `AgentRunRequest`, `AgentRunState`, and
  `AgentRunResult`, plus the bounded string enums needed for status and termination. Do not add a
  generic Agent definition, configuration object, runner class, base class, protocol, lifecycle
  interface, provider adapter, event class, or workflow framework.
- Use standard-library `dataclasses` and `enum.StrEnum`. Add no runtime dependency.
- Keep `ResearchTask`, `SupervisorDecision`, `ResearchBrief`, and clarification schemas as frozen
  Pydantic models because they remain model-generated Structured Outputs boundaries. Do not use
  Pydantic for application-owned run structures.
- Let `run_research_worker` build one `AgentRunRequest`, own visible Worker lifecycle output, and
  return one `AgentRunResult` for expected operational outcomes.
- Let `run_research_worker_loop` initialize and mutate one `AgentRunState`, preserve the explicit
  custom function-tool loop, and return one finalized `AgentRunResult` instead of notes or an
  ordinary operational exception.
- Use one small finalization function to validate terminal field consistency and derive the
  immutable result from state. Do not scatter direct result construction across stop branches.
- Count model request attempts before calling `llm_call` and count allowed tool attempts before
  dispatch so failure results retain consumed budget usage.
- Keep `execute_worker_tool_call` responsible for argument parsing, one tool attempt, recoverable
  tool-error conversion, progress, and linked output construction. Do not make tool functions
  aware of Agent run state or result types.
- Let the Supervisor loop inspect the returned result. Append it only when status is completed;
  otherwise raise after the result summary has been printed.
- Replace the release 0.6.0 plain `ResearchResult` dictionary with the completed
  `AgentRunResult`; do not retain duplicate `notes`, counter, status, or reason fields in another
  wrapper.
- Preserve deterministic Supervisor and combined-notes rendering by reading task identity and
  notes from completed results. Do not send run accounting or failure data to model stages.
- Preserve the current request, tool, history-replay, `store=False`, `max_retries=0`, worker-
  isolation, Supervisor, Scope, and report boundaries.
- Keep Worker requests without an application `max_output_tokens` value. Do not aggregate the
  optional provider `usage` object or add token, cost, duration, or context preflight accounting.
- Keep all execution synchronous. Do not add streaming, asynchronous code, concurrency,
  persistence, retries, caching, hosted tools, MCP, tracing, evaluation, automated tests, Ruff,
  or mypy.
- Update `TECH_STACK.md`, `ROADMAP.md`, `specs/README.md`, project version and description, lock
  metadata, and the arXiv `User-Agent` only as required when implementing and accepting this
  release. Do not create a release tag until manual verification is complete.

## Manual Acceptance Scenario

With valid configuration and a Structured Outputs-compatible model, run:

```text
uv run deep_research.py "Research the impact of AI coding agents."
```

Across clarification answers, establish a software-engineering audience, a recent time horizon,
and interest in measured productivity benefits, failure modes, and limitations. At the first
approval prompt enter `revise`, then request at least one recent arXiv source and one current web
source with returned URLs. Approve the replacement brief.

Confirm that:

1. Scope, Research, Write, Critic, and Revise complete once in that order;
2. Scope and Supervisor behavior remain the bounded release 0.6.0 behavior;
3. every delegated task constructs one request and starts one fresh mutable run state;
4. every Worker starts with zero usage, running status, no termination reason, no notes, and no
   error;
5. ordered response and function-call-output items are replayed exactly as before without
   exposing the history;
6. each attempted Research model request increments model-turn usage exactly once;
7. each allowed custom function call increments tool usage exactly once, including recoverable
   malformed, unknown, or failed calls;
8. every started Worker prints exactly one Agent Run Result summary;
9. an ordinary successful Worker reports `completed`/`completed`, correct usage against limits,
   a non-empty notes field, and no error;
10. the full notes block follows the summary and is merged once into ResearchState;
11. Supervisor state and report inputs retain the task and notes but exclude run status, reason,
    counters, limits, errors, and private Worker history;
