# v0.18.0 — Batch Rollout Runner

## Status

Draft

## Learning Question

What becomes reproducible and comparable when versioned JSONL tasks produce multiple bounded
rollouts through the same durable Worker harness, evidence contracts, traces, and graders used by
interactive runs?

## Problem and Rationale

Release 0.17.0 supports concurrency inside one research run. Evaluation and future training work
require many independent runs without a second inference implementation. Release 0.18.0 adds a
batch control plane around the existing run contract.

OpenAI's Batch API uses uploaded JSONL requests, asynchronous processing, stable batch objects,
per-request results, and an explicit completion window; see the official
[Batch API reference](https://platform.openai.com/docs/api-reference/batch/object?api-mode=responses).
This release adopts the broadly useful JSONL identity and asynchronous-job concepts, but does not
delegate the complete multi-step Agent loop to that provider API because each rollout includes
tools, checkpoints, and adaptive control.

## Primary Mechanism

A versioned input JSONL file defines tasks and rollout counts. The batch runner creates stable
rollout IDs, schedules complete runs under global concurrency and cost limits, resumes partial
batches, and writes one result record per rollout plus aggregate evaluation.

## Architectural Decision

```text
batch JSONL
    -> validate unique task IDs and rollout configuration
    -> create immutable batch manifest
    -> schedule existing deep-research run contract
    -> each rollout owns run directory, evidence, checkpoints, trace, and report
    -> aggregate terminal results and graders
```

Interactive and batch modes call the same Scope-bypassed approved-brief entry point, Supervisor,
Worker, tools, report workflow, and finalization code. Batch mode cannot maintain a forked Agent
implementation.

## User-Visible Behavior

The CLI creates a batch ID and prints queued, running, completed, failed, cancelled, and resumed
counts plus budget and output paths. Status and inspection do not require waiting for completion.

## Runtime Flow

1. Validate input schema, task IDs, approved briefs, rollout counts, and configuration.
2. Persist an immutable batch manifest and input hash.
3. Derive rollout IDs from batch, task, and rollout index.
4. Reserve batch-level concurrency, elapsed time, token, and optional cost budgets.
5. Execute each rollout through the existing durable run entry point.
6. Resume incomplete rollouts without repeating completed ones.
7. Record one terminal result for every requested rollout.
8. Run configured evaluation suites and produce aggregate distributions.

## Batch Data Contract

Each input item contains task ID, approved ResearchBrief or deterministic brief fixture, rollout
count, provider/model configuration name, evaluation suite, and optional metadata. It never embeds
credentials. Results contain rollout/run IDs, terminal status, reason, artifact references,
metrics, usage, latency, and error class.

## Persistence and Artifact Contract

```text
batches/<batch-id>/
|- manifest.json
|- input.jsonl
|- results.jsonl
|- summary.json
`- rollouts/<rollout-id> -> run artifact reference
```

Manifest and input hashes make the batch immutable. Resume rejects changed input under the same ID.

## Idempotency and Replay Contract

Task ID plus rollout index identifies exactly one rollout. Completed rollouts are never rerun by
resume. A deliberate repeat creates a new batch ID. Result append is idempotent and conflicting
terminal records are invariant failures.

## Security and Trust Boundary

Batch input is untrusted and schema-bounded. Paths derive from validated IDs. Per-run tool and
source protections remain unchanged. Global concurrency and cost limits prevent one input item from
expanding resource use without bound.

## CLI Contract

```text
uv run batch_rollouts.py create tasks.jsonl
uv run batch_rollouts.py status <batch-id>
uv run batch_rollouts.py resume <batch-id>
uv run batch_rollouts.py cancel <batch-id>
uv run batch_rollouts.py summarize <batch-id>
```

## Observability Contract

Trace batch creation, rollout dispatch, queue time, reservation, resume, cancellation, terminal
status, and aggregation. Summaries report success distribution, failure classes, quality metrics,
tokens, estimated cost, and latency percentiles.

## Evaluation Contract

Aggregate deterministic and model-grader metrics without hiding failed rollouts. Report denominators,
configuration identity, mean, median, selected percentiles, and per-task variance. Comparing models
or policies requires the same immutable input hash and evaluation versions.

## Failure and Stopping Behavior

One rollout failure is recorded and does not abort unrelated rollouts. Harness corruption, invalid
manifest, or global budget violation stops new dispatch and checkpoints the batch. Cancellation
propagates to active runs under v0.17 semantics and preserves completed results.

## Implementation Constraints

Reuse the existing run harness and local persistence. Do not add training, reward computation,
distributed workers, provider Batch API orchestration, hosted queue infrastructure, or a second set
of research prompts.

## Manual Acceptance Scenario

Create two tasks with two rollouts each. Inject one process interruption and one Worker failure.
Resume, confirm exactly four stable rollout IDs and terminal records, no repeated completed run,
complete artifact links, preserved failures, correct aggregate denominators, and reproducible
summary from the same saved results.

## Completion Criteria

Schema validation, immutable manifests, dispatch, resume, cancellation, per-rollout isolation,
aggregation, budget enforcement, and interactive-harness parity pass. Every requested rollout has
one auditable terminal result.

## Out of Scope

Distributed clusters, hosted job queues, SFT/GRPO/RL pipelines, reward models, dataset publishing,
automatic prompt optimization, cross-user tenancy, and indefinite rollout counts.

## Known Limitations and Deferred Decisions

Single-host batches are bounded by local capacity and provider quotas. Training-data export is a
later decision justified only after evaluation demonstrates artifact quality.
