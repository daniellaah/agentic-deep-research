# v0.1.0 — One Responses API Call

## Status

Draft

## Learning Question

What are the minimum request, response, trace, and artifact boundaries needed to make one
OpenAI Responses API call understandable and runnable?

## Problem and Rationale

The project eventually needs a tool-calling Agent loop, but implementing the loop in the
first release mixes two learning steps:

1. how a Responses API call works; and
2. how an application turns repeated Responses calls into an Agent.

This release isolates the first step. It is deliberately not an Agent yet. It provides a
small, observable baseline that the next release can extend without introducing an
architecture.

## User-Visible Behavior

The user runs one command with one question. The CLI:

1. validates the question and required environment variables;
2. creates a unique run directory;
3. prints that the run and model request have started;
4. makes exactly one Responses API call;
5. prints the returned answer;
6. writes the provider response to `trace.jsonl`;
7. writes the answer to `report.md`; and
8. prints the artifact paths and final status.

The CLI does not accept input after the run starts.

## Runtime Flow

The complete success path is:

```text
question
→ validate configuration
→ create run directory
→ call client.responses.create(...)
→ read openai_response.output_text
→ write trace.jsonl
→ write report.md
→ exit successfully
```

There is no iteration, tool definition, tool execution, conversation history, stopping
policy, or Agent abstraction.

## Responses API Contract

The release uses the synchronous `OpenAI` client.

The model request contains only the behavior required for the single call:

- `model=MODEL_NAME`;
- `input=question`; and
- `store=False`.

It does not provide tools and does not use:

- `previous_response_id`;
- the Conversations API;
- streaming;
- structured output;
- background mode; or
- model-specific reasoning configuration.

A completed response must contain non-empty `output_text`. Otherwise the run fails.

Manual history begins in `v0.2.0`. That release will preserve and replay the initial user
input and every response output item according to the
[official OpenAI model guidance](https://developers.openai.com/api/docs/guides/latest-model).

## CLI Contract

Planned invocation:

```text
uv run --env-file .env deep_research.py \
  "Explain in three concise bullets how a trace helps debug an AI agent."
```

Requirements:

- the question is one required positional argument;
- `OPENAI_API_KEY` must be present;
- `MODEL_NAME` must be present;
- missing input or configuration produces a concise error and nonzero exit code;
- normal progress and the final answer are written to standard output;
- fatal errors are written to standard error;
- terminal text is English;
- no CLI dependency is introduced.

## Trace Contract

The trace is newline-delimited JSON. Each event is a plain dictionary with:

| Field | Meaning |
| --- | --- |
| `timestamp` | UTC ISO 8601 event time |
| `event` | Event name |
| `run_id` | Identifier shared by the run |
| `data` | Event-specific JSON object |

Required success events:

- `run.started`
- `model.request.started`
- `model.response.completed`
- `report.written`
- `run.completed`

The provider response is serialized from the SDK response with `model_dump(mode="json")`
and stored under `model.response.completed`. The project does not recreate OpenAI
response types or invent a second provider schema.

A failure after the run directory exists appends `run.failed` with the exception type and
message when the trace remains writable.

The trace records only application activity and provider-visible response data. It does
not claim to expose private chain-of-thought.

## Terminal Progress

Terminal output is intentionally small:

- run started;
- model request started;
- model response received;
- report written;
- run completed or failed.

The first release does not introduce a renderer, progress framework, or token streaming.

## Artifact Contract

A started API run creates:

```text
runs/<run-id>/
├── trace.jsonl
└── report.md
```

The run directory and trace file are created before the API request.

On success:

- `trace.jsonl` contains the required events;
- `report.md` contains `openai_response.output_text`.

On failure:

- `trace.jsonl` remains available when possible;
- `report.md` may be absent.

Runs rejected before API execution because of missing input or configuration do not need a
run directory.

## Failure Behavior

The command exits unsuccessfully when:

- the question is missing;
- `OPENAI_API_KEY` or `MODEL_NAME` is missing;
- the Responses API call fails;
- the response has no output text; or
- an artifact cannot be written.

There are no automatic retries in this release.

## Implementation Constraints

- All runtime code lives in `deep_research.py`.
- Use the OpenAI Responses API and official Python SDK directly.
- Use the synchronous `OpenAI` client.
- Use standard-library argument parsing, environment access, time, paths, and JSON.
- Use plain functions, dictionaries, lists, and local variables.
- Do not add classes, dataclasses, enums, protocols, registries, or an event hierarchy.
- Do not introduce a generic logging, tracing, configuration, or artifact abstraction.
- Do not add a tool, loop, history, iteration counter, concurrency, or asynchronous code.
- Do not use `previous_response_id` or the Conversations API.
- Do not add automated tests.
- Do not add an HTTP API, Web UI, database, package directory, or new dependency.

A small helper function is acceptable when it removes direct duplication, such as
appending one JSONL event. It must not become a framework for future imagined needs.

## Manual Acceptance Scenario

### Setup

Provide valid local values:

```text
OPENAI_API_KEY=...
MODEL_NAME=...
```

### Run

```text
uv run --env-file .env deep_research.py \
  "Explain in three concise bullets how a trace helps debug an AI agent."
```

### Verify Success

Confirm that:

1. the terminal shows the model request and final answer;
2. exactly one `model.request.started` event exists;
3. exactly one `model.response.completed` event exists;
4. no tool, history, or iteration event exists;
5. every trace line is valid JSON;
6. the serialized provider response has an ID, model, status, output, and usage when the
   API supplies usage;
7. `report.md` contains the final answer;
8. the trace ends in `run.completed`; and
9. the process exits successfully.

### Verify Configuration Failure

Run without `MODEL_NAME` and confirm:

- a concise error is written to standard error;
- no API request is attempted;
- the process exits unsuccessfully.

## Completion Criteria

The specification may become `Verified` when:

- both manual scenarios pass;
- Ruff and mypy pass for `deep_research.py`;
- the code remains a direct, readable single-file script;
- the trace and report are manually inspected;
- the implementation makes exactly one Responses API call; and
- README, tech stack, and roadmap match the implemented behavior.

Only then may the project create the `v0.1.0` Git tag.

## Out of Scope

- function tools;
- Agent loops;
- manual conversation history;
- paper or web search;
- citations and evidence quality;
- explicit research planning;
- mid-run user input;
- token streaming;
- retries and checkpoints;
- context compaction;
- critique and report revision;
- parallel or multi-agent execution;
- automated tests or formal evaluation.
