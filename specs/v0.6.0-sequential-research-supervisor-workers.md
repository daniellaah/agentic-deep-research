# v0.6.0 — Sequential Research Supervisor and Workers

## Status

Released

## Learning Question

What becomes observable and adaptable when one Research Supervisor repeatedly decides the
next bounded research task from application-owned state, while isolated Research Workers retain
the existing custom function-tool loop?

## Problem and Rationale

Release 0.5.0 creates one immutable `ResearchPlan` before any research begins. Every task is
chosen without seeing tool results, so the runtime cannot pursue a newly discovered lead, avoid
work made unnecessary by an earlier result, or change direction after an unproductive search.
The fixed planner and sequential task executor make this limitation easy to observe, but naming
each model call as an Agent or adding a generic Agent harness would not change it.

Release 0.6.0 replaces the static Plan stage with one adaptive research subsystem. A Research
Supervisor observes the approved `ResearchBrief`, completed worker results, and remaining worker
budget. On each turn it returns one validated `next_tasks` list containing zero or one
`ResearchTask`. One task starts one Research Worker with fresh Responses API history; an empty
list finishes Research. The worker uses the existing bounded Tavily and arXiv function-tool loop,
returns final Markdown notes, and then ends. The application records the task and notes in
`ResearchState` before asking the supervisor to decide again.

Two real manual runs exposed a Supervisor-specific structured-output failure: the response ended
inside generated JSON while the other structured stages completed normally. The Pydantic schema
was valid, but its narrative `decision_summary` did not control later behavior and the nullable
nested task represented a simple two-way choice indirectly. This release therefore narrows the
decision to the smallest useful control value. It does not add retries, JSON repair, fallback
decisions, or provider-specific recovery logic.

A later real run confirmed that the smaller decision schema completes successfully, then exposed
a separate task-bounding failure. The Supervisor delegated a report-sized task with page-length
and multi-source requirements. The Worker consequently accumulated long search results across
its manually replayed history until a later request exceeded the model's token-per-minute limit.
This was not a Pydantic failure. It showed that structural validation alone does not bound the
semantic size of a task and that the harness must own smaller search-result and tool-call budgets.
The release therefore describes task completion as narrow `evidence_targets`, not open-ended
report completion criteria, and reduces per-Worker research limits before adding retries or
context compaction.

Further real runs exposed a different Worker completion failure. A fixed 4,000-token Worker
output limit failed repeatedly, one 8,000-token run completed, and a later 8,000-token run again
ended without final notes after the tool budget was exhausted. The official Responses API
reference states that `max_output_tokens` includes both visible output and reasoning tokens, so a
fixed application limit does not reserve space for visible Worker notes and varies in effect by
configured model. Release 0.6.0 therefore retains the small fixed Supervisor limit but omits an
application-set Worker output limit. The visible harness budgets remain the Worker turn limit,
tool budget, result count, and per-result text limit. Free-text response extraction distinguishes
an incomplete or refused response from a completed response with empty text instead of
collapsing all three cases into one error. See the official
[Responses API reference](https://developers.openai.com/api/reference/cli/resources/responses/methods/create).

The official OpenAI SDK automatically retries eligible transient failures by default. That
provider behavior would contradict this release's explicit no-retry failure contract and hide
additional API attempts from the visible application harness. Release 0.6.0 therefore constructs
the `OpenAI` client with `max_retries=0`. A failed API request reaches the existing top-level
failure boundary without an SDK-owned or application-owned retry. See the official
[rate-limit guidance](https://developers.openai.com/api/docs/guides/rate-limits#retrying-with-exponential-backoff).

The application, rather than either model role, owns control flow, state mutation, budget
enforcement, and result merging. Scope and Write-Critic-Revise remain deterministic outer
workflow stages. Clarification, brief creation, writing, criticism, and revision are model calls,
but they are not renamed as Agents because they do not own an adaptive loop or tool policy.

The control relationship follows the manager pattern described by the
[OpenAI orchestration guide](https://developers.openai.com/api/docs/guides/agents/orchestration#choose-the-orchestration-pattern):
the supervisor remains in control while specialists act as bounded capabilities. This release
implements that relationship directly with the Responses API. It does not use an Agents SDK
handoff, transfer the user conversation to a worker, or register the worker as a provider-hosted
tool. The application invokes a worker only after validating a supervisor decision.

The release is intentionally sequential. Its learning objective is the nested control structure:
one application-owned supervisor loop delegates to separate worker tool loops. Parallel workers,
durable state, structured tracing, and output evaluation remain later mechanisms.

## Architectural Decision

The complete system is a hybrid of deterministic workflow and adaptive multi-agent research:

```text
deterministic Scope workflow
    -> approved ResearchBrief
    -> adaptive Research Supervisor loop
       -> validated next task or finish decision
       -> one isolated Research Worker tool loop
       -> application-owned result merge
       -> observe updated state and repeat or finish
    -> deterministic Write-Critic-Revise workflow
    -> final Markdown report
```

The architecture has these ownership boundaries:

- **Scope workflow** owns clarification, brief construction, local user input, revision, and
  explicit approval. It returns one immutable approved `ResearchBrief`.
- **Research Supervisor** owns only the model-directed research policy: choose one next task or
  decide that research should finish.
- **Research Worker** owns only one delegated task and its private, bounded search-tool history.
  A worker cannot create another worker, change the brief, or decide that the whole research run
  is complete.
- **Application runtime** owns `ResearchState`, decision validation, worker invocation, result
  merging, counters, hard limits, stopping, failures, and terminal output.
- **Report workflow** owns presentation of completed research through the existing explicit
  Write, Critic, and Revise calls.

There is no peer-to-peer routing, worker-to-worker communication, shared mutable model context,
generic `AgentDefinition`, base Agent class, orchestration framework, or artifact-handoff layer.

## Confirmed Architecture Choices

This release fixes three architecture choices:

1. **Structured supervisor decisions instead of a delegation function tool.** Each supervisor
   turn returns a validated list containing zero or one `ResearchTask`, and the application
   invokes the worker when that list contains a task. This keeps state ownership and control flow
   explicit. Registering a worker as a custom function tool would demonstrate a more literal
   nested tool call, but it would mix orchestration dispatch with the existing external
   research-tool layer.
2. **Strict worker context isolation.** A worker receives the approved brief and only its
   delegated task. It does not receive earlier worker notes. The supervisor sees all completed
   results, but uses them only to choose the next direction and avoid duplication. Every new task
   must remain independently answerable from the approved brief and fresh Worker searches; the
   supervisor does not copy earlier notes, URLs, source lists, or identifiers into the task.
3. **An application-owned stop at four workers.** After the fourth successful worker, Research
   stops successfully without a fifth supervisor call. A finish-only fifth call would add a model
   request after no further action is possible.

These choices keep the first supervisor-worker release bounded and directly inspectable.

## User-Visible Behavior

The CLI continues to accept one positional research question, then runs five top-level stages:

1. **Scope** creates and obtains approval for a validated `ResearchBrief` using the release 0.5.0
   bounded interaction.
2. **Research** repeatedly asks the supervisor to delegate one worker or finish, runs delegated
   workers sequentially, and combines successful worker notes.
3. **Write** drafts a report from only the approved brief and combined worker notes.
4. **Critic** reviews the draft against those same inputs.
5. **Revise** produces the final Markdown report.

There is no `Plan` stage, immutable `ResearchPlan`, plan display, plan approval, or fixed task
count chosen before research. After Scope approval, the user does not interact with the run.

Within Research, the terminal shows each supervisor decision in order. A decision containing one
task shows that complete task before the worker starts. Worker progress shows its one-based
number, task title, model turns, tool calls, remaining tool budget, completion, and final notes.
An empty decision shows that Research is finished. If the application reaches the hard worker
limit, it shows an application-owned budget stop instead of requesting another worker.

The final report remains non-empty Markdown and should satisfy the approved brief to the extent
supported by returned notes. Acceptance for this release verifies system behavior, state flow,
Agent loops, limits, and stopping; it does not score research quality, factual correctness,
source quality, citation accuracy, or semantic completeness.

## Runtime Flow

```text
question
→ load and validate configuration
→ run the release 0.5.0 Scope workflow
→ obtain and render one approved ResearchBrief
→ initialize application-owned ResearchState with no results
→ Research
    → render current ResearchState for the supervisor
    → Supervisor decision call(state, SupervisorDecision schema)
    → validate the complete decision against current state and limits
    → print the decision
    → if next_tasks is empty
        → require at least one completed worker result
        → record the application-owned supervisor-finish reason
        → leave the supervisor loop
    → if next_tasks contains one task
        → assign the next one-based worker number
        → build worker input from only the approved brief and delegated task
        → start one fresh Research Worker history
        → run the existing bounded function-tool loop
        → collect non-empty final Markdown notes
        → append one compact task result to ResearchState
        → print the worker notes
        → if the worker limit has been reached
            → record an application-owned budget stop
            → leave the supervisor loop
        → otherwise render updated state and request the next supervisor decision
→ render and print combined research notes in worker completion order
→ Write(approved brief + combined research notes)
→ print the draft
→ Critic(approved brief + combined research notes + draft)
→ print the critique
→ Revise(approved brief + combined research notes + draft + critique)
→ print the final Markdown report
```

Each supervisor decision is a separate stateless structured request built from the complete
current application state. Supervisor response items are not replayed between decisions. Each
worker has its own manually managed Responses API history, which ends when that worker returns
notes. Neither supervisor response history nor worker transcripts enter another worker or the
report workflow.

## Supervisor Decision Contract

Every supervisor call returns exactly this Pydantic model shape:

```text
SupervisorDecision
└── next_tasks: list[ResearchTask] with 0 or 1 item
    ├── title: string
    ├── research_question: string
    └── evidence_targets: list[string]
```

The application enforces these invariants:

- every field is required and extra fields are forbidden;
- `next_tasks` contains zero or one item;
- the first valid decision must contain exactly one task because Research cannot complete without
  at least one worker result;
- no decision is requested after the hard worker budget is exhausted; and
- a validated task is immutable after the application accepts the decision.

`ResearchTask` uses these field bounds:

- `title` contains 1 through 100 characters;
- `research_question` contains 1 through 600 characters; and
- `evidence_targets` contains 1 through 3 items of 1 through 200 characters each.

The supervisor instructions require delegated tasks to be focused, independently researchable,
within the approved brief, useful given prior results, and non-duplicative of completed tasks.
The research question must be one concise sentence. Each evidence target identifies one small,
observable fact, comparison, example, or source-type requirement that the Worker can satisfy with
a few focused searches. A task focuses on one primary subject or one direct comparison. When a
brief requests several examples, systems, or case studies, the Supervisor delegates them across
successive Workers instead of bundling a survey and cross-example synthesis into one task. A task
must not request a page or word count, a complete report, multiple report sections, a broad
taxonomy plus examples and recommendations, or more than three distinct sources. Earlier results
inform task selection but must not be copied into the task as notes, URLs, source lists, paper
identifiers, or a narrative summary. An empty list after at least one result means that no
additional bounded task is useful. Those semantic qualities are instruction-level expectations
in this release. The application validates structure and state consistency but does not use
another model call, embedding search, or heuristic scorer to judge them.

## ResearchState Contract

`ResearchState` is a small application-owned in-memory dictionary, not a model-generated
Pydantic object or a named class. It contains only:

```text
ResearchState
├── approved_brief: rendered string
├── worker_results: ordered list[ResearchResult]
│   ├── worker_number: application-assigned integer
│   ├── task: validated ResearchTask
│   └── notes: non-empty Markdown string
└── stop_reason: null | application-owned string
```

The state begins with the rendered approved brief, an empty result list, and no stop reason. Only
the application mutates it. A result is appended only after one worker returns non-empty notes
successfully. Worker numbers are assigned contiguously from one and list order is completion
order, which is also delegation order in this sequential release. The worker limit is one
constant, and the current worker number and remaining budget are derived from
`len(worker_results)` rather than stored as duplicate mutable state.

Before every supervisor call, the application renders one deterministic state view containing:

- the complete approved brief;
- the fixed worker limit and derived workers remaining;
- every completed worker number and task; and
- every completed worker's final notes.

The rendered state excludes the original question, clarification artifacts, approval commands,
superseded briefs, supervisor raw Responses, worker raw Responses, worker tool-call payloads, and
private worker histories. Because at most four workers run, v0.6.0 sends all completed notes to
the supervisor without summarization or context compaction.

When the supervisor returns an empty task list, the application stores the fixed reason `Research
Supervisor selected no next task.` When the fourth worker completes, the application stops
Research with the fixed reason `Research worker limit reached.` and does not make another
supervisor request. Either stop is a successful bounded completion, not an exception, provided at
least one worker result exists.

## Research Worker Contract

A decision with one task creates exactly one Research Worker invocation. A worker receives only:

- the complete rendered approved brief;
- its application-assigned worker number;
- the delegated task title;
- the delegated research question; and
- the delegated evidence targets.

The worker does not receive another worker's notes, remaining global worker budget, Scope
artifacts, report artifacts, or a shared conversation. The delegated task must stand alone: the
supervisor may choose its direction from prior findings but must not relay earlier evidence or
source details through the task.

Each worker starts a fresh ordered Responses API history and runs the existing research Agent
loop. It may call only the existing Tavily web search and arXiv paper search tools. It returns one
non-empty Markdown notes string after it stops requesting tools or after the application forces a
final-notes turn because its tool budget is exhausted.

The application wraps the validated task and returned notes as one plain `ResearchResult` entry.
This is ordinary application state, not a handoff protocol or new artifact abstraction. The
worker's complete history is discarded after its final notes are collected.

Combined research notes are rendered deterministically in result order. Each section includes
the worker number, task title, research question, evidence targets, and notes so the report
workflow retains task-to-result association. The report stages do not receive supervisor
decisions or the final stop reason.

## Responses API Contract

Scope retains the release 0.5.0 synchronous `client.responses.parse` calls, Structured Outputs
schemas, refusal handling, approval rules, `store=False`, and application-owned input boundaries.
The CLI constructs its one official SDK client with `max_retries=0`, so no Scope, Supervisor,
Worker, or report request is retried below `llm_call`.

Every supervisor decision uses one synchronous `client.responses.parse` request with:

- supervisor-specific `instructions`;
- the deterministic current-state rendering as explicit input;
- `text_format=SupervisorDecision`;
- a fixed 4,000-token Supervisor output limit;
- `store=False`; and
- no custom tools, `tool_choice`, `previous_response_id`, or Conversation.

The request must produce a completed, non-refusal response whose `output_parsed` is one validated
`SupervisorDecision`. The runtime does not fall back to free text, infer a task or stop decision,
repair the decision with another model call, reuse an earlier decision, or invent a default task.

The supervisor loop is application-owned even though each individual supervisor request is a
structured call rather than a function-tool turn. The loop becomes agentic because the model's
validated `next_tasks` list determines whether the application dynamically delegates another
independent worker or stops. The worker remains the tool-using Agent introduced in release 0.3.0.

Each worker preserves the existing manual Responses API history contract:

1. initialize one history with its worker input;
2. append every response output item in original order;
3. execute returned custom function calls synchronously in response order;
4. append linked `function_call_output` items; and
5. replay the complete worker history on its next turn.

While worker tool budget remains, requests use the configured model, Research instructions,
existing custom tools, `tool_choice="auto"`, and `store=False`. After tool budget exhaustion, the
next worker request uses the same instructions and tools with `tool_choice="none"`, plus the
existing application-owned final-notes input. No worker uses provider-managed conversation state.
Every Supervisor model request uses a fixed 4,000-token output limit. Worker requests omit
`max_output_tokens` and use the configured model's default because that parameter limits the sum
of visible output and reasoning tokens rather than reserving visible-note capacity. Scope and
report-stage output budgets remain unchanged in this release. This release does not set a model-
specific reasoning effort.

Each search-tool result list contains at most three entries. Tavily content and each arXiv
summary are truncated by the application to at most 2,000 characters before entering Worker
history. Titles, authors, dates, and URLs remain intact. This is a deterministic context-input
boundary, not model-generated summarization or a new compression stage.

Write receives only the approved brief and deterministically combined research results. Critic
adds the draft, and Revise adds the critique. Those stages do not receive the original question,
Scope history, supervisor raw responses, stop reason, worker histories, or raw tool results
independently of the final worker notes.

`llm_call` remains the thin provider boundary. Structured output remains mutually exclusive with
tools and tool choice, all requests remain synchronous, and all paths return the official SDK
`Response` without wrapping it.

Both structured and free-text extraction require a completed response and reject refusal content.
When a response is incomplete, the application includes the available `incomplete_details.reason`
in its concise fatal error. A completed required free-text response must still contain non-empty
`output_text`.

## Instruction Contract

All model instructions and application-owned model-input constants remain plain strings in
`agent_instructions.py`:

- **Scope instructions** retain the complete release 0.5.0 clarification, brief creation, and
  optional brief revision behavior. Brief creation and revision explicitly define
  `output_requirements` and `success_criteria` as requirements for the eventual final Markdown
  report, never requirements to produce another ResearchBrief.
- **Supervisor instructions** return only one `SupervisorDecision` from the current state. The
  first decision must contain exactly one task. Each later decision contains zero or one task,
  uses prior results only to choose direction and avoid unnecessary or duplicate work, respects
  the complete approved brief, and returns an empty list when no additional bounded task is
  useful. Each task contains one narrow question about one primary subject or direct comparison
  and one through three evidence targets. Multiple examples or case studies are distributed
  across successive Workers; one task must not request report-length output, multiple report
  sections, a cross-example survey, or more sources than the bounded Worker can investigate. The
  supervisor must not copy earlier evidence into a task, conduct research, call search tools,
  write report content, change the brief, address the user, claim approval, or expose private
  reasoning.
- **Research Worker instructions** retain the existing Research behavior while identifying the
  role as one isolated worker. The worker investigates only its delegated task, respects the
  approved brief, grounds notes in returned tool evidence, preserves useful source URLs, and does
  not plan later tasks or decide whether the overall run should finish.
- **Write, Critic, and Revise instructions** retain their release 0.5.0 responsibilities, but
  receive combined worker results rather than notes from an immutable plan.

The static Planning instructions are no longer used at runtime. No instruction may request or
claim to expose private chain-of-thought.

## CLI Contract

The invocation shape remains:

```text
uv run deep_research.py "Research the impact of AI coding agents."
```

The positional question and these environment variables remain required:

- `OPENAI_API_KEY`;
- `MODEL_NAME`; and
- `TAVILY_API_KEY`.

`MODEL_NAME` must support the required Structured Outputs schemas and existing custom function
tools. `python-dotenv` continues to load the repository-root `.env`. Missing input or
configuration makes no external request and does not prompt for Scope input.

Progress uses the fixed top-level stage labels `Scope`, `Research`, `Write`, `Critic`, and
`Revise`, including their one-based positions out of five. Successful output makes visible:

- every release 0.5.0 Scope boundary through explicit approval;
- each supervisor decision number and whether it contains one task or finishes;
- the complete task whenever a decision contains one;
- each worker number, task title, model turn, tool activity, and remaining tool budget;
- every completed worker's notes;
- the supervisor or hard-limit stop reason;
- combined research notes with task association; and
- the draft, critique, and final Markdown report.

The CLI does not show a `Plan` stage or ask for research decisions after brief approval.

## Limits and Stopping Contract

Scope retains all release 0.5.0 interaction limits. Let `R` be the number of brief revisions,
where `R` is zero or one.

Research has these application-owned global limits:

- at most 4 supervisor decision requests;
- at most 4 successfully completed Research Workers;
- exactly one worker may run at a time;
- at least one successful worker result is required before an empty `next_tasks` list is valid;
- the application stops Research immediately after the fourth successful worker without making
  a fifth supervisor decision.

Every worker independently has at most 6 Research model turns, 5 tool execution attempts,
and 3 results per tool call. Tavily content and arXiv summaries are each limited to 2,000
characters before they enter model history. Counters and Responses history restart for every worker. Malformed,
unknown, failed, and budget-exceeding tool calls retain the release 0.5.0 behavior and count
against that worker's tool budget.

Let `W` be the number of successful workers and `S` the number of supervisor decisions. For a
successful run, `1 <= W <= 4` and `2 <= S <= 4`. If the supervisor finishes before the global
worker limit, `S = W + 1`. If four workers complete, `S = W = 4` and the application supplies the
hard-limit stop reason.

Each worker makes at least 1 and at most 6 Research requests under the effective tool
budget behavior. A successful run therefore makes:

- exactly `2 + R` Scope requests;
- `S` supervisor requests;
- between `W` and `6W` worker requests; and
- exactly 3 report-stage requests.

The absolute hard maximum is 34 model requests and 20 research-tool execution attempts. The
worker's six-turn guard remains a secondary safety bound. Every Supervisor request has a fixed
maximum of 4,000 output tokens. Worker requests use the configured model's default output limit;
their application-owned bounds are turns, tool attempts, result count, and per-result text size.

A valid empty `next_tasks` decision after at least one result and the application-owned
four-worker stop both continue to the report workflow. Cancellation, invalid state transition,
structured-output failure, fatal worker failure, or report failure stops the complete run. The
runtime does not skip a failed worker, retry it, ask the supervisor for a replacement, or produce
a partial report.

## Observability Contract

Live terminal output remains the complete observability mechanism. It shows the deterministic
outer workflow, every supervisor decision boundary, every isolated worker boundary, the worker
tool loops, central result merging, and the reason Research stops.

The CLI prints validated application-facing decisions, tasks, final worker notes, combined
research notes, draft, critique, and final report. It does not print raw structured JSON,
Pydantic representations, complete state serialization, prompts, secrets, complete Responses API
histories, raw tool payloads, or model reasoning items.

Tasks, worker notes, and stop reasons are application-facing outputs. They do not request, store,
reconstruct, or claim to expose private chain-of-thought. This release adds no structured trace,
event model, trace file, token accounting, cost accounting, or automated evaluation.

## Artifact Contract

Release 0.6.0 creates no run directory and writes no application output files. The approved
brief, `ResearchState`, supervisor decisions, worker notes, combined notes, draft, critique, and
final report remain in memory. The user-visible boundary values required by the observability
contract are printed in full.

## Failure Behavior

Missing input or configuration, any Scope or supervisor API error, an unsupported Structured
Outputs schema, a refusal, an incomplete structured or free-text response, a missing or invalid
parsed value, an empty `next_tasks` decision before any successful worker, any fatal worker error,
an empty required free-text output, or a later API error prints a concise fatal error and exits
nonzero.

Scope failures and cancellation retain release 0.5.0 behavior and stop before Research. A
supervisor failure stops before the proposed worker starts. A worker failure stops before its
result is merged, before another supervisor decision, and before report generation. Write,
Critic, or Revise failure stops at that stage.

There are no SDK-owned or application-owned API retries, schema-repair calls, fallback decisions,
inferred tasks, default first task, skipped or retried workers, fallback static plan, partial
report, or output file. Ordinary search-tool errors remain linked function outputs inside the
active worker and do not by themselves stop the run.

## Implementation Constraints

- Keep Scope, Pydantic boundary models, supervisor loop, worker tool loop, `ResearchState`, report
  workflow, CLI input, and terminal output in `deep_research.py`.
- Keep all model instruction and application-owned model-input constants in
  `agent_instructions.py` as plain strings without model calls, tools, state, validation, user
  input, or output post-processing.
- Keep custom search-tool definitions and implementations in `agent_tools.py`; update only
  project version metadata such as the arXiv `User-Agent` when implementing the release.
- Remove the runtime static Plan stage and do not call the release 0.5.0 planner. The obsolete
  `ResearchPlan` boundary and Planning instructions need not remain in the active runtime.
- Reuse Pydantic 2 for `SupervisorDecision` and nested `ResearchTask`. Represent delegation with
  one `next_tasks` list constrained to zero or one item. Do not add an action field, nullable
  nested task, decision summary, or cross-field validator.
- Name the bounded task requirements `evidence_targets`, not `completion_criteria`. Keep one
  through three targets and use Supervisor instructions to prohibit report-sized tasks rather
  than adding semantic validation or a quality Agent.
- Keep `ResearchState`, worker results, and Responses API histories as plain dictionaries and
  lists. Store only `approved_brief`, `worker_results`, and `stop_reason`; derive counters instead
  of storing duplicate mutable values. Do not add a state-management abstraction or persistent
  repository.
- Use `run_scope_workflow`, `run_research_supervisor_loop`, `run_research_worker`,
  `run_research_worker_loop`, `run_report_workflow`, and `run_deep_research` as the visible
  execution boundaries. Keep Supervisor decision requests, Worker lifecycle, Worker Agent loop,
  report workflow, and complete-system workflow distinct without introducing a generic runner,
  Agent registry, Agent configuration object, base Agent class, lifecycle interface, or routing
  framework.
- Use `request_*` for individual model decision boundaries, `build_*` for model inputs,
  `format_*` for pure text rendering, `require_*` for validated response extraction,
  `execute_*` for tool side effects, and `run_*` for workflows or loops. Keep `llm_call` as the
  deliberately thin provider boundary.
- Let `execute_worker_tool_call` own argument parsing, one research-tool execution, tool-error
  conversion, progress output, and construction of the linked `function_call_output`. Let
  `run_research_worker` own one Worker's visible lifecycle while the Supervisor loop remains the
  only place that appends its returned result to `ResearchState`.
- Preserve one thin `llm_call` provider boundary, direct synchronous Responses API calls,
  `store=False`, application-owned state, and the existing worker history replay behavior.
- Let `llm_call` accept an optional output-token limit. Apply a 4,000-token limit only to
  Supervisor requests. Omit an application-set output-token limit from Worker, Scope, and report
  requests.
- Build each supervisor input from the deterministic current-state rendering. Do not replay raw
  supervisor response items or use provider-managed conversation state.
- Start every worker with a fresh history and discard that history after final notes. Do not let
  workers read or mutate shared state or call other workers.
- Keep top-level Scope, Research, and report-workflow sequencing explicit in `run_deep_research`.
  Keep Write, Critic, and Revise calls explicit in `run_report_workflow`; do not introduce a
  workflow engine or Agents SDK.
- Construct the one official SDK client with `max_retries=0`. Do not allow SDK-owned retries or
  add an application retry loop.
- Add no runtime dependency, file output, persistence, concurrency, asynchronous code, retries,
  caching, streaming, hosted OpenAI tools, MCP, structured tracing, automated evaluation,
  automated tests, Ruff, or mypy.

## Manual Acceptance Scenario

With valid configuration and a Structured Outputs-compatible model, run:

```text
uv run deep_research.py "Research the impact of AI coding agents."
```

Across the clarification answers, establish a software-engineering audience, a recent time
horizon, and interest in measured productivity benefits, failure modes, and limitations. At the
first approval prompt enter `revise`, then provide this revision:

```text
Require at least one recent arXiv paper and one current web source, compare their evidence, and
cite the returned URLs in a concise Markdown report.
```

At the final prompt enter `approve`. Confirm that:

1. Scope, Research, Write, Critic, and Revise complete once in that order;
2. Scope retains the v0.5.0 bounded clarification, revision, and explicit approval behavior;
3. there is no Plan request, `Plan` progress stage, immutable plan, or plan approval prompt;
4. the first supervisor decision contains exactly one validated task;
5. every delegated task contains one narrow research question and one through three evidence
   targets, without a page count, report outline, or requirement for more than three sources;
6. exactly one worker starts for each one-item `next_tasks` list, workers run one at a time, and every
   worker starts with fresh Responses API history;
7. each worker uses only the approved brief and its delegated task, while every supervisor call
   receives the approved brief, remaining global worker budget, and all earlier completed task
