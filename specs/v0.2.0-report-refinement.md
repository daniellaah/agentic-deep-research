# v0.2.0 — Fixed Write-Critic-Revise Workflow

## Status

Released

## Learning Question

What becomes easier to observe and improve when report refinement is split into three
explicit model calls instead of asking one model call to write and self-review at once?

## Problem and Rationale

Release 0.1.0 can produce a complete report, but its single model call provides no visible
separation between drafting, critique, and revision. This release introduces deterministic
multi-call orchestration so a contributor can inspect what each fixed stage contributed
before the project adds an autonomous Agent loop.

The workflow deliberately uses no research tools or external evidence. The critic can
assess the draft's structure, reasoning, completeness, and compliance with the original
question, but it cannot verify factual accuracy, sources, or citations. Making that limit
explicit prevents report refinement from being mistaken for grounded research.

The implementation continues to use the synchronous Responses API. Each stage is a new,
stateless request with `store=False`; the application passes the required upstream text in
the next stage's `input` rather than using `previous_response_id` or a Conversation. The
Responses API accepts text input and exposes aggregated generated text through the SDK's
`response.output_text` property, so no new API mechanism or dependency is required.

The fixed draft-feedback-revision decomposition is also consistent with the mechanism studied by
the peer-reviewed
[Self-Refine paper](https://proceedings.neurips.cc/paper_files/paper/2023/file/91edff07232fb1b55a505a9e9f6c0ff3-Paper-Conference.pdf):
generate an initial output, produce feedback on that output, and refine it from the feedback. This
release adopts only one deterministic refinement pass and keeps its artifacts visible; it does not
claim that self-critique independently verifies facts.

## User-Visible Behavior

The CLI loads configuration, accepts one question, and runs three named stages in a fixed
order:

1. **Write** produces an initial report draft.
2. **Critic** evaluates the draft and returns actionable revision guidance.
3. **Revise** applies the useful guidance and returns the final report.

The terminal prints concise start and completion progress for every stage. A completion
message identifies the artifact written by that stage. After revision, the CLI prints the
final report, its path, and a run-completed message. It does not print the full draft or
critique because those remain inspectable as files.

## Runtime Flow

```text
question
→ load and validate configuration
→ write call(question)
→ validate draft and save draft.md
→ critic call(question + draft)
→ validate critique and save critique.md
→ revise call(question + draft + critique)
→ validate final report and save report.md
→ print final report and exit
```

This is fixed workflow orchestration, not an Agent loop. The application decides every
stage and transition before execution; the model cannot choose another action, repeat a
stage, call a tool, or change the stopping condition.

## Responses API Contract

`research_workflow` invokes `llm_call` exactly three times on a successful run. `main`
creates the client and invokes `research_workflow` once. `llm_call` remains the thin
provider boundary: it uses the synchronous `OpenAI` client, accepts stage-specific
instructions and text input, sets `store=False`, and returns the original SDK `Response`.

Every request contains:

- `model=MODEL_NAME`;
- stage-specific `instructions`;
- one explicit text `input`; and
- `store=False`.

The stages have these input boundaries:

- **Write** receives only the original question.
- **Critic** receives the original question and the complete draft.
- **Revise** receives the original question, complete draft, and complete critique.

Each response must contain non-empty `output_text`. The workflow does not pass raw Response
objects, response IDs, hidden state, or manually accumulated response items between calls.

The writer must produce only a Markdown report. The critic must produce only a concise,
actionable Markdown critique and explicitly limit its review to properties assessable from
the question and draft. The reviser must produce only the final Markdown report, preserve
sound draft content, apply useful critique, and avoid mentioning the workflow or critique.

## CLI Contract

```text
uv run deep_research.py \
  "Explain in three concise bullets how a trace helps debug an AI agent."
```

The question is required. `python-dotenv` loads the repository-root `.env`, while existing
process environment variables take precedence. `OPENAI_API_KEY` and `MODEL_NAME` are
required. Normal output goes to standard output; fatal errors go to standard error.

Progress uses the fixed stage labels `Write`, `Critic`, and `Revise`, including their
one-based position out of three. A successful run makes the following facts visible:

- which stage is running;
- when that stage produced non-empty output;
- where each artifact was written; and
- which text is the final report.

## Trace Contract

This release does not create `trace.jsonl` or another structured trace. The three Markdown
artifacts are the observable record of the deterministic workflow. Structured tracing
begins in release 0.3.0, when model-selected tool calls, repeated history transitions, and
stopping decisions introduce an Agent loop worth tracing.

## Artifact Contract

A successful run creates one unique directory under the repository-root `runs/` directory:

```text
runs/<run-id>/
├── draft.md
├── critique.md
└── report.md
```

`draft.md`, `critique.md`, and `report.md` contain the corresponding stage's exact
`response.output_text`. The run directory is rooted at the repository, independent of the
caller's current working directory. Artifact files are UTF-8 text.

The run directory is created only after the Write stage returns non-empty output. Each
artifact is written before the next model stage begins. Therefore a failure after Write may
leave `draft.md`, and a failure after Critic may leave both `draft.md` and `critique.md`.
These partial artifacts expose completed work without implying that the run succeeded.
Configuration failures, Write API failures, and empty Write output create no run directory.
An artifact-write failure may leave an incomplete run directory or file.

## Failure and Stopping Behavior

The command fails for missing input or configuration, any API error, empty stage output, or
an artifact-write error. It reports a concise fatal error to standard error and exits with a
nonzero status.

The workflow stops immediately at the failing stage, makes no later model calls, and
performs no retries. It makes exactly three model calls on success and at most three calls
on any run. Partial stage artifacts follow the artifact contract above.

## Implementation Constraints

- Keep all runtime behavior in `deep_research.py`.
- Use the synchronous OpenAI Responses API directly.
- Keep `llm_call` as a thin wrapper that returns the SDK `Response`.
- Use direct functions, strings, and standard-library utilities, plus `python-dotenv`.
- Keep the three stage calls explicit in `research_workflow`; do not generalize them into
  a workflow engine, stage registry, class hierarchy, or retry abstraction.
- Keep `main` responsible for CLI parsing, configuration, client construction, final
  output, and top-level error handling; it invokes `research_workflow` once.
- Use one client and one configured model for all three calls.
- Do not add dependencies, tools, loops, response history, structured trace events,
  concurrency, asynchronous code, provider abstractions, or automated tests.

## Manual Acceptance Scenario

Provide valid `OPENAI_API_KEY` and `MODEL_NAME`, then run:

```text
uv run deep_research.py \
  "Explain in three concise bullets how a trace helps debug an AI agent."
```

Confirm that:

1. Write, Critic, and Revise start and complete once in that order;
2. exactly three model requests are made;
3. the terminal prints only the final report in full;
4. `draft.md`, `critique.md`, and `report.md` contain non-empty stage outputs;
5. the final report follows the requested three-bullet format;
6. the run directory does not contain `trace.jsonl`; and
7. the process exits successfully.

Then run without `MODEL_NAME` and confirm that the command reports a concise error, makes
no API request, creates no run directory, and exits unsuccessfully.

## Completion Criteria

The specification may become `Verified` after both manual scenarios pass, Ruff and mypy
pass, exactly three Responses API calls are confirmed, all three artifacts are inspected,
and the README, changelog, tech stack, roadmap, and project version match the
implementation. Only then may the project create the `v0.2.0` tag.

## Out of Scope

Research tools, web or paper search, factual or citation verification, source grounding,
Agent loops, model-selected actions, response history, `previous_response_id`, the
Conversations API, structured tracing, planning, clarification, retries, streaming,
checkpoints, concurrency, multi-agent execution, and automated evaluation.
