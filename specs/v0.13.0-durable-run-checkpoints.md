# v0.13.0 — Durable Run Checkpoints and Resume

## Status

Draft

## Learning Question

What becomes recoverable when every stable workflow boundary commits a versioned application
checkpoint that can resume the same run without repeating completed model or tool work?

## Problem and Rationale

Release 0.12.0 persists evidence and claim artifacts but the orchestration state remains in memory.
A process failure loses the active Supervisor, Worker, session, budgets, and report-stage cursor.
Release 0.13.0 makes one run durable without adopting a workflow framework.

LangGraph documents checkpointed state as the foundation for durable execution, fault recovery,
human-in-the-loop, state inspection, and replay from a successful step; see its official
[persistence guide](https://docs.langchain.com/oss/python/langgraph/persistence) and
[runtime overview](https://docs.langchain.com/oss/python/langgraph/overview). Its interrupt guide
also requires a durable production checkpointer and stable thread ID for pause and resume; see
[Interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts). This release implements
the minimum equivalent application-owned contract directly.

## Primary Mechanism

Introduce one stable `run_id`, a versioned checkpoint manifest, atomic state commits at explicit
workflow boundaries, and `--resume`/`--inspect` commands. A checkpoint stores public application
state and artifact references, never credentials or private reasoning.

## Architectural Decision

```text
complete logical step
    -> persist its artifacts
    -> atomically commit next workflow cursor and state version
    -> emit progress
process stops
    -> load and validate latest committed checkpoint
    -> reconstruct clients from current credentials
    -> continue at next uncompleted logical step
```

Checkpoints occur after brief approval, Supervisor decision, model response classification, each
committed tool result, context summary replacement, terminal Worker result, draft, citation map,
critique, revision, and terminal run status.

## User-Visible Behavior

Every run prints its ID and current checkpoint sequence. `--inspect` reports status, cursor,
budgets, artifacts, and pending action without invoking a model. `--resume` continues a paused or
interrupted run. Brief approval becomes a durable pause rather than terminal-only input state.

## Runtime Flow

1. Create a run manifest with schema and application versions.
2. Assign monotonic checkpoint sequence numbers.
3. Persist step artifacts before committing the cursor that declares the step complete.
4. Write checkpoints atomically and retain the prior valid checkpoint.
5. On resume, validate manifest, hashes, invariants, provider/model identity, and artifact presence.
6. Reconstruct the selected client from environment credentials.
7. Resume at the first uncompleted logical step without replaying completed work.
8. Persist terminal completed, failed, or cancelled status.

## State Ownership Contract

The checkpoint includes approved brief, ResearchState, AgentRunRequest, serializable AgentRunState,
budget counters, source and evidence references, session summary, report cursor, status, pending
approval, and artifact hashes. SDK clients, API keys, provider Response objects that cannot be
safely serialized, and private reasoning are excluded. Required opaque replay items must use the
SDK's supported public serialization or cause an explicit unsupported-resume state.

Each checkpoint records `application_version`, `checkpoint_schema_version`,
`evidence_schema_version`, `claim_schema_version`, provider, exact model, instruction version, and
tool-schema version. Incompatible versions fail closed; silent field loss is forbidden.

## Persistence and Artifact Contract

Store a monotonic checkpoint manifest and content-addressed step artifacts under
`runs/<run-id>/checkpoints/`. A small atomic `latest.json` pointer identifies the newest committed
sequence; prior valid checkpoints remain available for recovery inspection. Generated checkpoints
are ignored by Git and use only validated run-derived paths.

## Idempotency and Replay Contract

This release avoids replay of completed logical steps through the cursor and committed artifacts.
Full external-effect idempotency and classified retry arrive in v0.14. A resumed operation whose
completion is ambiguous stops with `recovery_required` rather than guessing or duplicating work.

## Security and Trust Boundary

Checkpoint paths are run-ID derived and cannot be supplied as arbitrary filesystem paths. Secrets
are reloaded from environment and never persisted. Evidence remains untrusted. Inspect output
redacts content and errors that may contain credentials.

## CLI Contract

```text
uv run deep_research.py "Question"
uv run deep_research.py --inspect <run-id>
uv run deep_research.py --resume <run-id>
uv run deep_research.py --cancel <run-id>
```

Exactly one mode is allowed. Resume requires the same provider and model unless a future migration
spec explicitly permits change.

## Observability Contract

Print run ID, checkpoint sequence, cursor, pause reason, resume source, schema versions, and final
status. Do not print serialized history or evidence content.

## Evaluation Contract

Deterministic crash-injection tests cover every checkpoint boundary, atomic-write interruption,
corrupt latest checkpoint fallback, missing artifact, incompatible schema, wrong provider/model,
cancel/resume rules, approved-brief pause, and absence of duplicate model/tool work.

## Failure and Stopping Behavior

Invalid or incompatible checkpoints fail without mutation. Cancellation commits a terminal state;
resuming a cancelled or completed run is rejected. A paused run may wait indefinitely. Crash after
artifact write but before cursor commit is recovered conservatively from the previous checkpoint.

## Implementation Constraints

Use standard-library serialization and atomic files before adding a database or workflow engine.
Do not introduce concurrency. Keep the explicit orchestration functions visible.

## Manual Acceptance Scenario

Run through one Worker and terminate the process after a committed source read, after a context
summary, and after the draft in three separate trials. Resume each run, confirm completed calls are
not repeated, budgets remain monotonic, citations still resolve, and the final artifacts match a
non-interrupted control run. Inspect and cancel a paused approval run.

## Completion Criteria

Crash injection, resume, inspection, cancellation, artifact-integrity, real-provider, and retained
regression scenarios pass. A run can cross process boundaries without losing or duplicating
committed logical work.

## Out of Scope

Distributed locks, multiple simultaneous resumptions, remote databases, provider migration,
automatic retry, compensation, parallel Workers, time travel UI, and cross-version migration.

## Known Limitations and Deferred Decisions

Filesystem durability is single-host. Ambiguous external calls still require intervention.
Idempotency, retry, and failure-aware Supervisor policy are deferred to v0.14.
