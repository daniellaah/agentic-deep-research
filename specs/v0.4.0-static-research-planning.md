# v0.4.0 — Static Structured Research Planning

## Status

Released

## Learning Question

What becomes easier to observe and control when one validated, immutable research plan is
created before the existing tool-using Agent begins its work?

## Problem and Rationale

Release 0.3.0 gives one research Agent the complete user question and lets it decide what to
search inside a bounded function-tool loop. Its searches are visible, but the intended
coverage is not known before research starts, separate lines of inquiry are not named, and
the final notes do not show which part of the question each search was meant to answer.

Release 0.4.0 adds one planner call before research. The planner returns a bounded
`ResearchPlan` whose ordered `ResearchTask` values state what to investigate and how to
recognize adequate coverage. Pydantic validates that model-generated boundary before any
research tool can run. The application then invokes the existing research Agent once per
task, sequentially, and keeps every task's notes associated with that task for final report
synthesis.

This release establishes a deliberately static baseline. The plan is produced once and is
never revised in response to tool results, missing evidence, contradictions, or failures.
Completion criteria guide each research Agent and make intended coverage inspectable; they
are not automatically scored or proven satisfied. Those limitations make the need for a
later adaptive supervisor observable without introducing it here.

The structured planner design follows the
[OpenAI Structured Outputs guide](https://developers.openai.com/api/docs/guides/structured-outputs),
which documents Pydantic schemas with `client.responses.parse`, `text_format`, and
`response.output_parsed`. The planner continues to use the
[Responses API](https://developers.openai.com/api/reference/cli/resources/responses/methods/create)
with application-owned state and `store=False`.
That API contract defines `tool_choice="none"` as preventing tool calls and producing a
message instead. The budget-exhausted Research turn therefore uses that request control
instead of switching to a second instruction set.

## User-Visible Behavior

The CLI accepts one question and runs five stages:

1. **Plan** creates, validates, and prints one research plan.
2. **Research** executes every plan task in order with the existing tool-using Agent.
3. **Write** drafts a report from the question and combined research notes.
4. **Critic** reviews the draft against those same inputs.
5. **Revise** produces the final Markdown report.

For every numbered task, the printed plan shows its title, research question, and completion
criteria. Research progress identifies the active task by number and title before showing
that task's model turns and tool calls. The workflow continues immediately after printing
the plan; there is no confirmation, edit, or approval prompt.
After each model-facing stage completes, the CLI prints its full result in a labeled,
plain-text section: task-scoped research notes, combined research notes, draft, critique,
and final report.

The final report synthesizes evidence across tasks. It is not required to preserve the
plan's task headings, but it must answer the original question, cite returned source URLs,
distinguish evidence from inference, and state important limitations.

## Runtime Flow

```text
question
→ load and validate configuration
→ Plan call(question, ResearchPlan schema)
→ require one parsed and validated ResearchPlan
→ print the immutable plan
→ for each ResearchTask in list order
    → build a task input from the original question and current task
    → start a fresh ordered Responses API history for that task
    → run the existing bounded research Agent loop
    → associate the returned notes with the current task
    → print the task-scoped research notes
→ combine note text from all task results in plan order
→ print the combined research notes
→ Write(question + combined research notes)
→ print the draft
→ Critic(question + combined research notes + draft)
→ print the critique
→ Revise(question + combined research notes + draft + critique)
→ print the final Markdown report
```

The planner is one model call, not an Agent loop. Research tasks are separate sequential
invocations of the same `agent_loop` implementation, not separate named agents or workers.
Each task begins with fresh response history and does not receive another task's transcript
or notes. The planner must therefore make tasks self-contained and minimize overlap.

## Research Plan Contract

The planner returns exactly these two Pydantic model shapes:

```text
ResearchPlan
└── tasks: list[ResearchTask]
    ├── title: string
    ├── research_question: string
    └── completion_criteria: list[string]
```

The application enforces these invariants:

- every field is required and extra fields are forbidden;
- surrounding whitespace is stripped from strings;
- `tasks` contains 1 through 4 tasks in execution order;
- each `title` contains 1 through 100 characters after stripping;
- each `research_question` contains 1 through 600 characters after stripping; and
- each task has 1 through 3 completion criteria, each containing 1 through 240 characters
  after stripping.

List position is the task identity for this release. The application numbers tasks from
one when printing the plan and when collecting notes; the model does not generate task IDs.
The planner instructions require tasks to be focused, non-duplicative, independently
researchable, and jointly sufficient for the original question. A completion criterion
describes evidence or coverage to seek, not a hidden reasoning step or a guarantee that the
criterion will be met.

After validation, the plan is immutable. The runtime must not add, remove, reorder, rewrite,
or regenerate tasks. The plan remains a Pydantic value at the model boundary; task results
and Responses API histories remain plain lists and dictionaries.

## Responses API Contract

The planner uses the configured model in one synchronous `client.responses.parse` request
with:

- planner-specific `instructions`;
- the original question as explicit input;
- `text_format=ResearchPlan`;
- `store=False`; and
- no tools, `previous_response_id`, or Conversation.

The request must produce a non-refusal, complete response whose `output_parsed` is a
validated `ResearchPlan`. The configured `MODEL_NAME` must support the generated Structured
Outputs schema. The runtime does not fall back to JSON mode or an unvalidated text plan when
the model is incompatible, refuses, returns an incomplete response, or produces no parsed
value.

`llm_call` remains the thin provider boundary and supports optional structured-output and
tool-choice parameters. Structured output is mutually exclusive with tools and tool
choice, and tool choice is valid only when tools are supplied. The planning path calls
`responses.parse`, while ordinary text and research-tool paths continue to call
`responses.create`. All paths return the original SDK `Response` object.

For each task, the existing research Agent receives one user input containing only:

- the original question;
- the current task number and title;
- the task's research question; and
- the task's completion criteria.

The task loop preserves the release 0.3.0 Responses API history contract: append every
response output item in order, execute all returned custom function calls synchronously in
response order, append linked `function_call_output` items, and replay the complete history
for that task. While tool budget remains, Research requests use `store=False`, the custom
Tavily and arXiv function tools, and `tool_choice="auto"`. After the tool budget is
exhausted, the next request uses the same Research instructions and tool definitions but
sets `tool_choice="none"`. Its request input is the complete task history plus one
application-owned user item directing the model to produce final notes from collected
evidence without requesting or imitating another tool call. The extra item is constructed
for that final request and is not added to the stored task history. No Research request
uses provider-managed conversation state.

`execute_research_plan` appends each successful notes string to a plain list in plan order
and returns the strings joined with blank lines. List position keeps each result associated
with its plan task during Research. Write, Critic, and Revise receive the original question
and that combined note text. They do not receive task numbers, task titles, research
questions, completion criteria, raw Response objects, or research transcripts.

## Instruction Contract

All model instruction and application-owned model-input constants live in the
repository-root `agent_instructions.py` file. That module contains plain string constants
only: it does not call the model, execute tools, own workflow state, or alter model output.
`deep_research.py` imports those constants and continues to own every model-call boundary
and all runtime behavior.

The instruction constants define these stage-specific responsibilities:

- **Plan:** return only one structured plan matching `ResearchPlan`. Tasks must be focused,
  non-duplicative, self-contained, independently researchable, and jointly sufficient for
  the original question. Completion criteria describe observable evidence or coverage.
  Planning must not answer the question, claim research has occurred, request tool calls,
  expose private reasoning, or produce a report outline.
- **Research:** investigate only the current task while using the original question for
  relevance. Select Tavily for current web sources and arXiv for papers when those source
  types are relevant, base findings on returned evidence rather than search queries, retain
  useful source URLs, identify limitations or uncertainty, and return Markdown research
  notes only. Research output must not contain greetings, tool-call syntax, process
  narration, follow-up questions, offers of additional work, or claims unsupported by tool
  results. It must not add a literal end marker after the notes. One separate
  budget-exhausted input tells the same Research stage to stop requesting tools and produce
  final notes using only evidence already present in the current task history. There is no
  separate Research synthesis instruction set.
- **Write:** answer the original question using only the combined research notes. Synthesize
  rather than concatenate, preserve useful URLs, distinguish evidence from inference, state
  important limitations, and return only the draft report. Do not introduce unsupported
  sources or claims, discuss the workflow, include conversational closing material, or add
  a literal end marker.
- **Critic:** inspect the draft against the original question and research notes for
  completeness, clarity, reasoning, source use, unsupported claims, limitations, and
  instruction following. Return concise, actionable revision guidance rather than a new
  report. Greetings, closings, follow-up offers, and meta-commentary are defects that the
  guidance must require the reviser to remove, not optional content to preserve. The
  response ends after its last actionable revision item without an offer or closing.
- **Revise:** produce the final Markdown report from the original question, research notes,
  draft, and useful critique. Correct supported issues, preserve evidence and URLs, retain
  important limitations, and return the report only. Do not mention upstream artifacts,
  ask questions, offer follow-up work, suggest alternate formats, or add greetings,
  closings, process narration, or other meta-commentary. End immediately after the report's
  final section.
  The report begins directly with its title or substantive answer and must not announce
  that it is synthesizing supplied notes. It ends on substantive report content or a source
  citation without a literal end marker.

These detailed instructions improve the expected stage outputs without adding retries,
post-processing, output repair, validation layers, or another model call. Model output
remains probabilistic, and the existing stage failure rules remain unchanged.

## CLI Contract

```text
uv run deep_research.py \
  "How does explicit planning affect tool-using LLM research agents?"
```

The question and these environment variables remain required:

- `OPENAI_API_KEY`;
- `MODEL_NAME`; and
- `TAVILY_API_KEY`.

`MODEL_NAME` must identify a model compatible with the required Structured Outputs schema
and the existing custom function tools. `python-dotenv` loads the repository-root `.env`.
Normal output goes to standard output and fatal errors go to standard error. Missing input
or configuration makes no external request.

Progress uses the fixed top-level stage labels `Plan`, `Research`, `Write`, `Critic`, and
`Revise`, including their one-based position out of five. Successful output makes visible:

- when planning starts and completes;
- the complete validated plan;
- how many research tasks will run;
- the active task's number and title;
- model turns, tool activity, and remaining tool budget within that task;
- completion of every task and report stage; and
- every task's research notes, the combined research notes, the draft, the critique, and
  the final Markdown report in labeled sections.

## Limits and Stopping Contract

The plan contains at most 4 research tasks. Each task independently preserves the release
0.3.0 limits of at most 10 research model turns, 8 tool execution attempts, and 5 results
per tool call. The counters restart for each task. The outer task-start line identifies the
active task before its generic Research and Tool progress labels begin.

With `N` validated tasks, a successful run makes one Plan request, at least `N` Research
requests, and exactly three report-stage requests. Every non-terminal Research turn with
automatic tool selection contains at least one function call and therefore consumes at
least one tool attempt. The eighth attempt occurs no later than turn 8, and the forced
final-notes request occurs no later than turn 9. The effective hard maximum is therefore
`4 + 9N` model requests and `8N` tool execution attempts; because `N` is at most 4, a run
can make no more than 40 model requests or 32 tool execution attempts. The inherited
10-turn guard remains a secondary safety bound.

Malformed, unknown, failed, and budget-exceeding tool calls retain the release 0.3.0
behavior and count against the current task's tool budget. After that task's eighth
attempt, its next model turn passes the existing tool definitions with
`tool_choice="none"` and requests final notes from its own history. A task succeeds only
when the model returns non-empty notes without requesting another function. If that final
request unexpectedly returns a formal function call despite `tool_choice="none"`, the task
fails instead of attempting another tool or model turn.

The workflow stops after all tasks finish and the three report stages succeed. It does not
stop early because a criterion appears satisfied, extend research because a criterion
appears unmet, or modify the plan for any observed result.

## Observability Contract

Live terminal output remains the complete observability mechanism. The validated plan and
task boundaries add visible intent to the existing turn and tool progress. Full
task-scoped notes, combined research notes, draft, critique, and final report make each
model-facing workflow boundary directly inspectable. The terminal does not print raw
structured-output JSON, Pydantic representations, prompts, complete Responses API
histories, tool payloads, secrets, or model reasoning items.

The plan is an application-facing list of research tasks and completion criteria. It must
not request, store, or claim to expose private chain-of-thought. This release adds no
structured trace.

## Artifact Contract

Release 0.4.0 creates no run directory and writes no application output files. The plan,
task-scoped notes, draft, critique, and final report remain in memory. The validated plan
and every in-memory result are printed in full, including each task's notes, the combined
research notes, the draft, the critique, and the final report.

## Failure Behavior

Missing input or configuration, a planner API error, an unsupported structured-output
schema, a planner refusal, an incomplete planner response, a missing or invalid parsed
plan, any fatal research-task error, an empty required report-stage output, or a later API
error prints a concise fatal error and exits nonzero.

Planner failure stops before the plan is printed and before any research tool can run. A
research-task failure stops the workflow immediately: later tasks and all report stages do
not run. A Write, Critic, or Revise failure stops at that stage. There are no retries,
schema-repair calls, fallback plans, skipped tasks, partial reports, or output artifacts.
Ordinary tool errors remain linked function outputs for the active Agent and do not by
themselves stop the run.

## Implementation Constraints

- Keep the planner, Pydantic plan models, sequential task execution, Agent loop,
  Write-Critic-Revise workflow, CLI, and terminal output in `deep_research.py`.
- Keep all model instruction and application-owned model-input constants in the
  repository-root `agent_instructions.py` as plain strings without model calls, tools,
  state, validation, or post-processing logic.
- Keep custom tool definitions and implementations in `agent_tools.py` without changing
  their release 0.3.0 external behavior.
- Add Pydantic as a direct runtime dependency because the application now imports and owns
  the structured plan models; do not rely on it only as an OpenAI SDK transitive
  dependency.
- Use Pydantic v2 models and field constraints at the planner boundary. Keep Responses API
  histories and task-result collections as plain lists and dictionaries.
- Use the synchronous OpenAI Responses API directly and keep `llm_call` as a thin wrapper
  returning the SDK `Response`.
- Make exactly one planning request. Do not implement a planner loop, plan repair, or
  replanning.
- Invoke the existing `agent_loop` sequentially once per task with fresh history and
  independent existing limits.
- Keep sequential task execution, task progress, task-level error context, and note
  aggregation in one `execute_research_plan` function that returns combined note text.
- Keep `agent_loop` task-agnostic. It receives only its research input and runtime
  dependencies; `execute_research_plan` owns task numbering, titles, counts, and task-level
  failure context.
- Keep report-stage calls explicit in `research_workflow`; do not introduce a workflow
  engine, planner framework, base Agent class, task class hierarchy, repository layer, or
  provider abstraction.
- Preserve `store=False` and do not use `previous_response_id` or the Conversations API.
- Preserve the existing tool and model-turn budgets and sequential execution behavior.
  Use `tool_choice="auto"` while Research tool budget remains and `tool_choice="none"` for
  the final notes request after it is exhausted. Do not add a separate synthesis-stage
  instruction set.
- Do not add file output, structured tracing, retries, caching, streaming, asynchronous
  code, concurrency, hosted tools, MCP, automated tests, Ruff, or mypy.

## Manual Acceptance Scenario

With valid configuration and a Structured Outputs-compatible model, run:

```text
uv run deep_research.py \
  "What evidence do one recent arXiv paper and one current web source give for planning \
  before tool execution in LLM research agents? Compare one benefit, one failure mode, \
  and one limit; cite both sources."
```

Confirm that:

1. Plan, Research, Write, Critic, and Revise complete once in that order;
2. exactly one Plan model request occurs before any research request or tool call;
3. the terminal prints one valid plan containing 1 through 4 numbered tasks and 1 through
   3 non-empty completion criteria per task;
4. every research task starts and completes once in plan order, with its own turn and tool
   counters;
5. Tavily and arXiv are both used somewhere in the complete research stage without
   printing their payloads;
6. every task's notes, the combined research notes, draft, critique, and final report are
   printed in labeled sections, while only combined note text reaches Write in plan order
   without plan or task metadata;
7. Write begins only after every research task completes;
8. the final report is non-empty, addresses the requested comparison, and cites at least
   one returned arXiv source and one returned web source;
9. the program creates no run directory or application output files; and
10. the process exits successfully.

Then run without `TAVILY_API_KEY` and confirm a configuration error, no model or tool
request, and a nonzero exit. In an isolated planner-boundary check, provide a refused,
incomplete, missing, or schema-invalid planner result and confirm that the workflow exits
nonzero without starting Research. In an isolated task-failure check, make the first task's
forced final-notes request fail or return no text and confirm that no later task or report
stage begins.
In an isolated tool-budget check, exhaust one task's eight tool attempts and confirm its
next model request uses the normal Research instructions, passes the Research tools with
`tool_choice="none"`, includes the budget-exhausted input, and does not execute another
tool.

## Completion Criteria

The specification may become `Verified` after these checks pass:

```text
uv run python -m py_compile deep_research.py agent_instructions.py agent_tools.py
uv run deep_research.py --help
```

The success, configuration-failure, planner-boundary-failure, and task-stopping scenarios
must also pass. Inspect the printed plan, task ordering, task-note association, combined
research notes, draft, critique, final report, and absence of application output files.
Confirm that project documentation, direct dependencies, lock file, and project version
match the implementation. Automated tests, Ruff, and mypy are not required.

## Out of Scope

Clarification, a `ResearchBrief`, plan approval or editing, multiple planning rounds, plan
repair, replanning, adaptive task creation, automatic completion-criterion scoring,
evidence sufficiency decisions, gap or contradiction ledgers, task dependencies, shared
research state, supervisor-worker architecture, isolated worker identities, multi-agent
execution, concurrency, retries, checkpoints, file artifacts, structured traces, selected-
page reading, arbitrary URL fetching, deterministic citation validation, source-quality
scoring, caching, streaming, context compaction, hosted OpenAI tools, MCP, automated
evaluation, automated tests, Ruff, and mypy.
