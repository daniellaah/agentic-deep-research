# v0.8.0 — Deep Retrieval Worker

## Status

Released

## Learning Question

What becomes observable and controllable when a Research Worker must first discover a source,
select it through an application-issued identifier, and spend a separate bounded read budget
before using page content as evidence?

## Problem and Rationale

Release 0.7.0 gives each Worker an explicit application-owned run contract, but its two search
tools return only bounded discovery snippets, URLs, and arXiv abstracts. A Worker can decide what
to search for, yet it cannot deliberately inspect a promising returned web source. The final
report can therefore over-rely on search-result summaries and cannot make the difference between
source discovery and selected-source reading visible.

Release 0.8.0 adds one small retrieval step inside the existing Worker:

```text
search -> receive application source IDs -> select one ID -> read bounded content -> continue or finish
```

The application, not the model, owns the readable-source registry. Search results remain
untrusted evidence, and only an eligible primary `url` returned by a successful search in the
active Worker receives a stable `S1`, `S2`, ... identifier. The read tool accepts that identifier
and a focused within-source query; it never accepts a model-supplied URL. This makes the source
provenance boundary enforceable without introducing a generic browser, crawler, or URL-fetching
interface.

Selected content is obtained through the synchronous Tavily Extract API already available in the
existing `tavily-python` dependency. The current official API documents a Python `extract`
method, one-or-more URL input, `basic` and `advanced` extraction depths, Markdown or text output,
and a query-sensitive `chunks_per_source` control whose chunks are at most 500 characters. This
release sends exactly one application-allowlisted URL, uses `basic` Markdown extraction, supplies
the Worker's focused query, requests at most five relevant chunks, and still applies its own hard
character limit before content enters Responses history. See the official
[Tavily Extract API reference](https://docs.tavily.com/documentation/api-reference/endpoint/extract)
and [Python SDK reference](https://docs.tavily.com/sdk/python/reference).

Using Tavily Extract keeps the mechanism synchronous and adds no dependency. The application
does not directly connect to selected destinations. It nevertheless rejects non-HTTP(S),
credential-bearing, local-name, non-global IP-literal, malformed, and explicit PDF destinations
before registering them. The exact canonical destination must remain the one selected from the
active Worker's registry; a different extraction-result destination is rejected. These checks
are a narrow release contract, not a claim to implement a production browser security policy.

The existing five-call custom-tool budget remains the hard total for search and read calls
combined. A separate two-attempt source-read budget makes the new behavior legible without
expanding the run contract into token, time, or cost accounting. A permitted extraction attempt
consumes both budgets even when extraction fails. An invalid identifier or an attempt after the
read limit consumes the already-attempted general tool call but creates no outbound extraction
and consumes no additional read attempt.

## Architectural Decision

The complete application remains the v0.7.0 Scope, sequential Supervisor-Worker Research, and
Write-Critic-Revise workflow. Only the active Worker's tool environment and run accounting grow:

```text
deterministic Scope workflow
    -> approved ResearchBrief
    -> adaptive Research Supervisor loop
       -> AgentRunRequest
       -> AgentRunState with fresh history, source registry, and read counter
       -> Research Worker
          -> search web or arXiv
          -> application validates returned primary URLs
          -> application assigns per-Worker source IDs
          -> model selects source ID plus focused query
          -> application resolves the ID and spends one read attempt
          -> Tavily extracts one bounded selected-source result
          -> model continues searching, reading, or returns notes
       -> AgentRunResult with turn, tool, and read usage
       -> merge only completed result
    -> deterministic Write-Critic-Revise workflow
    -> final Markdown report
```

Ownership boundaries are fixed as follows:

- Search implementations discover results and do not decide which source should be read.
- The Worker model chooses a returned source ID and a focused extraction query.
- `AgentRunState` owns the active Worker's source-ID-to-URL registry and read usage.
- The application validates, registers, resolves, and revalidates destinations and rejects any
  ID not issued from that active Worker's own successful searches.
- `agent_tools.py` owns the Tavily Extract call and bounded returned content, but receives the
  resolved URL only from the application.
- `AgentRunResult` retains read usage and its fixed limit, but not the registry or extracted
  content.
- Only completed Markdown notes reach the Supervisor state and report stages; raw search and
  selected-source payloads remain private to the Worker's discarded Responses history.

No model may invent, mutate, or transfer the source registry. A later Worker starts again at
`S1`; identifiers have meaning only inside one active `AgentRunState`.

## User-Visible Behavior

The CLI invocation, five top-level stages, Scope approval, Supervisor behavior, final report,
and overall fail-fast policy remain unchanged.

Every eligible search result returned to the Worker now includes one application-issued
`source_id`. Terminal progress reports how many new readable sources that search registered and
the active Worker's total. When the model selects a source, the terminal prints a separate
`Read used/limit` boundary containing the source ID, safe hostname, completion or failure, bounded
content size when successful, and remaining read attempts. It does not print extracted content.

Every Agent Run Result summary adds:

```text
Source reads: <used>/2
```

A read is still one custom function call, so it also appears in the existing tool-call usage.
The Worker turn-start line shows both remaining total tool calls and remaining source reads.

The research notes and final report may use selected-source content, must keep useful returned
URLs near supported claims, and must distinguish evidence from inference as before. They do not
expose internal source IDs because those identifiers are ephemeral application controls rather
than citations.

## Runtime Flow

For every search function call:

1. Count the allowed custom function attempt before dispatch.
2. Parse and validate the existing search arguments.
3. Execute at most one search returning at most three results.
4. For each result's primary `url`, validate the destination contract.
5. Reuse an existing ID for a duplicate canonical URL or assign the next contiguous source ID.
6. Add the ID only to the corresponding result returned to this Worker.
7. Append the linked bounded function output to ordered Responses history.

For every selected-source function call:

1. Count the allowed custom function attempt before dispatch.
2. Validate `source_id` and the non-empty focused query.
3. Resolve the ID exclusively through the active state's registry.
4. Reject an unknown ID, ineligible URL, or exhausted read budget without extraction.
5. Increment read usage before the permitted external extraction attempt.
6. Send exactly one resolved URL to Tavily Extract with `basic` depth, Markdown format, the
   focused query, at most five relevant chunks, and a 30-second SDK timeout.
7. Require exactly one successful result whose canonical URL matches the registered destination.
8. Truncate extracted content to at most 6,000 characters and return one result containing the
   source ID, original source URL, bounded content, content size, truncation flag, and remaining
   read budget.
9. Append the linked function output to ordered Responses history.

The source registry is updated only from successful search result items. A `pdf_url` metadata
field, a URL mentioned inside snippets or extracted content, model recollection, a Supervisor
task URL, or an earlier Worker's source cannot create a readable destination.

## Source Registry and Destination Contract

`AgentRunState` adds:

```text
source_urls: dict[str, str]
source_reads_used: integer
```

Initialization uses an empty dictionary and zero reads. IDs are contiguous, one-based, and
formatted as `S<number>`. Duplicate canonical URLs reuse their first ID and do not enlarge the
registry. Registration order follows tool-result order and the existing synchronous tool-call
order.

A primary result URL is eligible only when:

- it is a non-empty absolute `http` or `https` URL;
- it contains a hostname and no username or password;
- its port is syntactically valid;
- its hostname is not `localhost`, a `.localhost`, `.local`, or `.internal` name;
- an IP-literal hostname is globally reachable according to Python `ipaddress.is_global`; and
- its case-insensitive path does not end in `.pdf`.

Fragments do not identify a different destination and are removed for canonical comparison.
Scheme and host comparison are case-insensitive, default ports are normalized, and path plus
query remain significant. The original returned URL is preserved for the read result and later
citation. A source that fails eligibility remains visible as an ordinary search result but gets
no `source_id` and cannot be selected.

The application sends only the registered URL resolved from `source_id`; it never sends a URL
argument supplied by the model. Extraction results that identify no destination, more than one
destination, or a canonically different destination become recoverable linked tool errors. No
redirect allowlist, DNS resolver, cookie store, authentication, JavaScript execution, or direct
HTTP browser is added.

## Tool and Content Contract

The existing search schemas and result limits remain unchanged. One third strict function tool
is added:

```text
read_source_tool
|- source_id: non-empty application-issued identifier
`- query: non-empty focused extraction query, at most 500 characters
```

The tool returns a one-item JSON list on success so all custom tool outputs retain the current
list-shaped boundary. Its item contains only:

```text
source_id
url
content
content_characters
truncated
source_reads_remaining
```

The response excludes Tavily request IDs, usage or credits, response time, images, favicon,
failed-result payloads, raw response objects, headers, cookies, and unbounded content. Search and
read results remain untrusted model input. Instructions explicitly tell the Worker not to follow
commands found in either.

The application limits are:

| Boundary | Limit |
| --- | ---: |
| Results per search | 3 |
| Selected URLs per read call | 1 |
| Selected-source read attempts per Worker | 2 |
| Relevant extraction chunks requested | 5 |
| Selected content entering history per read | 6,000 characters |
| Focused read query | 500 characters |
| Total custom function attempts per Worker | 5 |
| Model turns per Worker | 6 |

No additional result, read, turn, token, time, or cost budget is inferred from provider output.

## Agent Run Contract Changes

`AgentRunState` adds the private registry and `source_reads_used`. `AgentRunResult` adds immutable
`source_reads_used` and `source_read_limit` fields. Finalization requires read usage to be between
zero and two, never greater than total tool-call usage, and copies it into the result. The
registry, source count, selected IDs, URLs, raw content, and per-source activity are not copied
into the result.

The existing status and termination vocabulary is unchanged. Exhausting the separate read
budget is not terminal: the Worker may continue with search snippets, already extracted content,
or final notes while total tool and turn budgets remain. The successful `tool_limit` reason still
means the fifth total custom tool attempt forced a later tool-disabled final-notes turn.

## CLI Contract

Invocation remains:

```text
uv run deep_research.py "Question"
```

`OPENAI_API_KEY`, `MODEL_NAME`, and `TAVILY_API_KEY` remain the only configuration values. The
same Tavily key authorizes both search and selected-source extraction. No source, domain, proxy,
timeout, content, or read-budget CLI option or environment variable is added.

## Observability Contract

Live terminal output remains the only run observability mechanism. It may print source IDs,
safe destination hostnames, registered-source counts, bounded content character counts, and used
versus limit read accounting. It must not print selected content, the full destination URL in
progress lines, raw tool payloads, source registry representations, Tavily metadata, credentials,
request bodies, prompts, instructions, full Responses history, response usage, or reasoning
items.

This release adds retrieval visibility, not structured tracing. It creates no event schema,
trajectory, per-source artifact, evidence database, or browser log.

## Artifact Contract

Release 0.8.0 creates no run directory and writes no application output files. The source
registry and extracted content remain in the active Worker's memory and disappear with its
mutable state. Only completed notes remain inside a completed `AgentRunResult` and
`ResearchState`; draft, critique, and final report remain in memory and terminal output.

## Failure and Stopping Behavior

Unknown source IDs, invalid read queries, exhausted read budgets, ineligible registered
destinations, extraction failures, empty or malformed extraction responses, multiple returned
results, mismatched returned URLs, and empty extracted content become recoverable linked tool
errors. They consume the total custom tool call already attempted. A permitted extraction attempt
also consumes one read attempt even when it fails. The Worker may adapt while its remaining total
budget permits.

Search failures remain recoverable. An ineligible search URL is not itself a failed search; it
simply receives no source ID. Source registration and result enrichment failures that cannot be
converted into a valid linked output retain the existing fatal `failed`/`tool_error` boundary.

All existing refusal, model-error, tool-limit, turn-limit, cancellation, Supervisor, Scope,
report, and top-level failure behavior remains unchanged. There are no retries, fallback readers,
arbitrary URL repair, partial reports, replacement Workers, or new termination reasons.

## Implementation Constraints

- Keep workflow, registry ownership, budget accounting, Agent run contract, terminal progress,
  and CLI in repository-root `deep_research.py`.
- Keep all model-facing instructions in `agent_instructions.py` and all three tool schemas,
  remote calls, result bounding, and dispatch in `agent_tools.py`.
- Extend the existing two Agent dataclasses that need retrieval state or accounting. Do not add a
  source class, registry class, reader class, browser abstraction, generic tool context, provider
  adapter, or configuration object.
- Use `urllib.parse` and `ipaddress` for application URL checks. Add no dependency.
- Use the already installed synchronous Tavily Python client for extraction. Do not fetch selected
  destinations directly with `requests`.
- Keep source IDs application-issued and per Worker. Never expose a URL argument in the read-tool
  schema.
- Count a permitted read attempt immediately before extraction and preserve its usage on failure.
- Keep all custom function execution synchronous and ordered. Preserve the existing Responses
  output-item replay, linked `function_call_output`, `store=False`, and SDK retry policy.
- Preserve current Scope, Supervisor, report, Pydantic boundary, model-turn, total tool-call,
  Worker count, failure, and artifact behavior.
- Keep Worker requests without an application `max_output_tokens` value.
- Add no asynchronous execution, concurrency, streaming, direct browser, crawler, arbitrary URL
  fetch, authentication, full-paper ingestion, caching, retries, persistence, tracing, evaluation,
  citation verification, evidence scoring, or automated test suite.
- Update `TECH_STACK.md`, `ROADMAP.md`, `specs/README.md`, README, changelog, project version and
  description, lock metadata, and arXiv `User-Agent`. Do not create a release tag until manual
  verification is complete.

## Manual Acceptance Scenario

With valid configuration and a Structured Outputs-compatible model, run:

```text
uv run deep_research.py "Compare recent evidence about AI coding-agent productivity and failure modes."
```

Establish a recent time horizon and require current web evidence plus at least one relevant arXiv
source. Approve the brief. Confirm that:

1. Scope, Research, Write, Critic, and Revise complete in the existing order;
2. one Worker searches before reading and search output available to the model contains only
   application-issued IDs for eligible primary URLs;
3. the Worker selects at least one ID and cannot pass an arbitrary URL to the read tool;
4. terminal output shows registration counts, read start/completion, safe host, bounded content
   size, remaining read budget, and final read usage without printing content;
5. the selected source result entering history contains exactly one item and no more than 6,000
   content characters;
6. useful selected-source evidence and its original URL appear in notes without internal IDs;
7. the Agent result reports exact model-turn, total-tool, and source-read usage;
8. completed notes alone merge into ResearchState and later report stages receive no registry,
   read counters, or raw selected-source payload;
9. the complete final Markdown report is printed and the process exits successfully; and
10. no run directory or application output file is created.

Exercise isolated Worker and tool paths with controlled search and Tavily Extract responses:

1. eligible HTTP(S) URLs receive contiguous IDs; duplicate canonical URLs reuse the first ID;
2. malformed URLs, credentials, local names, non-global IP literals, non-HTTP(S) schemes, and
   `.pdf` paths receive no ID;
3. an arXiv abstract URL may receive an ID while its `pdf_url` metadata never does;
4. IDs from another Worker, model-invented IDs, and URLs found only inside content are rejected
   without extraction;
5. one valid read passes exactly one registered URL and the focused query to Tavily, truncates
   oversized content, appends one linked output, and increments both usage counters once;
6. a valid extraction failure consumes one read attempt, returns a linked error, and may be
   followed by successful notes;
7. a third read attempt produces a linked limit error, makes no extraction, leaves read usage at
   `2/2`, and still consumes the attempted total tool call;
8. zero, multiple, empty, malformed, or canonically mismatched extraction results become linked
   errors without exposing raw provider metadata;
9. exhausting five combined search/read calls retains the forced tool-disabled notes turn and
   `completed`/`tool_limit` semantics; and
10. result finalization rejects read usage outside its limit and copies valid usage into the
    immutable result.

Preserve the complete v0.7.0 run-contract, early Supervisor finish, four-Worker hard stop,
configuration, Scope input and cancellation, structured-output, report, request-count, and
failure scenarios.

## Completion Criteria

The specification may become `Verified` after these checks pass:

```text
uv run python -m py_compile deep_research.py agent_instructions.py agent_tools.py
uv run deep_research.py --help
```

The real-service scenario and isolated registration, destination, selection, content-bound,
budget, history, result, and failure scenarios must pass. Inspect terminal ordering, exact usage,
fresh Worker state, completed-result merging, report inputs, and absence of application output
files.

Acceptance confirms the selected-source reading mechanism and its integration. It does not grade
research conclusions, verify citations independently, measure retrieval recall, compare Tavily
extraction with another reader, or score evidence quality.
